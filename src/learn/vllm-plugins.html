The idea

vLLM can load extra code that is not in its own source tree. The extra code is a {{term plugin | plugin}}. A plugin declares an {{term entry-point | entry point}} in its packaging metadata. vLLM finds the entry point by its group name and calls it. afd-plugin uses this to add AFD, and it changes no vLLM file.

A {{term general-plugin | general plugin}} is the simplest kind. It is one function. vLLM calls the function with no arguments. The function then registers models, patches vLLM functions, or sets up whatever the plugin needs. For afd-plugin the function is {{term register-afd}}.

An everyday comparison. Think of a start-up checklist with named tasks. The host reads the list and runs each task once. The comparison stops here: vLLM runs the list again in every process it starts, and each run starts fresh. So one plugin function runs many times, in many processes.

The picture

Read the top panel left to right. Process 0 starts first, then the engine core, then the workers. Each process loads the plugins once. The lower panel shows why a plugin must run safely more than once.

The diagram shows each worker as a separate process. This is true for the multi-process executor ({{cite vllm:vllm/v1/executor/abstract.py:70-73}}). With a single device, vLLM uses the in-process executor, so the worker runs inside the EngineCore process ({{cite vllm:vllm/v1/executor/abstract.py:74-77}}). The worker call then hits the guard and does not reload the plugins.

In the code

Step 1: The five entry-point groups

vLLM defines five plugin groups. Each group loads in a different set of processes. The comments in the file say where ({{cite vllm:vllm/plugins/__init__.py:16-30}}). afd-plugin uses only the first group, vllm.general_plugins.

GroupLoaded in
vllm.general_pluginsAll processes: process 0, the engine core and the workers ({{cite vllm:vllm/plugins/__init__.py:16-18}}).
vllm.io_processor_pluginsProcess 0 only ({{cite vllm:vllm/plugins/__init__.py:19-20}}).
vllm.platform_pluginsAll processes, when current_platform is first used ({{cite vllm:vllm/plugins/__init__.py:21-23}}).
vllm.stat_logger_pluginsProcess 0 only, in async serving mode ({{cite vllm:vllm/plugins/__init__.py:24-26}}).
vllm.endpoint_pluginsThe API server front-end process only ({{cite vllm:vllm/plugins/__init__.py:27-30}}).

Step 2: load_plugins_by_group and load_general_plugins

Two functions do the work. load_plugins_by_group finds the entry points of one group, filters them, and loads each one ({{cite vllm:vllm/plugins/__init__.py:36-74}}). {{term load-general-plugins}} loads the general group, then calls each loaded function ({{cite vllm:vllm/plugins/__init__.py:87-90}}).

The filter is the VLLM_PLUGINS environment variable. vLLM parses it in envs.py. When the variable is not set, the value is None and vLLM loads every plugin ({{cite vllm:vllm/envs.py:1146-1150}}). When the variable is an empty string, the value is [""], which matches no plugin name, so vLLM loads none ({{cite vllm:vllm/plugins/__init__.py:63-64}}).

Step 4: How a plugin registers models, workers and config

A general plugin registers things through vLLM APIs that run in the same process.

  • Models. The plugin calls {{term model-registry}}'s register_model(name, model_cls). The class can be a string in the "module:Class" form, so vLLM imports it only when it is needed ({{cite vllm:vllm/model_executor/models/registry.py:1126-1141}}).
  • Workers. There is no register API for a worker. vLLM reads the worker class name from parallel_config.worker_cls and imports it by its qualified name ({{cite vllm:vllm/v1/worker/worker_base.py:273-277}}). A plugin changes the worker by setting this field.
  • Config. vLLM has one open config field, additional_config, for out-of-tree config ({{cite vllm:vllm/config/vllm.py:434}}). afd-plugin reads its "afd" key.

Step 5: What a plugin can and cannot change

A general plugin runs real Python in the vLLM process. So it can change vLLM behaviour by monkey-patching: it replaces a vLLM function or method with its own. afd-plugin does this with its {{term patch | compat patches}}.

A plugin cannot do some things:

  • It cannot change a name that another module already bound with from ... import. That name keeps the original object. A patch that replaces a module attribute (module.func) changes only later attribute lookups. So the patch must run before the code that reads the attribute.
  • It cannot change compiled C++ or CUDA code. It can only change the Python that calls it.
  • It cannot add a new command-line flag on its own. The plugin function gets no parser.

There is one near-exception for the command line. vLLM calls load_general_plugins() at the start of add_cli_args ({{cite vllm:vllm/engine/arg_utils.py:3003-3009}}). So a plugin that registers a new quantization method or a new platform makes it a valid choice for the existing --quantization or --device flag.

Deep dive

vLLM calls load_general_plugins() from five places. The guard makes it run at most once per process, but a new process resets the guard. So the plugin runs in each of these processes.

#Call siteFunctionProcessWhen
1{{cite vllm:vllm/engine/arg_utils.py:3009}}AsyncEngineArgs.add_cli_args Process 0 (launch / API)While the CLI parser is built, so a plugin can extend it.
2{{cite vllm:vllm/engine/arg_utils.py:839}}EngineArgs.__post_init__ Process 0 (launch / API)When the engine config is built from the args.
3{{cite vllm:vllm/v1/engine/core.py:119}}EngineCore.__init__ EngineCore processWhen the engine core starts.
4{{cite vllm:vllm/v1/worker/worker_base.py:271}}WorkerBase.init_worker Each worker processBefore the worker class is resolved and built.
5{{cite vllm:vllm/model_executor/models/registry.py:1570}}_run Model-inspection subprocessIn the short-lived subprocess that resolves a model class ({{cite vllm:vllm/model_executor/models/registry.py:1536-1564}}).

Call sites 1 and 2 are both in process 0. The guard means the second one returns early. The other three run in separate processes, so each one loads the plugins again.

vLLM keeps a module-level flag, plugins_loaded, that starts at False ({{cite vllm:vllm/plugins/__init__.py:33}}). The first call sets it to True; a later call in the same process returns at once ({{cite vllm:vllm/plugins/__init__.py:82-85}}).

The flag is Python module state. vLLM starts workers with spawn in many setups, which copies no Python state. So each new process imports the modules again, the flag is False again, and the plugin runs again. The function's own docstring warns about this ({{cite vllm:vllm/plugins/__init__.py:78-81}}).

afd-plugin handles it with a second guard of its own, _registered, inside register_afd ({{cite afd_plugin/__init__.py:150-153}}). The guard stops repeated work in one process; it does not stop the many processes. So the registration steps must be safe to run more than once.

In afd-plugin

afd-plugin is a single general plugin. Three facts connect it to this page:

  • The entry point is afd = "afd_plugin:register_afd" in the vllm.general_plugins group ({{cite pyproject.toml:45-46}}). See {{link concepts/plugin-entry-point}}.
  • The function register_afd applies the patches and registers the models and the routing strategy ({{cite afd_plugin/__init__.py:142-216}}). See {{link concepts/plugin-entry-point}} and {{link code/init-py}}.
  • One compat patch sets the worker class. It rewrites parallel_config.worker_cls, but only when it is "auto" ({{cite afd_plugin/compat/patches/config_validation.py:60}}, {{cite afd_plugin/compat/patches/config_validation.py:92}}). See {{link concepts/worker-selection}} and {{link concepts/compat-patches}}.

What can go wrong

  • VLLM_PLUGINS set to empty. An empty string loads no plugins, so AFD does not activate ({{cite vllm:vllm/envs.py:1146-1150}}).
  • A plugin that is not idempotent. The function runs in many processes. State kept in one process does not reach the others.
  • A patch that runs too late. A monkey-patch cannot change a name that another module already bound with from ... import. The patch must run before that import, or before the attribute lookup it changes.

Why it matters. AFD is installed only through this plugin mechanism. If the plugin does not load, or a patch runs too late, the two roles do not form and the run fails.

Which entry-point group does afd-plugin use, and what is its entry point?

The vllm.general_plugins group. The entry point is afd = "afd_plugin:register_afd" ({{cite pyproject.toml:45-46}}).

 What does VLLM_PLUGINS do when it is set to an empty string?

It loads no plugins. The empty string parses to [""], which matches no plugin name ({{cite vllm:vllm/envs.py:1146-1150}}, {{cite vllm:vllm/plugins/__init__.py:63-64}}).

 Why must a general plugin be safe to run more than once?

vLLM calls it in several processes (process 0, the engine core, each worker and a model-inspection subprocess). The plugins_loaded guard resets in every new process ({{cite vllm:vllm/plugins/__init__.py:82-85}}).

 How does a plugin set the worker class, since there is no register API for it?

It sets parallel_config.worker_cls. vLLM reads that field and imports the class by its qualified name ({{cite vllm:vllm/v1/worker/worker_base.py:273-277}}).

 A plugin cannot add a new CLI flag. How can it still change what --quantization accepts?

vLLM calls load_general_plugins() at the start of add_cli_args. So a plugin that registers a new quantization method before the parser is built makes it a valid choice for the existing flag ({{cite vllm:vllm/engine/arg_utils.py:3003-3009}}).

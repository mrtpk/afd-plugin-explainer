This page names each box, with its vLLM line and the AFD hook on it. --- AFD hooks into one chain of vLLM v1 parts: API server, {{term enginecore | EngineCore}}, executor, worker, {{term model-runner-v2 | Model Runner V2}} and the model.

The idea

vLLM v1 runs a request through a fixed chain of parts. The API server process builds the config and owns HTTP. The EngineCore process holds the scheduler and the executor. The executor starts the workers. Each worker owns one device and builds a model runner, which runs the model.

afd-plugin does not replace this chain. It changes six small points along it: the config, the EngineCore start, the worker class, the model runner class and the model class. This page names each box once, gives its vLLM line, and points to the AFD hook.

An everyday comparison. Think of a factory line with six stations. AFD does not rebuild the line; it changes the tool at a few stations. The comparison stops here: one station (the FFN EngineCore) stops the line early and runs its own loop.

The picture

Read the boxes top to bottom. Each box runs in a process or is built inside one. The violet row on each box is the one place AFD changes it. The {{term plugin}} loads once in each process, so the hooks take effect everywhere they are needed.

Deep dive

The number of processes depends on the executor ({{cite vllm:vllm/v1/executor/abstract.py:70-77}}).

  • Multi-process executor (mp). Each worker is a separate process. The plugin loads again in each one, so the worker and runner hooks run in the worker process ({{cite vllm:vllm/v1/worker/worker_base.py:271}}).
  • Single-device executor (uni). The worker runs inside the EngineCore process ({{cite vllm:vllm/v1/executor/abstract.py:74-77}}). The worker's plugin load hits the guard, so it does not reload the plugins.

The config hook is different from the others. It runs in the API server process, while create_engine_config builds the config ({{cite afd_plugin/compat/patches/config_validation.py:51-113}}). vLLM then pickles the config and sends it to the EngineCore and worker processes, so those processes do not rebuild it. The worker rewrite must therefore happen in the API server process, before the config is sent.

Five of the six boxes keep their normal vLLM job and only change a class or a field. The FFN EngineCore is different. After it builds the executor, the AFD patch returns before the scheduler and the KV cache are set up ({{cite afd_plugin/compat/patches/engine_core.py:56-68}}). The FFN side then runs a connector loop instead of vLLM's request loop ({{cite afd_plugin/compat/patches/engine_core.py:411-419}}). The attention EngineCore keeps the normal chain. The {{link concepts/roles}} page covers this split.

Which vLLM box holds the scheduler and the executor?

The EngineCore process. It builds both ({{cite vllm:vllm/v1/engine/core.py:134}}, {{cite vllm:vllm/v1/engine/core.py:162}}).

 When is the Model Runner V2 used?

When the V2 model runner is on; vLLM reads it from VLLM_USE_V2_MODEL_RUNNER ({{cite vllm:vllm/config/vllm.py:692-694}}, {{cite vllm:vllm/v1/worker/gpu_worker.py:469-482}}). AFD needs it on both roles.

 Why must the worker-class rewrite happen in the API server process?

vLLM builds the config there, then pickles it to the other processes. The rewrite runs inside create_engine_config before the config is sent ({{cite afd_plugin/compat/patches/config_validation.py:51-113}}).

 Which box does AFD not change?

The executor. AFD works through the worker the executor builds; it adds no executor patch ({{cite vllm:vllm/v1/executor/abstract.py:70-77}}).

 The FFN EngineCore and the attention EngineCore are the same vLLM class. What makes them behave differently?

The AFD EngineCore patch checks the role. For the FFN role it returns after building the executor and skips the scheduler and KV cache ({{cite afd_plugin/compat/patches/engine_core.py:56-68}}); the FFN side then runs a connector loop ({{cite afd_plugin/compat/patches/engine_core.py:411-419}}). The attention role keeps the normal chain.

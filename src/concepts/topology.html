This page shows how the role rank, the subgroups and the DP-metadata routes come from the topology sizes. scripts: viz/topology-mapper.js --- The P2P {{term connector}} builds one {{term afd-world | AFD world}}, ordered [F0..A0..]. The topology sizes decide the subgroups and the {{term dp-metadata | DP metadata}} routes.

The idea

Every AFD rank has a {{term role-rank | role rank}}: its position inside its own role group. The role rank comes from the data-parallel, context-parallel and tensor-parallel placement. The P2P connector lays all ranks out in one world: the FFN ranks first, then the attention ranks.

Inside that world, each FFN rank owns a {{term p2p-subgroup | subgroup}}: itself plus the attention ranks mapped to it. The subgroups carry hidden states (the {{term data-plane | data plane}}). The control plane is narrower: only some attention ranks send {{term dp-metadata | DP metadata}}. The connector needs at least as many attention ranks as FFN ranks.

An everyday comparison. Think of delivery routes. Each van (FFN rank) serves a block of addresses (attention ranks). The addresses are split into blocks that differ in size by at most one. The comparison stops here: the "addresses" also report back to the depot on a second, smaller list of routes (the control plane), which does not match the delivery blocks one-to-one.

In the code

Step 1: The role rank

resolve_role_rank linearizes the global data-parallel rank and the local context-parallel and tensor-parallel ranks ({{cite afd_plugin/distributed/topology.py:61-105}}). The formula is one line ({{cite afd_plugin/distributed/topology.py:92}}).

The role rank must be inside the role size (num_attention_ranks for the attention role, or num_ffn_ranks for the FFN role). An out-of-range rank raises ({{cite afd_plugin/distributed/topology.py:99-104}}).

Step 2: The world order

build_rank_mapping turns the role rank into a world rank ({{cite afd_plugin/distributed/topology.py:118-184}}). FFN ranks keep their role rank; attention ranks come after all FFN ranks ({{cite afd_plugin/distributed/topology.py:135}}, {{cite afd_plugin/distributed/topology.py:143}}).

Step 3: The subgroups

Each attention rank a joins the subgroup of FFN rank a * F // A ({{cite afd_plugin/distributed/topology.py:136}}). The reverse lookup lists a subgroup's attention ranks as a contiguous block ({{cite afd_plugin/distributed/topology.py:108-115}}). The FFN rank is always subgroup rank 0 ({{cite afd_plugin/distributed/topology.py:153-161}}).

Step 4: The A ≥ F rule

The P2P connector needs at least as many attention ranks as FFN ranks, so each FFN rank owns at least one attention peer. validate_p2p_topology raises otherwise ({{cite afd_plugin/distributed/topology.py:52-58}}).

Step 5: The DP-metadata routes

The control plane uses fewer ranks than the data plane. Only the first min_size attention ranks send DP metadata, where min_size = min(F, A). Under the A ≥ F rule, min_size equals F, so the first F attention ranks are the senders, one per FFN rank ({{cite afd_plugin/distributed/topology.py:164-170}}).

The group that joins the control plane is the FFN ranks plus those first attention ranks ({{cite afd_plugin/distributed/topology.py:42-43}}).

Step 6: The plugin-owned process groups

The connector builds its process groups without patching vLLM. A helper creates each one from a rendezvous at tcp://host:port ({{cite afd_plugin/distributed/afd_process_group.py:62-120}}). The GPU connector calls it twice: once for the AFD world, and once for the control plane ({{cite afd_plugin/connectors/gpu/p2p.py:269-314}}).

The AFD world rendezvous uses the afd_process_group_timeout_s config value (default 120) ({{cite afd_plugin/connectors/gpu/p2p.py:275}}, {{cite afd_plugin/config.py:67-70}}). The control-plane group uses a fixed 30-minute timeout ({{cite afd_plugin/connectors/gpu/p2p.py:313}}).

What can go wrong

This page folds DP and TP into one role rank and leaves out the context-parallel case. The interactive visual does the same. The real resolver reads the data-parallel, context-parallel and tensor-parallel ranks ({{cite afd_plugin/distributed/topology.py:61-92}}). The NPU connectors build their own topology; see {{link concepts/npu-overview}}.
  • Fewer attention ranks than FFN ranks. The P2P connector raises: num_attention_ranks must be ≥ num_ffn_ranks ({{cite afd_plugin/distributed/topology.py:52-58}}).
  • A role rank out of range. A role rank that is not inside the role size raises; the topology sizes must match the parallel placement ({{cite afd_plugin/distributed/topology.py:99-104}}).
  • Mismatched host, port or rank counts. The two roles must agree on host, port and the rank counts, or the rendezvous fails or times out ({{cite afd_plugin/connectors/gpu/p2p.py:50-54}}).

Why it matters. The subgroups and the DP-metadata routes come only from the topology sizes. If the two roles do not agree on them, the collective setup cannot complete.

In what order does the P2P world place the ranks?

FFN ranks first, then attention ranks: [F0, F1, ..., A0, A1, ...] ({{cite afd_plugin/distributed/topology.py:16-23}}). An attention rank's world rank is ffn_size + role_rank ({{cite afd_plugin/distributed/topology.py:135}}).

 Why must there be at least as many attention ranks as FFN ranks?

So every FFN rank owns at least one attention peer. validate_p2p_topology raises when num_attention_ranks < num_ffn_ranks ({{cite afd_plugin/distributed/topology.py:52-58}}).

 In 4A2F, which attention ranks does FFN rank 0 own for the data plane?

A0 and A1. The subgroup index is a * F // A, so 0*2//4 = 0 and 1*2//4 = 0 both map to F0; A2 and A3 map to F1 ({{cite afd_plugin/distributed/topology.py:136}}).

 In 4A2F, which attention ranks send DP metadata, and to whom?

Only A0 and A1. min_size = min(2, 4) = 2, so only the first two attention ranks are senders; A0 sends to F0 and A1 sends to F1 ({{cite afd_plugin/distributed/topology.py:164-170}}). A2 and A3 send hidden states but no DP metadata.

 Which timeout controls the AFD world rendezvous, and which controls the control plane?

The AFD world uses afd_process_group_timeout_s (default 120 s) ({{cite afd_plugin/connectors/gpu/p2p.py:275}}, {{cite afd_plugin/config.py:67-70}}). The control-plane group uses a fixed 30-minute timeout ({{cite afd_plugin/connectors/gpu/p2p.py:313}}).

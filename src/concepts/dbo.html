The idea

In AFD the attention side sends hidden states to the FFN side and waits for the result. If it waited with nothing else to do, the GPU would idle. {{term dbo | Dual-batch overlap}} (DBO) cuts each step into two {{term stage | stages}}. The attention side sends stage 0, then works on stage 1 while the FFN side computes stage 0. The two roles overlap.

DBO is a native vLLM feature. The plugin reuses it and adds two things: a {{term dbo-yield | yield}} op that hands control to the other stage between send and receive, and scoped {{term patch | patches}} that let DBO run even with one data-parallel rank.

An everyday comparison. Think of a cook with two pans. They start pan 1, and while it simmers they start pan 2, instead of standing and watching pan 1. The comparison stops here: AFD always uses exactly two pans, never three, and a validator enforces that.

In the code

Step 1: Exactly two stages

DBO turns on with --enable-dbo. In vLLM that sets the number of microbatches to two ({{cite vllm:vllm/config/parallel.py:599-601}}). AFD requires exactly two. The GPU validator raises for any other count ({{cite afd_plugin/validation.py:126-131}}).

Step 2: Each stage carries a stage index on the wire

Each stage gets a {{term stage | stage index}}, 0 or 1. The ubatch helper clones the parent AFD metadata per stage and sets the index and the stage count ({{cite afd_plugin/v1/worker/ubatch_wrapper.py:26-36}}).

The {{term remote-ffn-proxy | RemoteFFNProxy}} reads the stage index from the forward context and records it in the transfer metadata ({{cite afd_plugin/model_executor/models/deepseek_v2.py:136-143}}). So the FFN side knows which stage each tensor belongs to.

Step 3: The proxy yields between send and receive

Inside the proxy, the order is: send the hidden states, {{term dbo-yield | yield}}, then receive the FFN output ({{cite afd_plugin/model_executor/models/deepseek_v2.py:146-158}}). The yield is what lets the other stage run while this one waits.

The yield calls a {{term custom-op | custom op}}, manual_dbo_yield, registered once per process ({{cite afd_plugin/v1/worker/dbo.py:27-49}}). The op yields only when vLLM DBO is active; otherwise it does nothing ({{cite afd_plugin/v1/worker/dbo.py:52-54}}).

Step 4: The thresholds decide when a step splits

A step splits into two stages only when it is large enough. The recipes set two thresholds: --dbo-decode-token-threshold and --dbo-prefill-token-threshold ({{cite recipe/gpu/P2pNcclAFDConnector/deepseek_v2_lite/prefill_decode_colocation/2a2f_graph_dbo_dp1tp2.sh:23-25}}).

vLLM reads these in check_ubatch_thresholds: a decode batch splits when its token count reaches the decode threshold, a batch with a prefill when it reaches the prefill threshold ({{cite vllm:vllm/v1/worker/ubatch_utils.py:141-149}}).

Step 5: DP1 DBO through scoped patches

Native vLLM builds no ubatch runner when the data-parallel size is one. AFD coordinates the two stages locally, so it re-enables DP1 with two {{term scoped-patch | scoped patches}} ({{cite afd_plugin/compat/patches/gpu_mrv2_ubatching.py:263-282}}).

Deep dive

The blocks below give the two scoped patches, the threshold logic with numbers, and the yield mechanism.

AFD never edits vLLM. It swaps two module functions only for the time of one AFD call, then restores them.

The factory seam. use_gpu_mrv2_ubatch_factory replaces maybe_build_ubatch_runner while the attention runner initializes its KV cache ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:473-486}}). Native code returns None at DP1; the patched factory builds the native UBatchRunner and binds a DP1 child-context metadata factory ({{cite afd_plugin/compat/patches/gpu_mrv2_ubatching.py:47-73}}).

The dispatch seam. use_gpu_mrv2_dbo_dispatch replaces dispatch_cg_and_sync_dp for one execute_model call ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:340-349}}). Native DP1 dispatch returns before the DBO threshold decision; the patch applies the native threshold and ubatch policy locally, with no DP handshake ({{cite afd_plugin/compat/patches/gpu_mrv2_ubatching.py:194-226}}).

The child metadata. At DP1 the native DPMetadata.make asserts DP greater than one. The patch builds the same metadata directly, one forward context per microbatch ({{cite afd_plugin/compat/patches/gpu_mrv2_ubatching.py:83-115}}).

Both seams restore the original function in a finally block, so they affect only AFD's own calls ({{cite afd_plugin/compat/patches/gpu_mrv2_ubatching.py:268-271}}, {{cite afd_plugin/compat/patches/gpu_mrv2_ubatching.py:279-282}}).

The thresholds are fields on the vLLM parallel config. Their defaults are large:

FieldDefaultSet in the recipe
dbo_decode_token_threshold32 ({{cite vllm:vllm/config/parallel.py:227}})2
dbo_prefill_token_threshold512 ({{cite vllm:vllm/config/parallel.py:232}})12

The recipe lowers both so small test batches still split ({{cite recipe/gpu/P2pNcclAFDConnector/deepseek_v2_lite/prefill_decode_colocation/2a2f_graph_dbo_dp1tp2.sh:24-25}}). The check is simple ({{cite vllm:vllm/v1/worker/ubatch_utils.py:141-149}}):

  1. If ubatching is off, do not split.
  2. For a uniform decode batch, split when the token count reaches the decode threshold.
  3. Otherwise, split when the token count reaches the prefill threshold.

A worked example. With the recipe values and a pure-decode step of 8 tokens, 8 is at least 2, so the step splits into two stages of 4. A decode step of 1 token does not reach 2, so it runs as a single batch, with no DBO.

At DP1 this decision runs inside the patched dispatch, which also guards against an empty trailing stage ({{cite afd_plugin/compat/patches/gpu_mrv2_ubatching.py:213-215}}). At DP greater than one, native code makes the decision across ranks.

The yield is a no-return custom op, torch.ops.vllm.manual_dbo_yield. Its real implementation calls dbo_yield only when dbo_enabled is true ({{cite afd_plugin/v1/worker/dbo.py:33-34}}, {{cite afd_plugin/v1/worker/dbo.py:52-54}}). Its fake implementation does nothing, so torch.compile can trace through it ({{cite afd_plugin/v1/worker/dbo.py:36-37}}).

Registration is idempotent. A second call returns early, and a RuntimeError that says the op is already registered is swallowed ({{cite afd_plugin/v1/worker/dbo.py:30-49}}). The op is registered once at plugin start-up ({{cite afd_plugin/__init__.py:190-192}}).

The op takes the hidden-state tensor as its argument and marks it as mutated, so the compiler keeps the yield in the right place relative to the send and the receive ({{cite afd_plugin/v1/worker/dbo.py:40-45}}). The tensor value is not changed.

What can go wrong

This page shows the two-stage model and the AFD additions. It does not show the native microbatch slicing and thread handoff inside vLLM; those stay in vLLM and are cited where AFD scopes them.
  • The wrong number of ubatches. Any count other than two raises at config validation ({{cite afd_plugin/validation.py:126-131}}).
  • Thresholds set below the microbatch count. vLLM requires each threshold to be at least the number of microbatches ({{cite vllm:vllm/config/parallel.py:1093-1099}}).
  • A step that is too small. A step under the threshold does not split, so it runs with no overlap ({{cite vllm:vllm/v1/worker/ubatch_utils.py:144-149}}). This is expected, not an error.
  • DBO with a graph but not two ubatches. The graph policy raises when ubatching is on with any count other than two ({{cite afd_plugin/v1/worker/cuda_graph.py:72-77}}).

Why it matters. DBO keeps both roles busy. The attention side does useful work on one stage while the FFN side works on the other, instead of waiting. The two-stage limit and the yield placement are what make the overlap correct.

How many stages does DBO split a step into?

Exactly two. --enable-dbo sets the microbatch count to two ({{cite vllm:vllm/config/parallel.py:599-601}}), and the validator rejects any other count ({{cite afd_plugin/validation.py:126-131}}).

 What does the proxy do between the send and the receive?

It calls the DBO yield op, manual_dbo_yield, which hands control to the other stage ({{cite afd_plugin/model_executor/models/deepseek_v2.py:151-154}}, {{cite afd_plugin/v1/worker/dbo.py:33-34}}).

 A pure-decode step has 1 token, with the recipe thresholds. Does it use DBO?

No. 1 is below the decode threshold of 2, so check_ubatch_thresholds returns false and the step runs as a single batch ({{cite vllm:vllm/v1/worker/ubatch_utils.py:144-149}}, {{cite recipe/gpu/P2pNcclAFDConnector/deepseek_v2_lite/prefill_decode_colocation/2a2f_graph_dbo_dp1tp2.sh:24}}).

 Why does the yield op have a fake implementation that does nothing?

So torch.compile can trace through it. The real op yields only when DBO is active; the fake op returns None ({{cite afd_plugin/v1/worker/dbo.py:36-37}}, {{cite afd_plugin/v1/worker/dbo.py:52-54}}).

 Native vLLM does not build a ubatch runner at DP1. How does AFD run DBO there without editing vLLM?

It installs two scoped patches. use_gpu_mrv2_ubatch_factory builds the runner at DP1 during KV initialization; use_gpu_mrv2_dbo_dispatch applies the threshold policy locally during one execute_model call. Both restore the original on exit ({{cite afd_plugin/compat/patches/gpu_mrv2_ubatching.py:47-73}}, {{cite afd_plugin/compat/patches/gpu_mrv2_ubatching.py:194-226}}).

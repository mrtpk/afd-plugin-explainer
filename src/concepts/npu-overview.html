This page maps the NPU workers, runners, model wrappers, patches and the operator loader, and points to the NPU docs. --- AFD on Ascend NPU keeps the same {{term attention-role | attention}}/{{term ffn-role | FFN}} split as GPU. Only the {{term connector}} transport changes.

The idea

The NPU path is the one place this site covers Ascend code. The attention/FFN contract is the same as on GPU (see {{link concepts/connector-contract}}): the attention side sends hidden states, the FFN side runs the experts and sends the result back. What changes is the transport. The NPU has two connectors, both backed by Ascend CAM operators.

  • CAMP2pAFDConnector — synchronous, with a {{term control-plane | control plane}}. {{term hccl | HCCL}} carries the hidden states; a smaller Gloo group carries the DP metadata ({{cite afd_plugin/connectors/npu/camp2p.py:3-8}}).
  • CAMAsyncAFDConnector — asynchronous, with control_plane = None. The CAM dispatch/combine operators carry the routing metadata, so a separate control plane is not needed ({{cite afd_plugin/connectors/npu/async_cam.py:277-283}}).

This page explains how the Python code selects, loads and drives the NPU operators and runners. It does not cover the CAM kernel internals or the vendored binaries, which are out of scope ({{cite afd_plugin/connectors/npu/bin/}}).

In the code

Step 1: CAMP2p, the synchronous connector with a control plane

The synchronous connector builds its own HCCL groups for the hidden states ({{cite afd_plugin/connectors/npu/camp2p.py:418-431}}) and a smaller Gloo group for the DP metadata ({{cite afd_plugin/connectors/npu/camp2p.py:460-468}}). It sets a control plane, CAMP2pAFDControlPlane ({{cite afd_plugin/connectors/npu/camp2p.py:385}}), so the DP metadata travels once per step, the same timing as the GPU connector. See {{link concepts/control-plane}}.

Step 2: CAMAsync has no control plane; its receive loop drives the FFN side

The asynchronous connector sets control_plane = None ({{cite afd_plugin/connectors/npu/async_cam.py:283}}). The CAM dispatch/combine operators own both the data motion and its routing metadata, so there is no separate DP metadata path ({{cite afd_plugin/connectors/npu/async_cam.py:277-282}}).

So what drives the FFN side? The NPU async FFN runner loops over the layers and, for each one, calls recv_ffn_work_item ({{cite afd_plugin/v1/worker/npu/async_ffn_model_runner.py:442-446}}). Each work item carries its own layer index, read from the CAM metadata of the dispatch-receive, not from a control-plane payload ({{cite afd_plugin/connectors/npu/async_cam.py:497-541}}).

The forward context sets dp_metadata = None for each work item ({{cite afd_plugin/v1/worker/npu/async_ffn_model_runner.py:473}}). The connector receive is the clock: when a dispatch arrives, the runner computes that layer and sends the result back. This is the mechanism the {{link concepts/control-plane}} page names in one line.

Step 3: The operator loader

Both connectors need the plugin's Ascend operators. The loader ensure_cam_p2p_ops_available sets the custom op-API environment, imports afd_plugin._C_ascend, and asserts the torch.ops.afd_ascend namespace ({{cite afd_plugin/compat/npu/ops.py:73-91}}). ensure_afd_ascend_ops_loaded is a backward-compatible alias for it ({{cite afd_plugin/compat/npu/ops.py:94-97}}).

The async connector needs four more operators, so it calls ensure_cam_async_ops_available, which checks the four afd_async_* ops ({{cite afd_plugin/compat/npu/ops.py:107-119}}). The extension afd_plugin._C_ascend is built from csrc/npu/pybind ({{cite setup.py:116-120}}), gated on AFD_BUILD_ASCEND_OPS or an Ascend platform ({{cite setup.py:43-54}}) and the SOC_VERSION ({{cite setup.py:67}}, {{cite setup.py:88}}). See {{link reference/env-vars}}.

The folder connectors/npu/bin/ holds a prebuilt CAM installer (.run) and a wheel (.whl), stored with Git LFS ({{cite afd_plugin/connectors/npu/bin/}}). The plugin's Python loads the CMake-built afd_plugin._C_ascend; it does not import the bin/ artifacts directly. The async docs note that the source build needs no external CAM wheel ({{cite docs/npu/CAM_ASYNC_CONNECTOR_USER_GUIDE.md:277}}).

Step 4: Async data-parallel patches, gated to NPU

The async path needs two extra patches. They install only when the role is attention and async_dp is on ({{cite afd_plugin/compat/npu/runtime.py:44-53}}), and the whole NPU patch set installs only when the device is npu ({{cite afd_plugin/__init__.py:199-209}}). On GPU, async_dp must be false. See {{link concepts/compat-patches}}.

  • async_dp_engine — swaps the attention engine entry point to a plain EngineCoreProc for async DP ({{cite afd_plugin/compat/patches/async_dp_engine.py:117-120}}; installed and gated at {{cite afd_plugin/compat/patches/async_dp_engine.py:414-432}}).
  • async_dp_forward_context — skips the DP metadata only for the async path, and rebinds the symbol in the importing modules ({{cite afd_plugin/compat/patches/async_dp_forward_context.py:88-127}}, {{cite afd_plugin/compat/patches/async_dp_forward_context.py:207-212}}).

What can go wrong

  • Operators not built. The loader raises when afd_plugin._C_ascend is missing; build with Ascend ops enabled ({{cite afd_plugin/compat/npu/ops.py:86-90}}).
  • Async ops missing. The async connector raises when any of the four afd_async_* operators is absent ({{cite afd_plugin/compat/npu/ops.py:115-119}}).
  • async_dp on GPU. The async-DP patches are NPU-only and gated at run time; on GPU async_dp must be false ({{cite afd_plugin/compat/npu/runtime.py:44-53}}).
  • Expecting a control plane with the async connector. The async connector has none; the receive loop drives the FFN side ({{cite afd_plugin/connectors/npu/async_cam.py:283}}).

Why it matters. The NPU keeps the AFD contract but changes the transport and the driving mechanism. The async connector folds the control plane into the data operators, so the FFN side follows the receive loop, not a metadata step.

Which NPU connector has a control plane, and which does not?

CAMP2pAFDConnector has one, CAMP2pAFDControlPlane ({{cite afd_plugin/connectors/npu/camp2p.py:385}}). CAMAsyncAFDConnector sets control_plane = None ({{cite afd_plugin/connectors/npu/async_cam.py:283}}).

 What two collective libraries does CAMP2p use, and for what?

HCCL for the hidden states, and a smaller Gloo group for the DP metadata ({{cite afd_plugin/connectors/npu/camp2p.py:418-431}}, {{cite afd_plugin/connectors/npu/camp2p.py:460-468}}).

 How does the async FFN side know which layer to compute without a control plane?

The runner calls recv_ffn_work_item in a loop; each item carries its layer index, read from the CAM dispatch metadata ({{cite afd_plugin/v1/worker/npu/async_ffn_model_runner.py:442-446}}, {{cite afd_plugin/connectors/npu/async_cam.py:497-541}}).

 How does the plugin load the Ascend operators, and what does it not load?

It imports the CMake-built afd_plugin._C_ascend and asserts the torch.ops.afd_ascend namespace ({{cite afd_plugin/compat/npu/ops.py:73-91}}). It does not import the vendored bin/ artifacts, and the kernel internals are out of scope.

 When do the async-DP patches install, and why can they not run on GPU?

Only when the role is attention and async_dp is on ({{cite afd_plugin/compat/npu/runtime.py:44-53}}), and only when the device is npu ({{cite afd_plugin/__init__.py:199-209}}). On GPU async_dp must be false, so the gate never opens.

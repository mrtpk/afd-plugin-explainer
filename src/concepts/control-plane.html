This page shows what the control plane carries, both publish paths, the wire format and the receive side. --- The {{term control-plane | control plane}} sends {{term dp-metadata | DP metadata}} from the attention side to the FFN side. It runs once per step, before the layer loop.

The idea

The FFN side must know the token count of each {{term stage}} before it receives any hidden states. The sizes set the shapes of the wire tensors and the receive buffers. The attention side sends these counts once per step, before the layer loop, over the control plane. This is separate from the {{term data-plane | data plane}}, which moves the hidden states once per layer and stage.

The payload is small: the per-DP-rank token counts, plus a few flags for graph capture and warm-up. It travels as JSON over a dedicated process group.

An everyday comparison. Think of a manifest sent ahead of a convoy of trucks. The manifest lists how many boxes each truck carries, so the warehouse can set up the right number of bays before the trucks arrive. The comparison stops here: one connector, the async NPU one, carries no manifest at all; its receive loop sizes each transfer as it comes.

In the code

Step 1: Once per step, before the layers

The control plane runs once per step, before the layer loop. On the attention side the publish happens during input preparation, before the model forward ({{cite afd_plugin/v1/worker/attention_metadata.py:115-116}}). On the FFN side the loop receives one payload per step, before it runs any layer ({{cite afd_plugin/v1/worker/ffn_worker.py:176}}). The data plane then runs once per layer and stage inside the forward.

Step 2: What the payload carries

The payload is an AFDControlPayload: a map from stage index to DP metadata, plus the graph and warm-up flags ({{cite afd_plugin/connectors/metadata.py:107-150}}).

Each stage's DP metadata is an AFDDPMetadata. Its one required field is the per-DP-rank token count, stored as an int32 CPU tensor ({{cite afd_plugin/connectors/metadata.py:23-44}}). This plugin-owned type keeps the wire format decoupled from vLLM's own DP metadata object ({{cite afd_plugin/connectors/metadata.py:320-328}}).

Step 3: The two attention publish paths

The attention runner publishes the DP metadata on one of two paths, both once per step before the layer loop. For a {{term dbo | DBO}} step, a prepare seam publishes one complete payload before the microbatch threads start ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:153-157}}).

For a non-DBO step, the metadata is attached to the forward context and sent there ({{cite afd_plugin/v1/worker/attention_metadata.py:252-257}}). Both paths end in the same call, which updates the local state and then sends ({{cite afd_plugin/v1/worker/attention_metadata.py:115-116}}).

Step 4: The wire format and the separate group

The payload is encoded as compact JSON: only the per-stage token counts and the flags ({{cite afd_plugin/connectors/metadata.py:320-346}}). The send is two messages: a long size tensor, then a uint8 byte tensor ({{cite afd_plugin/connectors/metadata.py:376-401}}).

The GPU connector carries this over a dedicated NCCL process group, the "p2p" group, not the per-subgroup data communicators. The connector owns the group; the control plane uses it ({{cite afd_plugin/connectors/gpu/p2p.py:724-733}}, {{cite afd_plugin/connectors/gpu/p2p.py:853-883}}). Only the designated sender ranks transmit; the rest no-op ({{cite afd_plugin/connectors/gpu/p2p.py:870-875}}).

Step 5: The FFN side receives and derives the shapes

The FFN loop blocks on recv_dp_metadata_list until its mapped attention sender transmits ({{cite afd_plugin/connectors/gpu/p2p.py:885-908}}). The FFN runner then calls update_state_from_dp_metadata once per step, before the layer loop ({{cite afd_plugin/v1/worker/ffn_model_runner.py:194-203}}).

update_state_from_dp_metadata derives the expected wire-tensor shape for each stage and, in graph mode, preallocates the receive buffers so capture and replay reuse stable addresses ({{cite afd_plugin/connectors/gpu/p2p.py:744-851}}).

Step 6: The async NPU connector has no control plane

One connector sets control_plane = None: the async NPU connector ({{cite afd_plugin/connectors/npu/async_cam.py:283}}). It has no control plane; its receive loop drives the FFN side instead. See {{link concepts/npu-overview}}.

Deep dive

encode_control_payload writes compact JSON with sorted keys ({{cite afd_plugin/connectors/metadata.py:320-346}}). For one stage the fields are:

FieldType on the wireMeaning
num_tokens_across_dp_cpulist of inttokens per DP rank for this stage
max_tokens_across_dp_cpuintthe max over the list
is_graph_capturingboolthe attention side is capturing a graph
is_warmupboola warm-up step, not a real serving step
is_graph_replayingboolthe attention side is replaying a captured graph
is_profileboolan initial memory-profile forward

The transfer is two torch.distributed sends: a one-element long size tensor, then the uint8 object tensor, both staged on the device the caller chooses ({{cite afd_plugin/connectors/metadata.py:389-401}}). The receive reads the size first, then the bytes, and raises when the two messages come from different ranks ({{cite afd_plugin/connectors/metadata.py:403-420}}).

On the FFN side, update_state_from_dp_metadata stores the payload, then builds one _TensorMetadata per stage ({{cite afd_plugin/connectors/gpu/p2p.py:766-818}}). It reads each attention peer's token count from the DP metadata, then multiplies by the hidden size:

  • For an FFN rank, one entry per attention peer in the subgroup, plus the concatenated total ({{cite afd_plugin/connectors/gpu/p2p.py:776-807}}).
  • When CUDA graphs are on and the model is not eager, it preallocates the receive buffers, but only while capturing ({{cite afd_plugin/connectors/gpu/p2p.py:820-840}}).

A per-DP count is expanded across its TP peers when the DP metadata covers fewer ranks than the role size ({{cite afd_plugin/connectors/gpu/p2p.py:939-962}}). The {{link concepts/wire-data}} page reads the shapes in full.

The control-plane group is the FFN ranks plus the first min_size attention ranks ({{cite afd_plugin/distributed/topology.py:42-43}}). Each FFN rank f receives from the attention rank at p2p_rank % min_size + ffn_size, which resolves to attention role rank f ({{cite afd_plugin/connectors/gpu/p2p.py:902}}). The DP metadata is the same per-DP-rank token list for every rank, so one sender per FFN rank carries all the FFN rank needs. The {{link concepts/topology}} page shows which ranks are senders.

What can go wrong

This page shows the GPU control plane. The sync NPU connector has a control plane too; the async NPU connector has none ({{cite afd_plugin/connectors/npu/async_cam.py:283}}). See {{link concepts/npu-overview}}. The page leaves out the graph lifecycle details, which the {{link concepts/cuda-graphs}} page covers.
  • A GPU connector with no control plane. The GPU FFN loop needs a control-plane-driven connector and raises for one that sets control_plane = None ({{cite afd_plugin/v1/worker/ffn_worker.py:169-174}}).
  • Fragments from different ranks. The receive raises if the size message and the byte message come from different ranks ({{cite afd_plugin/connectors/metadata.py:418-419}}).
  • A stall before the first transfer. The FFN loop blocks on the control plane each step ({{cite afd_plugin/connectors/gpu/p2p.py:885-908}}). If the attention side never publishes, the FFN loop waits.

Why it matters. The DP metadata sets the wire shapes. Without it, the FFN side cannot size its receive buffers, and the per-layer transfers cannot start.

How often does the control plane run, compared with the data plane?

The control plane runs once per step, before the layer loop ({{cite afd_plugin/v1/worker/attention_metadata.py:115-116}}, {{cite afd_plugin/v1/worker/ffn_worker.py:176}}). The data plane runs once per layer and stage.

 What is the main content of the payload?

The per-DP-rank token counts for each stage, as an int32 tensor, plus graph and warm-up flags ({{cite afd_plugin/connectors/metadata.py:23-44}}, {{cite afd_plugin/connectors/metadata.py:135-139}}).

 The attention side has two publish paths. What are they?

The DBO prepare seam, which publishes before the microbatch threads start ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:153-157}}), and the non-DBO forward-context path ({{cite afd_plugin/v1/worker/attention_metadata.py:252-257}}). Both end in the same apply-then-send call ({{cite afd_plugin/v1/worker/attention_metadata.py:115-116}}).

 Which connector has no control plane, and what drives its FFN side then?

The async NPU connector, CAMAsyncAFDConnector ({{cite afd_plugin/connectors/npu/async_cam.py:283}}). With no control plane, its receive loop drives the FFN side ({{cite afd_plugin/connectors/base.py:56-60}}).

 On the FFN side, what does update_state_from_dp_metadata do with the payload?

It derives the expected wire-tensor shape for each stage from the token counts and the hidden size, and, in graph mode, preallocates the receive buffers while capturing ({{cite afd_plugin/connectors/gpu/p2p.py:744-851}}). It runs once per step before the layer loop ({{cite afd_plugin/v1/worker/ffn_model_runner.py:194-203}}).

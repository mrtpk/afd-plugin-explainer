This page shows the lifecycle, the four data-path calls, the optional control plane, the config hook and the factory. --- A {{term connector}} moves hidden states between the {{term attention-role | attention role}} and the {{term ffn-role | FFN role}}. One abstract base class sets its contract.

The idea

{{term afd}} splits a model into two server processes. The attention side computes attention and must hand its hidden states to the FFN side. The FFN side runs the feed-forward and MoE experts, then hands the result back. A connector owns this exchange.

Every connector subclasses one abstract base class, AFDConnectorBase ({{cite afd_plugin/connectors/base.py:37}}). The base class fixes three jobs: set up and release the transport, move hidden states each way, and apply the optional {{term control-plane | control plane}}. Each connector picks its own transport, but the call names and the order stay the same.

An everyday comparison. Think of a courier contract. The sender hands over a parcel; the courier delivers it and brings back a reply. The comparison stops here: a connector also sets up and tears down its own transport, and it runs this exchange once per model layer.

In the code

Step 1: One base class, three jobs

The base class docstring names the three jobs of every connector ({{cite afd_plugin/connectors/base.py:37-54}}).

Step 2: The lifecycle

The owning worker creates the connector, calls init_afd_connector once, uses the data path many times, then calls close. is_initialized is true between the two. init_afd_connector is a collective call: every attention and FFN rank must run it ({{cite afd_plugin/connectors/base.py:124}}).

Step 3: The attention-side calls

Before you read the send call: the leading dimension of the hidden-state tensor must equal context.metadata.total_tokens. If it does not, the call raises ValueError ({{cite afd_plugin/connectors/base.py:167-170}}).

The attention side calls send_attn_output to send its hidden states, then recv_ffn_output to get the FFN result back. recv_ffn_output takes a preallocated ref_tensor, because the backends cannot always allocate their own output ({{cite afd_plugin/connectors/base.py:185-192}}).

The GPU connector, P2pNcclAFDConnector, implements these calls with vLLM's PyNcclCommunicator ({{cite vllm:vllm/distributed/device_communicators/pynccl.py:91}}), wrapped in custom ops so the transfers stay usable under CUDA graph capture ({{cite afd_plugin/connectors/gpu/p2p.py:36-39}}). See {{link code/p2p-py}}.

Step 4: The FFN-side calls

The FFN side calls recv_attn_output to get the hidden states, runs the FFN compute, then calls send_ffn_output to send the result back. recv_attn_output returns both the tensor and the transfer context that the matching send needs ({{cite afd_plugin/connectors/base.py:216-227}}).

Step 5: The optional control plane

The base class holds an optional control_plane attribute. When it is set, the per-stage token counts travel over the control plane, and the arrival of a payload drives each FFN step. When it is None, the connector has no control plane and the receive loop drives the FFN side ({{cite afd_plugin/connectors/base.py:56-60}}).

A control plane is itself an abstract class, AFDControlPlane, with three calls: apply a payload locally, send a payload, and receive one ({{cite afd_plugin/connectors/base.py:258}}). The {{link concepts/control-plane}} page covers it.

Step 6: The config hook

Each connector parses its own options through parse_extra_config, a class method on the base class ({{cite afd_plugin/connectors/base.py:64-72}}). The base __init__ calls it and stores the result on extra_info ({{cite afd_plugin/connectors/base.py:105-107}}). The raw values come from connector_extra_config inside the AFD config ({{cite afd_plugin/config.py:282-286 | connector_extra_config_from_source}}).

Step 7: The factory

The factory maps a connector name to a class and builds the instance. create_connector reads the name from the AFD config, resolves the {{term role-rank | role rank}}, and constructs the connector ({{cite afd_plugin/connectors/factory.py:49-68}}). An unknown name raises ValueError ({{cite afd_plugin/connectors/factory.py:58-59}}).

Three connectors are registered at import time ({{cite afd_plugin/connectors/factory.py:88-102}}). The default name is "P2pNcclAFDConnector" ({{cite afd_plugin/config.py:52}}).

Deep dive

The blocks below give the full call order, a worked example with real shapes, and the differences between the three connectors.

One layer and one {{term stage}} run like this. The data-plane calls are in bold.

  1. Attention side: the model produces hidden states for the layer.
  2. The control plane sends the per-stage token counts, when the connector has one ({{cite afd_plugin/connectors/base.py:279-283}}).
  3. Attention side: send_attn_output(hidden_states, context) ({{cite afd_plugin/connectors/base.py:145}}).
  4. The FFN side applies the control-plane payload, when present, to size its buffers ({{cite afd_plugin/connectors/base.py:261-266}}).
  5. FFN side: recv_attn_output(ubatch_idx) returns the hidden states and the context ({{cite afd_plugin/connectors/base.py:206}}).
  6. FFN side: runs the FFN and MoE compute (not in the connector).
  7. FFN side: send_ffn_output(ffn_output, context) ({{cite afd_plugin/connectors/base.py:229}}).
  8. Attention side: recv_ffn_output(ref_tensor, ubatch_idx) returns the result, which continues through the rest of the layer ({{cite afd_plugin/connectors/base.py:173}}).

The {{term stage}} is the {{term dbo | DBO}} ubatch index. With DBO the connector runs two stages per layer. See {{link concepts/dbo}}.

Take a 2A2F topology: two attention ranks (A0, A1) and two FFN ranks (F0, F1). Each FFN rank owns one attention peer, so A0 maps to F0 and A1 maps to F1 ({{cite afd_plugin/connectors/gpu/p2p.py:11-20}}).

The hidden size comes from the model config, hf_text_config.hidden_size ({{cite afd_plugin/connectors/gpu/p2p.py:195-197}}). For DeepSeek-V2-Lite this is 2048. This value is inferred from the DeepSeek-V2-Lite checkpoint config; it is not stored in either repository.

Take one decode step with 8 tokens on A0. The numbers:

  • Tensor: hidden_states of shape [8, 2048], in the model dtype (bf16, inferred from the recipe).
  • Metadata: seq_lens = [8], so total_tokens = 8 ({{cite afd_plugin/connectors/metadata.py:198-200}}). The send call checks shape[0] == 8 ({{cite afd_plugin/connectors/metadata.py:230-231}}).
  • On the wire (A0 to F0): one tensor of 8 × 2048 × 2 bytes = 32,768 bytes per layer, per direction.
  • FFN side: F0 receives [8, 2048], runs the FFN, and sends back [8, 2048]. A0 gets it through recv_ffn_output.

When one FFN rank owns more than one attention peer, it concatenates the inputs. For 2A1F with 8 tokens each, F0 would receive two tensors, concatenate them to [16, 2048], and split the output back by the recorded sequence lengths ({{cite afd_plugin/connectors/gpu/p2p.py:21-25}}).

The factory registers three connectors ({{cite afd_plugin/connectors/factory.py:88-102}}). They differ by device, by send/receive timing, and by whether they use a control plane.

The config hook also differs. The GPU connector accepts no options, so it rejects a non-empty connector_extra_config ({{cite afd_plugin/connectors/gpu/p2p.py:150-157}}). The async NPU connector parses typed fields and rejects unknown ones ({{cite afd_plugin/connectors/npu/async_cam.py:286-291}}). The NPU connectors are covered on the {{link concepts/npu-overview}} page.

What can go wrong

This page shows the contract, not a full transport. It leaves out the per-peer split and concatenation, the custom-op wrapping and the rank mapping. The {{link concepts/wire-data}} and {{link code/p2p-py}} pages give those.
  • Shape mismatch. A hidden-state tensor whose leading dimension is not total_tokens raises ValueError in the send call (skipped while torch.compile traces) ({{cite afd_plugin/connectors/gpu/p2p.py:347-353}}).
  • Unknown connector name. A name that is not registered raises ValueError in the factory ({{cite afd_plugin/connectors/factory.py:58-59}}).
  • Options for a connector that takes none. A non-empty connector_extra_config for the GPU connector raises ValueError ({{cite afd_plugin/connectors/gpu/p2p.py:154-157}}).
  • Wrong device. The GPU connector needs CUDA and NCCL. It has no automatic fallback to another transport on NPU ({{cite afd_plugin/connectors/gpu/p2p.py:46-48}}).

Why it matters. The two roles must agree on the contract, the shapes and the connector name, or the collective setup fails or the first transfer raises.

Which two calls does the attention side make, and in which order?

First send_attn_output, then recv_ffn_output ({{cite afd_plugin/connectors/base.py:145}}, {{cite afd_plugin/connectors/base.py:173}}).

 Which connector is the default?

P2pNcclAFDConnector, the GPU connector. The default is set in the AFD config ({{cite afd_plugin/config.py:52}}).

 One connector sets control_plane = None. Which one, and what drives its FFN steps then?

The async NPU connector, CAMAsyncAFDConnector ({{cite afd_plugin/connectors/npu/async_cam.py:283}}). With no control plane, the connector receive loop drives the FFN side ({{cite afd_plugin/connectors/base.py:56-60}}).

 Why does recv_ffn_output take a preallocated ref_tensor?

The backends cannot always allocate their own output tensor. The P2P connector also uses it as a stable buffer for CUDA graph capture ({{cite afd_plugin/connectors/base.py:185-192}}).

 On DeepSeek-V2-Lite with 8 decode tokens, what tensor shape does the attention side send, and which value checks it?

Shape [8, 2048]: 8 tokens by the hidden size 2048 (the 2048 is inferred from the checkpoint). The metadata total_tokens is 8, and the send checks shape[0] == total_tokens ({{cite afd_plugin/connectors/metadata.py:198-200}}, {{cite afd_plugin/connectors/metadata.py:230-231}}).

The idea

On the FFN role, {{term afd}} drops the vLLM serving loop. There is no real scheduler (only a no-op stand-in), no KV cache and no sampler. Instead, a daemon thread blocks on the {{term control-plane | control plane}}. When a payload arrives, it runs one {{term step}}: for each decoder layer and {{term stage}}, it receives hidden states, runs the FFN or experts, and sends the result back.

The runner is GPUFFNModelRunner, a stand-alone class, not a subclass of the vLLM runner ({{cite afd_plugin/v1/worker/ffn_model_runner.py:52}}). It keeps only what the FFN role needs: the model, the connector and an optional CUDA graph cache.

An everyday comparison. Think of a short-order kitchen with no front counter. Orders arrive on a ticket rail (the control plane). The cook reads one ticket, makes the dish, and sends it out. The comparison stops here: the "ticket" carries only token counts, and the dish is a tensor that goes back to the exact attention rank that asked.

In the code

Step 1: Construction keeps only the FFN parts

The runner parses the AFD config, validates the V2 contract, resolves the graph policy and builds the connector ({{cite afd_plugin/v1/worker/ffn_model_runner.py:63-99}}). Like the attention runner, it requires a control-plane-driven connector and asserts it at construction ({{cite afd_plugin/v1/worker/ffn_model_runner.py:87-89}}).

Step 2: load_model loads the FFN model (and only its weights)

load_model calls the native model loader ({{cite afd_plugin/v1/worker/ffn_model_runner.py:111-126}}). The model it loads is the AFD {{term model-wrapper | model wrapper}} for the FFN role, which builds only the FFN modules and keeps only the FFN weights. See {{link concepts/model-wrappers}} for the weight filter.

get_kv_cache_spec returns an empty dict and initialize_kv_cache is a no-op ({{cite afd_plugin/v1/worker/ffn_model_runner.py:147-151}}). The FFN role allocates no KV cache.

Step 3: The server loop runs one step per control payload

The worker starts the loop on a daemon thread ({{cite afd_plugin/v1/worker/ffn_worker.py:133-158}}). The thread reads one DP-metadata payload per step, then dispatches to graph capture or to execute ({{cite afd_plugin/v1/worker/ffn_worker.py:168-199}}).

  1. Lines 169-174. A connector with control_plane None raises; the GPU FFN needs a control plane.
  2. Line 176. One recv_dp_metadata_list per step.
  3. Lines 182-189. Graph warm-up or capture calls capture_model.
  4. Lines 190-196. Otherwise execute_model runs the step.

Step 4: _ffn_forward loops over layers and stages

execute_model makes the graph key, then either replays a captured graph or calls _ffn_forward for the eager path ({{cite afd_plugin/v1/worker/ffn_model_runner.py:153-184}}). _ffn_forward loops over the layer indices, and over the stages inside each layer ({{cite afd_plugin/v1/worker/ffn_model_runner.py:222-269}}).

  1. Line 236. recv_attn_output returns the hidden states and the transfer context.
  2. Lines 251-261. An expert layer with the gate on the attention side calls compute_experts_output with the router logits.
  3. Lines 262-267. Any other layer calls _execute_eager_mode, which calls compute_ffn_output.
  4. Line 268. send_ffn_output sends the result back to the attention rank.

Step 5: The FFN role never samples

sample_tokens raises; the FFN role produces no tokens ({{cite afd_plugin/v1/worker/ffn_model_runner.py:405-406}}). The scheduler-driven execute_model on the worker also raises, because FFN work is connector-driven, not scheduler-driven ({{cite afd_plugin/v1/worker/ffn_worker.py:122-131}}).

The graph cache is keyed by the per-stage token counts ({{cite afd_plugin/v1/worker/ffn_model_runner.py:166}}). AFD on GPU allows only {{term full-decode-only | FULL_DECODE_ONLY}} graphs. The {{link concepts/cuda-graphs}} page reads capture and replay.

Take a 2A2F topology: two attention ranks (A0, A1) and two FFN ranks (F0, F1). The mapping sends A0 to F0 and A1 to F1 ({{cite afd_plugin/distributed/topology.py:135-136}}). Run with {{term dbo | DBO}}, so there are two {{term stage | stages}} per layer.

Use DeepSeek-V2-Lite as the model. This model has 27 decoder layers (layer 0 dense, the rest MoE). The 27 and the dense/MoE split are inferred from the DeepSeek-V2-Lite checkpoint config; they are not stored in either repository. With compute_gate_on_attention=false, the FFN runs every layer.

  1. The control plane delivers one payload for the step, with one DP-metadata entry per stage ({{cite afd_plugin/v1/worker/ffn_worker.py:176}}).
  2. _ffn_forward sets layer_indices = range(27) because the gate is on the FFN side ({{cite afd_plugin/v1/worker/ffn_model_runner.py:211-215}}).
  3. For each of the 27 layers, the runner loops over the two stages ({{cite afd_plugin/v1/worker/ffn_model_runner.py:223-230}}).
  4. That is 27 x 2 = 54 receive/compute/send cycles on F0 (and 54 on F1) for the step. F0 serves only A0's tokens, because A0 maps to F0.

The data plane runs 54 times per FFN rank in this step; the control plane ran once. This is why AFD counts the control plane per step and the data plane per layer and stage.

The worker stops the loop, then shuts the runner down ({{cite afd_plugin/v1/worker/ffn_worker.py:207-219}}). The runner's shutdown releases the graph state and native-equivalent GPU state, then closes the connector in a finally ({{cite afd_plugin/v1/worker/ffn_model_runner.py:442-456}}).

What can go wrong

This page reads the GPU FFN runtime. The NPU async connector drives the FFN side without a control plane; that path is on {{link concepts/npu-overview}}. For the file layout, see {{link code/ffn-worker}}.
  • A connector with no control plane. The GPU FFN loop raises ({{cite afd_plugin/v1/worker/ffn_worker.py:169-174}}); the runner also asserts it at construction ({{cite afd_plugin/v1/worker/ffn_model_runner.py:87-89}}).
  • A scheduler-driven step. The worker's execute_model raises; requests go only to the attention API server ({{cite afd_plugin/v1/worker/ffn_worker.py:122-131}}).
  • A missing DP-metadata list. The runner's execute_model raises if the control payload has no metadata ({{cite afd_plugin/v1/worker/ffn_model_runner.py:164-165}}).
  • A loop error. The daemon stores the exception; the next call re-raises it ({{cite afd_plugin/v1/worker/ffn_worker.py:201-205}}).

Why it matters. The FFN side is passive: it does nothing until a control payload arrives. If the attention side does not publish, the loop blocks; if a connector has no control plane, the loop cannot start.

Does the FFN role have a KV cache?

No. get_kv_cache_spec returns an empty dict and initialize_kv_cache is a no-op ({{cite afd_plugin/v1/worker/ffn_model_runner.py:147-151}}).

 What drives one FFN step?

One recv_dp_metadata_list from the control plane, read by the daemon loop ({{cite afd_plugin/v1/worker/ffn_worker.py:176}}).

 Inside _ffn_forward, what is the order of the three connector and compute calls per layer and stage?

recv_attn_output, then the compute (compute_experts_output or compute_ffn_output), then send_ffn_output ({{cite afd_plugin/v1/worker/ffn_model_runner.py:236-268}}).

 What happens when a captured graph exists for the step's token counts?

The run mode is REPLAY: the captured CUDA graph replays and the runner returns without recompute ({{cite afd_plugin/v1/worker/ffn_model_runner.py:175-177}}).

 On 2A2F with DBO and a 27-layer model, how many data-plane cycles does one FFN rank run per step, and how many control-plane reads?

27 layers x 2 stages = 54 receive/compute/send cycles on the data plane, and one control-plane read ({{cite afd_plugin/v1/worker/ffn_model_runner.py:223-230}}, {{cite afd_plugin/v1/worker/ffn_worker.py:176}}). The 27 is inferred from the DeepSeek-V2-Lite checkpoint.

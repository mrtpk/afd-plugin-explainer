This page covers the discipline, the gates, and what each GPU patch changes. --- AFD changes no vLLM source. {{term register-afd}} imports {{term patch | patch}} modules that replace vLLM functions in place, each behind a {{term version-gate | version gate}}.

The idea

AFD is an external {{term plugin}}. It must not edit the vLLM source. Instead, it replaces a few vLLM functions at run time with its own versions. Each replacement is a {{term patch}}, in afd_plugin/compat/patches/. {{term register-afd}} imports the patch modules once at start-up ({{cite afd_plugin/__init__.py:172-181}}).

Every patch copies the matching vLLM function from the pinned release and marks only the AFD difference between PATCH START and PATCH END comments. The patched signature must match the original ({{cite AGENTS.md:161-168}}). A {{term version-gate | version gate}} decides whether a patch installs, so AFD does not break a vLLM it was not built for.

An everyday comparison. Think of a train that swaps one carriage for a custom one before it leaves, and swaps the original back when it returns. The comparison stops here: a patch checks the train model first, and some patches swap the carriage only for the length of one trip.

In the code

Step 1: Patch discipline

The patches package is a closed namespace: it raises on any unexpected attribute, so nothing leaks ({{cite afd_plugin/compat/patches/__init__.py:12-13}}). Each patch function carries comments that give the reason, the change, and the upstream target ({{cite AGENTS.md:165-170}}), and marks the AFD lines with PATCH START and PATCH END.

Step 2: Two version checks

The first check runs in register_afd. It is not strict, so a vLLM that is not exactly the target release only warns ({{cite afd_plugin/compat/vllm.py:38-50}}, {{cite afd_plugin/__init__.py:162-170}}).

The second check is the install gate, is_target_vllm_compatible. It allows the target release and any dev build, and returns true when vLLM is absent so CPU imports still work ({{cite afd_plugin/compat/vllm.py:53-68}}).

Step 3: config_validation

This patch replaces two vLLM functions: EngineArgs.create_engine_config ({{cite vllm:vllm/engine/arg_utils.py:2040 | create_engine_config}}) and VllmConfig.__post_init__ ({{cite vllm:vllm/config/vllm.py:1254 | VllmConfig.__post_init__}}). It installs at import time, behind the gate ({{cite afd_plugin/compat/patches/config_validation.py:235-261}}).

What it changes: it rewrites worker_cls to the AFD role worker, but only when the value was "auto" ({{cite afd_plugin/compat/patches/config_validation.py:92-93}}, {{cite afd_plugin/compat/patches/config_validation.py:179-197}}). It also relaxes one vLLM ubatching backend check for AFD configs ({{cite afd_plugin/compat/patches/config_validation.py:200-214}}). See {{link concepts/worker-selection}}.

Step 4: engine_core

This patch replaces EngineCore.__init__, _initialize_kv_caches and shutdown, plus the busy loops of EngineCoreProc and DPEngineCoreProc ({{cite afd_plugin/compat/patches/engine_core.py:722-727}}). The vLLM targets are in vllm/v1/engine/core.py ({{cite vllm:vllm/v1/engine/core.py:108 | EngineCore.__init__}}, {{cite vllm:vllm/v1/engine/core.py:1403 | EngineCoreProc.run_busy_loop}}).

What it changes: for an {{term ffn-role | FFN}} config, __init__ returns right after the executor is built, so the FFN EngineCore has no scheduler and no KV cache ({{cite afd_plugin/compat/patches/engine_core.py:56-68}}). The busy loop instead runs the connector loop ({{cite afd_plugin/compat/patches/engine_core.py:411-419}}). See {{link concepts/roles}}.

Step 5: gpu_mrv2_ubatching

This patch is different: it installs through {{term scoped-patch | scoped}} context managers, not at import time ({{cite afd_plugin/compat/patches/gpu_mrv2_ubatching.py:263-282}}). It replaces maybe_build_ubatch_runner ({{cite vllm:vllm/v1/worker/gpu/ubatch_utils.py:538 | maybe_build_ubatch_runner}}) and dispatch_cg_and_sync_dp ({{cite vllm:vllm/v1/worker/gpu/dp_utils.py:214 | dispatch_cg_and_sync_dp}}) only inside AFD's own initialize_kv_cache and execute_model calls. It re-enables DBO at one data-parallel rank. See {{link concepts/dbo}}.

Step 6: async_dp patches

Two patches support async-DP, which is {{term async-dp | NPU-only}}. They install at import time but only change behavior for async configs, gated at run time ({{cite afd_plugin/config.py:303-308}}). On GPU, async_dp must be false, so these patches run as transparent re-implementations.

  • async_dp_engine replaces EngineCoreProc.run_engine_core ({{cite vllm:vllm/v1/engine/core.py:1283 | run_engine_core}}), launch_core_engines ({{cite vllm:vllm/v1/engine/utils.py:1104 | launch_core_engines}}) and DPAsyncMPClient.add_request_async ({{cite vllm:vllm/v1/engine/core_client.py:1486 | add_request_async}}), selecting a non-DP engine for async attention ({{cite afd_plugin/compat/patches/async_dp_engine.py:117-120}}).
  • async_dp_forward_context replaces set_forward_context ({{cite vllm:vllm/forward_context.py:269 | set_forward_context}}) and skips DP metadata only for async configs ({{cite afd_plugin/compat/patches/async_dp_forward_context.py:88-127}}).

Step 7: NPU patches

The patches under afd_plugin/compat/patches/npu/ install only when the device is NPU ({{cite afd_plugin/__init__.py:204-209}}). They are covered on {{link concepts/npu-overview}}. In one line each:

  • npu/ascend_config: keep AFD settings out of the strict Ascend config namespace ({{cite afd_plugin/compat/patches/npu/ascend_config.py:3}}).
  • npu/ascend_platform: patch the Ascend platform config normalization for AFD DBO ({{cite afd_plugin/compat/patches/npu/ascend_platform.py:3-5}}).
  • npu/mla_graph: route Ascend MLA {{term acl-graph | ACL graph}} parameters through AFD forward contexts ({{cite afd_plugin/compat/patches/npu/mla_graph.py:3-5}}).
  • npu/mrv2_ubatching: scope Ascend seams for the native ubatch runner ({{cite afd_plugin/compat/patches/npu/mrv2_ubatching.py:3-8}}).

Deep dive

The blocks below give the install gate and its guards, the monkey-patch rule, and a pointer to the full table.

The config patch installs at the bottom of its module, inside an if on the gate ({{cite afd_plugin/compat/patches/config_validation.py:235-261}}). It saves each original function once, using a hasattr guard, then stores it and assigns the patched function.

  1. Save once. The hasattr guard writes the original only if it is not already saved, so a reload does not overwrite it ({{cite afd_plugin/compat/patches/config_validation.py:236}}, {{cite afd_plugin/compat/patches/config_validation.py:243}}).
  2. Read the saved original. The module keeps a reference to the saved original ({{cite afd_plugin/compat/patches/config_validation.py:250-257}}).
  3. Assign the patch. The assignment runs once per process, because Python caches the module import ({{cite afd_plugin/compat/patches/config_validation.py:259-260}}).

On a non-matching, non-dev vLLM the gate is false, so no patch installs. Then worker_cls is never rewritten and AFD does not take effect; register_afd still registers models, the routing strategy and the DBO op.

Python binds names in two ways. A from module import name binds the name to the original object. A later change to module.name changes only new attribute lookups, not names already bound by a from-import.

So a patch must run before the code that reads the attribute. The config patch installs at register_afd time, before any engine or worker builds a config ({{cite afd_plugin/__init__.py:172-181}}). The set_forward_context patch also rebinds the symbol in modules that already imported it, so those modules see the patched version ({{cite afd_plugin/compat/patches/async_dp_forward_context.py:208-212}}).

The reference page lists every patch with its vLLM target line at the pinned commit, its install mechanism and gate, when it is active, and what it changes. See {{link reference/compat-patches}}.

What can go wrong

This page shows the GPU patches in full and names the NPU patches. It does not describe the vLLM functions' insides, only what AFD replaces and why.
  • A vLLM that is not the target release. The start-up check only warns ({{cite afd_plugin/compat/vllm.py:48-50}}), but every install gate is false, so no patch installs ({{cite afd_plugin/compat/patches/config_validation.py:235}}).
  • A patch that imports but cannot apply. The patch imports are wrapped in a try that only logs on failure ({{cite afd_plugin/__init__.py:172-181}}).
  • A worker set to a non-AFD class. The patch rewrites worker_cls only when it was "auto"; an explicit non-AFD worker is rejected later ({{cite afd_plugin/validation.py:357-367}}). See {{link concepts/worker-selection}}.
  • A signature drift after a vLLM upgrade. A patched function must match the vLLM signature, or the call fails. The patch comments record the exact upstream target ({{cite AGENTS.md:165-170}}).

Why it matters. The patches are how AFD runs inside unmodified vLLM. The version gate keeps AFD from breaking a vLLM it was not built for, and the scoped patches keep AFD changes out of native requests.

How does AFD change vLLM behavior without editing vLLM?

It imports patch modules that replace vLLM functions in place at run time ({{cite afd_plugin/__init__.py:172-181}}).

 What does the config_validation patch rewrite, and only when?

It rewrites worker_cls to the AFD role worker, only when it was "auto" ({{cite afd_plugin/compat/patches/config_validation.py:92-93}}, {{cite afd_plugin/compat/patches/config_validation.py:175-176}}).

 What is the difference between the two version checks?

The start-up check (assert_vllm_version_supported, strict false) only warns ({{cite afd_plugin/compat/vllm.py:38-50}}). The install gate (is_target_vllm_compatible) decides whether each patch installs, and allows dev builds ({{cite afd_plugin/compat/vllm.py:53-68}}).

 Which GPU patch does not install at import time, and how does it install?

gpu_mrv2_ubatching. It installs through scoped context managers, only inside AFD's initialize_kv_cache and execute_model calls ({{cite afd_plugin/compat/patches/gpu_mrv2_ubatching.py:263-282}}).

 The async-DP patches install on GPU too. Why do they not change GPU behavior?

They change behavior only for async configs, gated at run time by is_afd_async_dp ({{cite afd_plugin/config.py:303-308}}). On GPU async_dp must be false, so the patches run as transparent re-implementations of the native functions ({{cite afd_plugin/compat/patches/async_dp_forward_context.py:88-127}}).

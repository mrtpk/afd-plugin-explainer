It overrides a few seams for the connector and the control plane, and delegates the model forward, sampling and output to the native class. --- The attention runner, AFDAttentionModelRunnerV2, wraps the native vLLM {{term model-runner-v2 | Model Runner V2}}. It adds the {{term connector}} and {{term control-plane | control plane}}, and reuses the rest.

The idea

On the {{term attention-role | attention role}}, {{term afd}} does not rewrite the vLLM model runner. It subclasses it. AFDAttentionModelRunnerV2 inherits the native GPU {{term model-runner-v2 | Model Runner V2}} and an AFD metadata mixin ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:358}}). The native class keeps request state, input preparation, attention, the KV cache, sampling and the output. The AFD subclass adds only the connector lifecycle and the control-plane publish.

The runner's own docstring states this split: native V2 keeps execution, dummy runs and the graph lifecycle; the AFD methods are connector and context plumbing ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:358-365}}).

An everyday comparison. Think of a seat cover on a car seat. It adds a pocket and a strap, but the seat, the frame and the belt stay the same. The comparison stops here: the runner's "pocket" must open and close at the exact moment vLLM builds each forward context.

In the code

Step 1: Construction makes the connector and checks for a control plane

The constructor validates the V2 contract, calls super().__init__, then builds the connector through the factory ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:369-411}}). It requires a control-plane-driven connector and raises otherwise ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:394-397}}).

Step 2: load_model defers the connector rendezvous to the end

load_model calls native loading first, then initializes the connector. The comment explains the order: the rendezvous waits until weights are loaded, so attention and FFN weight loading overlap ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:454-462}}).

Step 3: execute_model wraps native V2 in the AFD context

execute_model steps the profiler, opens _use_afd_execution_context, then delegates the whole forward to super().execute_model ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:569-595}}).

Because the forward is native, logits and sampling are native too. They run once per {{term step}}, after the last layer, on the attention side ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:586}}).

Step 4: The AFD metadata provider installs the sidecar

Model wrappers read AFD metadata from the vLLM forward context. The provider installs it as vLLM makes each context. The plugin cannot extend set_forward_context, so it wraps create_forward_context for the scope and mutates additional_kwargs ({{cite afd_plugin/model_executor/models/forward_context.py:37-67}}).

The installer and the publish logic live in the shared mixin, AFDMetadataProviderMixin ({{cite afd_plugin/v1/worker/attention_metadata.py:21}}). Both the V2 runner and the NPU runners reuse it.

Step 5: The control plane publishes once per step

The {{term dp-metadata | DP metadata}} crosses once per step, before the layer loop. One of two seams sends it. With {{term dbo | DBO}}, the ubatch prepare seam sends it after it stages the microbatches ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:153-158}}).

Without DBO, the forward-context provider sends it once, unless a graph lifecycle already pre-sent it ({{cite afd_plugin/v1/worker/attention_metadata.py:248-257}}). Both paths end in send_dp_metadata, which updates the connector state and sends the payload ({{cite afd_plugin/v1/worker/attention_metadata.py:115-116}}).

Deep dive

The context manager opens several scopes together, then restores the runner's sidecar state when it exits ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:316-355}}).

  1. use_gpu_mrv2_dbo_dispatch() lets native V2 run DBO on DP1 ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:342}}).
  2. _use_afd_fullgraph_replay_hook, but only in FULL_DECODE_ONLY graph mode ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:323-339}}).
  3. _use_afd_ubatch_preparation wraps the native ubatch prepare to attach the sidecar and publish control ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:344}}).
  4. use_afd_metadata_provider installs the sidecar on every new context ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:345-347}}).

The finally block restores the pending metadata, the suppress flag and the warm-up and graph flags ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:350-355}}).

DBO. {{term dbo | Dual-batch overlap}} runs two {{term stage | stages}} per layer. initialize_kv_cache scopes a factory so native V2 builds a DP1 ubatch runner ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:473-486}}). At run time the prepare seam stages the two microbatches and publishes one control payload for both ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:153-158}}). The {{link concepts/dbo}} page reads the yield op.

Graph replay. AFD supports {{term full-decode-only | FULL_DECODE_ONLY}} graphs. capture_model wraps the native capture so each descriptor publishes one warm-up and one capture payload ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:509-553}}). Native FULL replay builds no context, so a per-manager hook publishes one padded control payload before each replay ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:270-303}}). The {{link concepts/cuda-graphs}} page reads capture and replay in full.

The AFD subclass never copies these; it inherits them from native V2 and the vLLM stack.

What can go wrong

This page reads the GPU runner. The NPU runners reuse the same mixin but have their own context handling, covered on {{link concepts/npu-overview}}. For the file layout, see {{link code/attention-worker}}.
  • A connector with no control plane. The runner raises at construction; the GPU attention runner needs a control plane ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:394-397}}).
  • A KV-only context with no batch descriptor. The runner skips the AFD install for such a context, so it does not start a spurious transaction ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:434-443}}).
  • Construction failure. If any step after super().__init__ raises, the runner closes the connector and shuts down native state, then re-raises ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:405-411}}).
  • Missing graph manager in FULL_DECODE_ONLY. The replay hook raises if the graph manager is not initialized ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:244-248}}).

Why it matters. The runner must publish the DP metadata before the layers start, and attach the sidecar on every context. If a seam misses, the FFN side waits for a payload that never arrives, or a layer runs with no connector in scope.

Which native class does the attention runner subclass?

The GPU GPUModelRunner (Model Runner V2), imported as GPUModelRunnerV2 ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:358}}).

 Where does sampling run in AFD?

On the attention side, in native V2, once per step after the last layer. The AFD execute_model delegates to super ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:586}}).

 Why does load_model initialize the connector at the end?

So the collective rendezvous waits until weights are loaded, letting attention and FFN weight loading overlap ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:454-462}}).

 The plugin cannot extend set_forward_context. How does it attach AFD metadata to the forward context?

It wraps create_forward_context for the scope and mutates additional_kwargs right after vLLM makes the context ({{cite afd_plugin/model_executor/models/forward_context.py:37-67}}).

 There are two control-plane publish seams. When is each used, and how often do they send per step?

The DBO ubatch prepare seam sends when DBO stages microbatches ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:156-157}}); the forward-context provider sends on the non-DBO path, unless a graph lifecycle pre-sent it ({{cite afd_plugin/v1/worker/attention_metadata.py:248-257}}). Either way, the control plane sends once per step, before the layer loop.

This page explains why it is safe to call many times, how it stays importable without vLLM, its version gate, and the order and error behaviour of its registration steps. --- {{term register-afd}} is the one function vLLM calls to install {{term afd}}. It is safe to call many times, and safe to import without vLLM.

The idea

afd-plugin is one {{term general-plugin | general plugin}}. vLLM calls its entry function, register_afd, once in each process that loads plugins. The function installs the {{term patch | compat patches}}, the routing strategy, the {{term dbo | DBO}} custom op and the {{term model-wrapper | model wrappers}}. Then it stops; it runs no model.

Two facts shape the function. First, vLLM calls it in many processes, and the vLLM guard resets in each new process. So the function must be idempotent: safe to run again with no change. Second, the package must import on a machine with no vLLM, so local tests work. The function handles both with guards and early returns.

An everyday comparison. Think of a self-check at the start of a shift. You run it once; if someone runs it again, it sees the ticks and stops. The comparison stops here: each new process starts with an empty checklist, so the plugin runs the whole check again.

This page explains why and when register_afd does each thing. The line-by-line read of the module is on the {{link code/init-py}} page.

In the code

Step 1: Two guards make it idempotent

vLLM keeps a module flag, plugins_loaded, so {{term load-general-plugins}} runs the plugins at most once per process ({{cite vllm:vllm/plugins/__init__.py:82-85}}). The plugin adds its own flag, _registered. A second call to register_afd in the same process returns at once ({{cite afd_plugin/__init__.py:150-153}}).

Step 2: Import safety without vLLM

The function returns early when vLLM is not importable. It sets _registered first, so a later call does not retry ({{cite afd_plugin/__init__.py:157-160}}). So importing afd_plugin stays safe on a machine with no vLLM.

Step 3: The version gate warns, it does not stop

The function checks the vLLM version with strict=False. A mismatch gives a warning, not an error ({{cite afd_plugin/__init__.py:162-165}}). The helper raises only when strict is true; otherwise it calls warnings.warn ({{cite afd_plugin/compat/vllm.py:38-50}}).

Step 4: What it registers, and in which order

After the checks, the function runs these steps in order. Each is one or a few lines; the {{link code/init-py}} page reads them line by line.

  1. Import the four patch modules. Importing a patch module applies it ({{cite afd_plugin/__init__.py:172-176}}).
  2. Register the AFD routing strategy ({{cite afd_plugin/__init__.py:183-187}}).
  3. Register the DBO yield custom op ({{cite afd_plugin/__init__.py:189-192}}).
  4. NPU only: apply the Ascend config patch, when the device type is "npu" ({{cite afd_plugin/__init__.py:202-209}}).
  5. Register each model under its AFD<arch> name ({{cite afd_plugin/__init__.py:211-214}}).
  6. Set _registered = True ({{cite afd_plugin/__init__.py:216}}).

Step 5: Which steps are wrapped in try/except

Three steps swallow their own errors; three do not. A wrapped step logs at debug and lets the rest go on. An unwrapped step lets its error propagate and stop the process.

Deep dive

The two guards work at different levels, and the order matters.

  1. vLLM calls load_general_plugins from five call sites, in four kinds of process ({{cite vllm:vllm/plugins/__init__.py:87-90}}). The {{link learn/vllm-plugins}} page lists them.
  2. The vLLM guard plugins_loaded stops a second call in the same process ({{cite vllm:vllm/plugins/__init__.py:82-85}}). It is module state, so a new process starts it at False again.
  3. Inside one call, the plugin guard _registered stops repeated work if register_afd is reached twice in one process ({{cite afd_plugin/__init__.py:150-153}}).

Because the vLLM guard resets per process, the registration steps run again in each process. So each step must be safe to run more than once. ModelRegistry.register_model and the module-attribute patches both satisfy this: the patch modules guard against re-patching their own target ({{cite afd_plugin/compat/patches/config_validation.py:235-248}}).

There are two version checks, and they are not the same.

  • The explicit check in register_afd calls assert_vllm_version_supported(strict=False). It compares the installed vLLM version with 0.30.0 exactly, and only warns on a mismatch ({{cite afd_plugin/compat/vllm.py:29-50}}).
  • The patch-install gate is is_target_vllm_compatible(). Each patch module installs its replacement only when this returns true. It tolerates a dev build and matches the version by prefix ({{cite afd_plugin/compat/vllm.py:53-68}}, {{cite afd_plugin/compat/patches/config_validation.py:235-261}}).

So on a non-matching, non-dev vLLM, the explicit check warns, the function continues, but the patches do not install. AFD then does not take effect. The two checks let the import stay safe while the patches stay strict.

What can go wrong

  • Wrong vLLM version. The explicit check only warns ({{cite afd_plugin/compat/vllm.py:48-50}}). The patches then skip install, so AFD does not activate even though the process keeps running ({{cite afd_plugin/compat/patches/config_validation.py:235-261}}).
  • A failing patch import. The four patch imports are wrapped, so a failure is logged and the rest continue ({{cite afd_plugin/__init__.py:172-181}}). A missing patch can leave the stack half-installed.
  • A failing routing or model step. These are not wrapped, so their error stops the process ({{cite afd_plugin/__init__.py:183-187}}, {{cite afd_plugin/__init__.py:211-214}}).

Why it matters. AFD is installed only by this function. A warning that the version does not match is the one sign that the patches did not install and AFD is off.

What are the two guards that make register_afd idempotent?

vLLM's plugins_loaded ({{cite vllm:vllm/plugins/__init__.py:82-85}}) and the plugin's own _registered ({{cite afd_plugin/__init__.py:150-153}}).

 Which registration step runs only on NPU?

The Ascend config patch, applied only when the device type is "npu" ({{cite afd_plugin/__init__.py:202-209}}).

 The vLLM version does not match. Does the process stop?

No. The explicit check uses strict=False and only warns ({{cite afd_plugin/compat/vllm.py:48-50}}). But the patches skip install, so AFD does not activate ({{cite afd_plugin/compat/patches/config_validation.py:235-261}}).

 Why must each registration step be safe to run more than once?

vLLM calls the function in several processes, and the plugins_loaded guard resets in each new process ({{cite vllm:vllm/plugins/__init__.py:82-85}}).

 The routing strategy step is not wrapped in try/except, but the DBO op step is. What is the effect of that difference?

A failure in the routing strategy propagates and stops the process ({{cite afd_plugin/__init__.py:183-187}}). A failure in the DBO op is caught and logged at debug, so registration continues ({{cite afd_plugin/__init__.py:189-197}}).

Every number is cited. --- AFD exposes a small set of knobs. This page lists each one, where the code reads it, and the only numbers the repository states for it.

The idea

Tuning AFD means three things: shape the split and the overlap for throughput, set the timeouts and gate for reliable startup, and measure with the profiler and benchmark tools. The repository gives example values for some knobs and says to tune them for the workload. This page uses only numbers the code or the READMEs state.

An everyday comparison. Think of the knobs on an audio mixer. Each one changes one thing, and the factory marks are a starting point, not the final mix. The comparison stops at the meters: here the meters are the profiler and the benchmark, not your ear.

This page does not claim a speedup for any setting. The recipe values (DBO 2/12, capture size 64) are example values the READMEs say to tune ({{cite recipe/gpu/P2pNcclAFDConnector/deepseek_v2_lite/README.md:140-143}}, {{cite recipe/gpu/P2pNcclAFDConnector/deepseek_v2_lite/README.md:154-157}}).

In the code

Step 1: The A:F rank ratio

The attention ranks must be at least the FFN ranks. The P2P topology check raises when A < F ({{cite afd_plugin/distributed/topology.py:52-58}}). Within that rule you choose the counts and the DP/TP split per role ({{cite afd_plugin/validation.py:107-117}}). See {{link concepts/deployment-topologies}}.

Step 2: DBO thresholds

{{term dbo | DBO}} microbatches a step when the token count passes a threshold. The recipes set a low decode threshold 2 and prefill threshold 12 ({{cite recipe/gpu/P2pNcclAFDConnector/deepseek_v2_lite/prefill_decode_colocation/2a2f_graph_dbo_dp1tp2.sh:24-25}}). The vLLM defaults are higher: 32 for decode and 512 for prefill ({{cite vllm:vllm/config/parallel.py:227}}, {{cite vllm:vllm/config/parallel.py:232}}).

vLLM reads these thresholds per step to decide whether to microbatch ({{cite vllm:vllm/v1/worker/ubatch_utils.py:141-149}}). AFD requires exactly two microbatches when DBO is on ({{cite afd_plugin/validation.py:126-131}}). See {{link concepts/dbo}}.

Step 3: CUDA graph capture size

The graph variants set --max-cudagraph-capture-size and the cudagraph_capture_sizes list together, with cudagraph_mode: FULL_DECODE_ONLY ({{cite recipe/gpu/P2pNcclAFDConnector/deepseek_v2_lite/prefill_decode_colocation/2a2f_graph_dbo_dp1tp2.sh:26-29}}).

On GPU, AFD allows only FULL_DECODE_ONLY ({{cite afd_plugin/v1/worker/cuda_graph.py:20-21}}). The README says to set --max-cudagraph-capture-size and cudagraph_capture_sizes together, based on the batch sizes and GPU memory ({{cite recipe/gpu/P2pNcclAFDConnector/deepseek_v2_lite/README.md:154-157}}). See {{link concepts/cuda-graphs}}.

Step 4: The group timeout

afd_process_group_timeout_s sets how long the world process-group rendezvous waits; the default is 120 seconds ({{cite afd_plugin/config.py:70}}). The P2P connector reads it when it builds the world group ({{cite afd_plugin/connectors/gpu/p2p.py:275}}). The config comment says the right value depends on rank count, placement and model size, so it is left to the caller ({{cite afd_plugin/config.py:67-70}}).

Step 5: Gate placement

compute_gate_on_attention moves the MoE gate to the attention side. When it is on, the FFN side runs only the expert layers ({{cite afd_plugin/v1/worker/ffn_model_runner.py:211-215}}). It defaults to false ({{cite afd_plugin/config.py:66}}). Not every model allows it: the Qwen3-MoE wrapper requires it to be false ({{cite afd_plugin/model_executor/models/qwen3_moe.py:84-87}}). See {{link concepts/moe-handoff}}.

Deep dive

On an Ascend NPU, {{term batch-size-factor | BATCH_SIZE_FACTOR}} multiplies the CAM receive capacity. The base is 262144 tokens; the factor is applied with native float rounding, default 1 ({{cite afd_plugin/validation.py:45-54}}). The async FFN graph capacity check uses the same figure ({{cite afd_plugin/compat/npu/feature_validation.py:245-249}}). This knob matters only on NPU; see {{link concepts/npu-overview}}.

The plugin owns a torch profiler for each GPU runner role, enabled by environment variables with the prefix AFD_GPU_ATTENTION_PROFILER or AFD_GPU_FFN_PROFILER. The profiler is off until you set ..._ENABLE ({{cite afd_plugin/compat/profiler.py:46-61}}). Only then does the plugin build a torch profiler with the schedule from the other variables ({{cite afd_plugin/compat/profiler.py:64-96}}). The trace directory falls back to VLLM_TORCH_PROFILER_DIR, then to a per-role default ({{cite afd_plugin/compat/profiler.py:131-132}}). The NPU profiler is the same shape with one extra setting, ..._WITH_STACK ({{cite afd_plugin/compat/npu/profiler.py:52-70}}). The {{link reference/env-vars}} page lists every profiler variable.

For controlled MoE benchmarks, the plugin registers a deterministic routing strategy, afd_balanced ({{cite afd_plugin/model_executor/routing_simulator.py:166-171}}). Select it with vLLM's VLLM_MOE_ROUTING_SIMULATION_STRATEGY ({{cite afd_plugin/model_executor/routing_simulator.py:5-8}}). It returns uniform weights and deterministic expert ids from a fixed seed 1024 ({{cite afd_plugin/model_executor/routing_simulator.py:28}}). The optional AFD_BENCHMARK_FORCE_LB_TOPN_PER_RANK limits the local expert pool per EP rank; 0 selects all local experts ({{cite afd_plugin/model_executor/routing_simulator.py:125-127}}).

The strategy replaces real routing with a synthetic cycle, so it changes model outputs ({{cite afd_plugin/model_executor/routing_simulator.py:10-11}}). Use it only for benchmark and profiling runs, not for serving.

The repository ships a benchmark harness under tools/benchmarks/. The request_generator.sh script drives load against a running server; it wraps vllm bench serve and takes every knob as an environment variable ({{cite tools/benchmarks/request_generator.sh:44-57}}). The decode_bench_server.sh script starts a 2A2F decode-only stand that fakes out prefill ({{cite tools/benchmarks/decode_bench_server.sh:4-20}}). For a Kubernetes run, the repository ships a run-vllm-bench-k8s contributor skill ({{cite .agents/skills/run-vllm-bench-k8s/SKILL.md:1-6}}).

The NPU recipes include result images with their own captions. The CAMP2p recipe reports DeepSeek-V3.2 decode throughput per die at 16K and 32K ({{cite recipe/npu/CAMP2pAFDConnector/deepseek_v3_2/README.md:365}}, {{cite recipe/npu/CAMP2pAFDConnector/deepseek_v3_2/README.md:373}}); the async recipe reports a text-matched median TTFT comparison ({{cite recipe/npu/CAMAsyncAFDConnector/deepseek_v3_2/README.md:432}}). These numbers are from older runtimes, so this page does not restate them as current results. See {{link concepts/npu-overview}}.

What can go wrong

This page lists the knobs the repository exposes. It does not tune them for you; the right values depend on the model, the hardware and the workload, as the READMEs say.
  • DBO on without two microbatches. AFD requires exactly two microbatches when DBO is on, and raises otherwise ({{cite afd_plugin/validation.py:126-131}}).
  • A graph mode other than FULL_DECODE_ONLY on GPU. The GPU runner accepts only FULL_DECODE_ONLY ({{cite afd_plugin/v1/worker/cuda_graph.py:20-21}}).
  • A timeout too short for the placement. The rendezvous fails when the world group does not form in time ({{cite afd_plugin/connectors/gpu/p2p.py:275}}).
  • The routing simulator left on for serving. It changes model outputs, so it gives wrong answers outside a benchmark ({{cite afd_plugin/model_executor/routing_simulator.py:10-11}}).

Why it matters. The knobs trade throughput, memory and startup time. The repository gives example values and the read sites; the right values come from measuring your own workload.

What DBO thresholds do the recipes set, and how do they compare with the vLLM defaults?

The recipes set decode 2 and prefill 12 ({{cite recipe/gpu/P2pNcclAFDConnector/deepseek_v2_lite/prefill_decode_colocation/2a2f_graph_dbo_dp1tp2.sh:24-25}}). The vLLM defaults are higher, 32 and 512 ({{cite vllm:vllm/config/parallel.py:227}}, {{cite vllm:vllm/config/parallel.py:232}}).

 Is the profiler on by default?

No. Each role's profiler is off until you set its ..._ENABLE variable ({{cite afd_plugin/compat/profiler.py:46-61}}).

 What does compute_gate_on_attention change, and which model forbids it?

When on, the FFN side runs only the expert layers, because the attention side computes the gate ({{cite afd_plugin/v1/worker/ffn_model_runner.py:211-215}}). The Qwen3-MoE wrapper requires it to be false ({{cite afd_plugin/model_executor/models/qwen3_moe.py:84-87}}).

 How do you select the deterministic benchmark routing, and why not use it for serving?

Set VLLM_MOE_ROUTING_SIMULATION_STRATEGY=afd_balanced ({{cite afd_plugin/model_executor/routing_simulator.py:5-8}}). It replaces real routing with a synthetic cycle, so it changes model outputs ({{cite afd_plugin/model_executor/routing_simulator.py:10-11}}).

 On an NPU, what does BATCH_SIZE_FACTOR control, and from what base?

It multiplies the CAM receive capacity, base 262144 tokens, with native float rounding; default 1 ({{cite afd_plugin/validation.py:45-54}}). It has no effect on GPU.

This page shows the registration, the identity swap, and which architectures map to which wrapper. --- AFD registers each supported model under an AFD<arch> name. At build time it swaps the model config to that {{term model-wrapper | AFD identity}}.

The idea

{{term afd}} needs a role-aware version of each model, so the attention side can replace the FFN stage with a remote proxy. It supplies one AFD<arch> class per architecture. It registers these classes with vLLM's {{term model-registry | ModelRegistry}}, as lazy "module:Class" strings, so vLLM imports a class only when it is needed.

The model config names a plain architecture, for example DeepseekV2ForCausalLM. At build time, the AFD worker swaps that name to AFDDeepseekV2ForCausalLM, so vLLM builds the AFD class instead of the native one. The swap copies the config, so the native config is left unchanged.

An everyday comparison. Think of a catalogue with an "AFD" edition of each item. You order by the plain name; the clerk swaps in the AFD edition. The comparison stops here: the swap keeps one hidden link intact, so vLLM Ascend can still tell a text model from a multimodal one.

In the code

Step 1: Register each AFD name

At the end of register_afd, a loop registers each architecture under the name "AFD" + arch ({{cite afd_plugin/__init__.py:211-214}}). The source map holds eight architectures ({{cite afd_plugin/__init__.py:96-139}}).

Step 2: The lazy "module:Class" form

The registered value is a string, not a class. vLLM stores it and imports the class only when the model is built ({{cite vllm:vllm/model_executor/models/registry.py:1126-1141}}). So loading the plugin does not import every model file.

Step 3: Detect an AFD model

has_afd_model_registration returns true when the model's architecture, with any AFD prefix removed, is in the map ({{cite afd_plugin/model_executor/models/model_utils.py:16-22}}). The runtime validator uses it to require a registered AFD model ({{cite afd_plugin/validation.py:136-141}}).

Step 4: Swap the model identity

get_afd_model_config finds the architecture in the map, deep-copies the model config, and sets its architecture to AFD<arch> ({{cite afd_plugin/model_executor/models/model_utils.py:25-46}}). The worker then uses the returned config ({{cite afd_plugin/v1/worker/attention_worker.py:75-80}}).

Deep dive

get_afd_model_config does not change the original config. It deep-copies it, then sets the architecture on the copy ({{cite afd_plugin/model_executor/models/model_utils.py:43-45}}).

  • deepcopy keeps the inner aliasing. A code comment states the reason: the pure-text identity hf_text_config is hf_config is kept automatically, because deepcopy preserves aliasing within the copied object graph ({{cite afd_plugin/model_executor/models/model_utils.py:39-43}}).
  • vLLM Ascend reads that identity. It uses the same-object check to tell a text model from a multimodal model. So the swap must not break it.
  • Only the architecture name changes. The rest of the config is the copy of the original ({{cite afd_plugin/model_executor/models/model_utils.py:44}}).

The README names model families loosely. The code registers exact architecture strings.

  • The README lists "Qwen3.5 / Qwen3.6 MoE" ({{cite README.md:51}}), but the code registers one architecture, Qwen3_5MoeForConditionalGeneration ({{cite afd_plugin/__init__.py:125-131}}).
  • get_afd_model_config raises for that architecture when the device type is not cuda ({{cite afd_plugin/model_executor/models/model_utils.py:34-38}}). So Qwen3.5 and Qwen3.6 run on CUDA only.
  • DeepseekV4ForCausalLM resolves to the NPU class or the GPU class, chosen at import by torch_npu ({{cite afd_plugin/__init__.py:109-113}}).

What can go wrong

  • Model not registered. A model whose architecture is not in the map fails the runtime check: "AFD ModelRunnerV2 requires a registered AFD model" ({{cite afd_plugin/validation.py:136-141}}).
  • Qwen3.5 on NPU. get_afd_model_config raises for a non-CUDA device ({{cite afd_plugin/model_executor/models/model_utils.py:34-38}}).
  • Model file import error. Because the registration is a lazy string, an import error in the model file surfaces when vLLM builds the model, not when the plugin loads ({{cite vllm:vllm/model_executor/models/registry.py:1126-1141}}).

Why it matters. The worker runs an AFD model only after the identity swap. If the architecture is not registered, the swap does nothing and the runtime check stops start-up.

Under what name is Qwen3MoeForCausalLM registered?

AFDQwen3MoeForCausalLM. The loop registers each key under "AFD" + key ({{cite afd_plugin/__init__.py:211-214}}).

 Why is the registered value a string, not a class?

So vLLM imports the model class only when it is needed, not when the plugin loads ({{cite vllm:vllm/model_executor/models/registry.py:1126-1141}}).

 What does get_afd_model_config change, and what does it keep?

It deep-copies the config and changes only the architecture name to AFD<arch> ({{cite afd_plugin/model_executor/models/model_utils.py:43-45}}). It keeps the hf_text_config is hf_config identity ({{cite afd_plugin/model_executor/models/model_utils.py:39-43}}).

 The README says "Qwen3.5 / Qwen3.6". Which architecture string does the code register?

One: Qwen3_5MoeForConditionalGeneration ({{cite afd_plugin/__init__.py:125-131}}).

 Why does get_afd_model_config use deepcopy instead of editing the architecture in place?

To leave the original config unchanged, and because deepcopy preserves the inner aliasing so hf_text_config is hf_config stays true. vLLM Ascend uses that identity to tell a text model from a multimodal one ({{cite afd_plugin/model_executor/models/model_utils.py:39-45}}).

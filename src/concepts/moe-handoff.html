The choice changes which classes build, what crosses the connector, and which layers the FFN runs. --- A MoE layer has a gate and experts. The {{term compute-gate-on-attention}} flag decides which {{term afd | AFD}} role runs the gate, and so what crosses the {{term connector}}.

The idea

A mixture-of-experts layer has two parts: a small gate that picks experts per token, and the large experts themselves. {{term afd}} always runs the experts on the {{term ffn-role | FFN role}}, because the expert weights are large. The gate is small, so AFD can run it on either side.

One flag chooses: compute_gate_on_attention. When it is false (the default), the gate stays with the experts on the FFN side. When it is true, the gate runs on the {{term attention-role | attention role}}, and the attention side sends the router output along with the hidden states.

An everyday comparison. Think of a mailroom. You can write the delivery route on the parcel before you hand it over (gate on the attention side), or let the mailroom read the address and decide (gate on the FFN side). Either way the parcel reaches the same shelf. The comparison stops here: the gate output is a tensor, not a label, and it must match the experts the FFN side runs.

In the code

Step 1: The default: the gate runs on the FFN side

With the flag false, the attention side ships the whole FFN or MoE block through a {{term remote-ffn-proxy | remote FFN proxy}}. The FFN side runs the native block, gate and all. On the CUDA MoE path the attention role still builds a {{term remote-experts | remote-experts}} shell, but its gate is None, so the shell ships only the hidden states ({{cite afd_plugin/model_executor/models/deepseek_v2.py:319-335}}).

Step 2: Gate on the attention side: compute, then send the router logits

With the flag true, the shell builds its own gate ({{cite afd_plugin/model_executor/models/deepseek_v2.py:306-318}}). Its forward computes the router logits first, then calls the experts proxy with them ({{cite afd_plugin/model_executor/models/deepseek_v2.py:347-371}}).

The experts proxy is AFDAttentionFusedMoE, a RemoteFFNProxy that adds router_logits to the send only when the experts use external routing ({{cite afd_plugin/model_executor/models/deepseek_v2.py:178-191}}).

Step 3: The FFN side runs experts only, for expert layers only

The {{term ffn-server-loop | FFN server loop}} drives the FFN model runner. Inside _ffn_forward, the set of layers depends on the flag. With the gate on the attention side, the FFN runs only the expert layers; otherwise it runs all layers ({{cite afd_plugin/v1/worker/ffn_model_runner.py:211-215}}).

For each received layer, the runner picks the compute call. An expert layer with the gate on the attention side calls compute_experts_output with the transported router logits; any other layer calls compute_ffn_output ({{cite afd_plugin/v1/worker/ffn_model_runner.py:251-267}}).

Step 4: compute_experts_output needs the gate cleared

compute_experts_output runs the native experts runner with the transported router logits. It checks that the runner gate is None, which is the v0.30 contract for external routing ({{cite afd_plugin/model_executor/models/deepseek_v2.py:702-721}}).

Deep dive

The send order is fixed: hidden states, then router logits (if any), then input ids (if any) ({{cite afd_plugin/connectors/gpu/p2p.py:336-338}}).

The input_ids are a 1-D int32 tensor, token-aligned with the hidden states; they are used only for the DeepSeek-V4 hash MoE ({{cite afd_plugin/connectors/gpu/p2p.py:210}}, {{cite afd_plugin/model_executor/models/deepseek_v4.py:89-92}}). For controlled MoE benchmarks, the plugin registers a deterministic routing strategy, {{term afd-balanced | afd_balanced}} ({{cite afd_plugin/model_executor/routing_simulator.py:166-171}}). It replaces the gate's choice with uniform weights and fixed, EP-balanced expert ids, so every rank gets an equal share ({{cite afd_plugin/model_executor/routing_simulator.py:122-163}}).

  • How to turn it on. Set vLLM's VLLM_MOE_ROUTING_SIMULATION_STRATEGY to afd_balanced ({{cite afd_plugin/model_executor/routing_simulator.py:5-8}}).
  • Weights. Uniform, 1 / top_k per selected expert ({{cite afd_plugin/model_executor/routing_simulator.py:113-118}}).
  • Expert ids. A fixed permutation (seed 1024), or the first AFD_BENCHMARK_FORCE_LB_TOPN_PER_RANK experts of each rank ({{cite afd_plugin/model_executor/routing_simulator.py:66-96}}).
  • Honesty. It changes model outputs and is for benchmark and profiling runs only ({{cite afd_plugin/model_executor/routing_simulator.py:10-11}}).

The strategy is registered in register_afd, outside the patch try/except ({{cite afd_plugin/__init__.py:183-187}}).

What can go wrong

This page reads the CUDA gate placement and the wire payloads. It does not read the NPU gate kernels or the hash-router internals. See {{link concepts/npu-overview}} and {{link code/deepseek-v2-py}}.
  • Qwen3-MoE with the gate on attention. The Qwen3-MoE wrapper requires compute_gate_on_attention=false and raises otherwise ({{cite afd_plugin/model_executor/models/qwen3_moe.py:84-87}}). README.md:50 states the same rule.
  • A held gate on the FFN experts. compute_experts_output raises if the FFN experts runner still owns a gate ({{cite afd_plugin/model_executor/models/deepseek_v2.py:716-717}}).
  • A dense layer sent to compute_experts_output. It raises if the layer is not an attention-side-gate MoE layer ({{cite afd_plugin/model_executor/models/deepseek_v2.py:708-711}}).
  • GPU gate-on-attention calling the wrong path. On CUDA the gated path must call compute_experts_output, not compute_ffn_output; the dense call raises ({{cite afd_plugin/model_executor/models/deepseek_v2.py:690-693}}).

Why it matters. The two sides must agree on where the gate runs. If the attention side sends router logits but the FFN side keeps its own gate, the experts would route twice and the output would be wrong.

What does compute_gate_on_attention decide?

Which role runs the MoE gate. False (the default) keeps the gate with the experts on the FFN side; true runs it on the attention side ({{cite afd_plugin/model_executor/models/deepseek_v2.py:306-320}}).

 When the gate runs on the attention side, which layers does the FFN run?

Only the expert layers. layer_indices is the sorted expert-layer set when the flag is set, else all layers ({{cite afd_plugin/v1/worker/ffn_model_runner.py:211-215}}).

 What extra tensor crosses the wire when the gate runs on the attention side, and when is it consumed?

router_logits. The FFN experts runner consumes it only when its gate is None (external routing), which AFD arranges by clearing the runner gate ({{cite afd_plugin/model_executor/models/deepseek_v2.py:548-553}}, {{cite afd_plugin/model_executor/models/deepseek_v2.py:714-721}}).

 What does DeepSeek-V4 add to the handoff, and why?

A 1-D int32 input_ids tensor, because its hash router needs the token ids to pick experts ({{cite afd_plugin/connectors/gpu/p2p.py:210}}, {{cite afd_plugin/model_executor/models/deepseek_v4.py:89-92}}).

 What does the afd_balanced strategy return, and why is it not for production?

Uniform weights (1 / top_k) and deterministic, EP-balanced expert ids ({{cite afd_plugin/model_executor/routing_simulator.py:99-119}}). It replaces the real routing, so it changes model outputs; it is for benchmark and profiling runs only ({{cite afd_plugin/model_executor/routing_simulator.py:10-11}}).

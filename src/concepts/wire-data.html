This page shows the tensors that cross, the transfer metadata, the fan-in and split, and the custom ops. --- The {{term data-plane | data plane}} moves hidden-state tensors between the roles once per layer and {{term stage}}. The FFN rank fans in its peers, computes, and splits the output back.

The idea

For each layer and stage, the attention rank sends its hidden states to its FFN rank. The FFN rank may own more than one attention peer, so it concatenates the inputs along the token dimension, runs the feed-forward, then splits the output back and returns each slice to the rank that produced it.

Each transfer carries a small metadata record: the layer index, the stage index and the per-peer token lengths. The token lengths set the expected tensor shape and the split sizes. The transfers go through custom ops, so they stay usable under torch.compile and CUDA graph capture.

An everyday comparison. Think of parcels with shipping labels. The label says how many boxes and for which address, so the depot can combine shipments and later separate them again. The comparison stops here: the "parcels" also carry optional extras next to the hidden states, the router logits and the token IDs, which only some models send.

In the code

Step 1: What the attention rank sends

send_attn_output sends the hidden states first, then the optional router logits, then the optional token IDs ({{cite afd_plugin/connectors/gpu/p2p.py:323-390}}). The hidden states are a CUDA tensor of shape (num_tokens, hidden_size); the hidden size comes from the model config ({{cite afd_plugin/connectors/gpu/p2p.py:195-197}}).

The leading dimension must equal total_tokens, unless torch.compile is tracing ({{cite afd_plugin/connectors/gpu/p2p.py:347-353}}). The token IDs must be a one-dimensional int32 tensor ({{cite afd_plugin/connectors/gpu/p2p.py:363-370}}).

Step 2: The transfer metadata

Each transfer carries an AFDTransferMetadata: the layer index, the stage index and the per-peer sequence lengths ({{cite afd_plugin/connectors/metadata.py:188-190}}). The sum of the lengths is the expected leading dimension ({{cite afd_plugin/connectors/metadata.py:198-200}}).

The shape check compares shape[0] with total_tokens ({{cite afd_plugin/connectors/metadata.py:230-231}}).

Step 3: The FFN rank fans in its peers

recv_attn_output receives one tensor from every attention peer in the subgroup, concatenates them along the token dimension, and records each peer's length in the returned metadata ({{cite afd_plugin/connectors/gpu/p2p.py:428-552}}).

With one peer the single tensor is the whole input ({{cite afd_plugin/connectors/gpu/p2p.py:520-524}}). All of a step's receives run in one NCCL group, so the peers' transfers proceed together ({{cite afd_plugin/connectors/gpu/p2p.py:514-519}}).

Step 4: The FFN rank splits the output back

send_ffn_output splits the output along the token dimension by the recorded sequence lengths, then sends each slice to the attention rank that produced it ({{cite afd_plugin/connectors/gpu/p2p.py:554-613}}).

When the recorded lengths do not cover every peer, the split falls back to an even split, which raises if the tokens do not divide evenly ({{cite afd_plugin/connectors/gpu/p2p.py:590-599}}).

Step 5: The transfers are custom ops

The sends and receives are wrapped in four custom ops: afd_p2p_send, afd_p2p_recv, and the _group variants ({{cite afd_plugin/connectors/gpu/p2p.py:979-1122}}). The wrapping keeps the transfers traceable by torch.compile and capturable by CUDA graphs ({{cite afd_plugin/connectors/gpu/p2p.py:983-986}}). Each op runs on the current CUDA stream ({{cite afd_plugin/connectors/gpu/p2p.py:1002-1006}}). The {{link code/p2p-py}} page reads the custom ops in full.

Deep dive

Take a 4A2F topology, so FFN rank 0 owns attention ranks A0 and A1 ({{cite afd_plugin/distributed/topology.py:136}}). The hidden size is 2048 for DeepSeek-V2-Lite; this value is inferred from the checkpoint config, not stored in either repository. Take one decode step with 8 tokens on A0 and 8 on A1, in bf16 (inferred from the recipe).

  • A0 sends: hidden_states of shape [8, 2048], metadata seq_lens = [8].
  • A1 sends: hidden_states of shape [8, 2048], metadata seq_lens = [8].
  • On the wire: each tensor is 8 × 2048 × 2 bytes = 32,768 bytes, per layer, per direction.
  • F0 receives and concatenates: [16, 2048], with seq_lens = [8, 8] ({{cite afd_plugin/connectors/gpu/p2p.py:540-544}}).
  • F0 computes and splits back: two slices of [8, 2048]; the first returns to A0, the second to A1 ({{cite afd_plugin/connectors/gpu/p2p.py:601-613}}).

The FFN rank derives the per-peer shapes from the DP metadata before it receives ({{cite afd_plugin/connectors/gpu/p2p.py:776-807}}); see {{link concepts/control-plane}}.

Two tensors cross next to the hidden states, in this wire order: hidden states, then router logits, then token IDs ({{cite afd_plugin/connectors/gpu/p2p.py:336-338}}).

TensorShape / dtypeWhen it is sent
hidden_states[n, hidden_size], model dtypealways

The FFN side asks for the router logits only when compute_gate_on_attention is set, through a routing spec ({{cite afd_plugin/v1/worker/ffn_model_runner.py:225-229}}). It asks for the token IDs only when the model needs them ({{cite afd_plugin/v1/worker/ffn_model_runner.py:221}}). The router logits width and dtype come from the model ({{cite afd_plugin/connectors/gpu/p2p.py:481-491}}). The {{link concepts/moe-handoff}} page reads the gate placement.

Each receive writes into a buffer. In eager mode the connector allocates a fresh tensor per receive. When CUDA graphs are on, the receive reuses a buffer preallocated during the control-plane update, so the allocation stays stable for capture and replay ({{cite afd_plugin/connectors/gpu/p2p.py:472-477}}, {{cite afd_plugin/connectors/gpu/p2p.py:911-936}}). The attention side's recv_ffn_output takes a preallocated ref_tensor for the same reason ({{cite afd_plugin/connectors/gpu/p2p.py:392-426}}). The custom ops issue the transfers on the current CUDA stream, inside one NCCL group when there is more than one peer ({{cite afd_plugin/connectors/gpu/p2p.py:1037-1070}}).

What can go wrong

This page shows the GPU data plane. The NPU connectors move the same tensors with CAM operators; see {{link concepts/npu-overview}}. The page leaves out the backend transfer state the NPU connectors carry on the transfer context, and the graph key details, which the {{link concepts/cuda-graphs}} page covers.
  • Shape mismatch. A hidden-state tensor whose leading dimension is not total_tokens raises, unless torch.compile is tracing ({{cite afd_plugin/connectors/gpu/p2p.py:347-353}}).
  • An uneven split. When the recorded lengths do not cover every peer and the tokens do not divide evenly, the split raises ({{cite afd_plugin/connectors/gpu/p2p.py:590-599}}).
  • A CPU tensor. The hidden states must be on the GPU; a CPU tensor is rejected ({{cite afd_plugin/connectors/gpu/p2p.py:634-635}}).
  • Wrong token-ID dtype. The token IDs must be int32 and one-dimensional ({{cite afd_plugin/connectors/gpu/p2p.py:363-370}}).

Why it matters. The two roles must agree on the shapes. The recorded sequence lengths are the only record of which tokens belong to which peer, so the FFN rank uses them to split the output back.

What crosses from the attention rank to the FFN rank for one layer and stage?

The hidden states [n, hidden_size], then optional router logits and optional int32 token IDs, in that order ({{cite afd_plugin/connectors/gpu/p2p.py:336-338}}).

 How does the FFN rank know how to split its output back?

From the recorded sequence lengths. recv_attn_output records each peer's token length ({{cite afd_plugin/connectors/gpu/p2p.py:540-544}}), and send_ffn_output splits by those lengths ({{cite afd_plugin/connectors/gpu/p2p.py:590-613}}).

 Why are the sends and receives wrapped in custom ops?

So the transfers stay traceable by torch.compile and capturable by CUDA graphs ({{cite afd_plugin/connectors/gpu/p2p.py:983-986}}). The connector registers four ops, with fake implementations for tracing ({{cite afd_plugin/connectors/gpu/p2p.py:979-1122}}).

 When does the attention side send the int32 token IDs?

For the DeepSeek-V4 hash MoE, when the model asks for them ({{cite afd_plugin/connectors/gpu/p2p.py:210-214}}, {{cite afd_plugin/v1/worker/ffn_model_runner.py:221}}).

 In 4A2F with 8 tokens on A0 and 8 on A1, what shape does F0 run the FFN on, and what does it send back?

F0 concatenates to [16, 2048] with seq_lens = [8, 8] ({{cite afd_plugin/connectors/gpu/p2p.py:540-544}}), then splits the output into two [8, 2048] slices, one per peer ({{cite afd_plugin/connectors/gpu/p2p.py:601-613}}). The 2048 is inferred from the DeepSeek-V2-Lite checkpoint.

This page shows what each role owns, and why the FFN side has no real scheduler, no KV cache and no sampler. --- {{term afd}} runs one model as two servers. The {{term attention-role | attention role}} keeps vLLM's front end; the {{term ffn-role | FFN role}} is a connector-driven loop.

The idea

A normal vLLM server owns the whole request path: the API server, the scheduler, the KV cache, the model and the sampler. AFD keeps all of that on the {{term attention-server | attention server}}. The {{term ffn-server | FFN server}} is different. It has no API server, no KV cache and no real scheduler (only a no-op stand-in). A {{term connector}} loop drives it: it waits for work, runs the feed-forward and MoE experts, and sends the result back.

Each side also owns a different part of every decoder layer. The attention server builds the real attention module and sends its output to the FFN side. The FFN server builds the real experts and drops the attention module.

An everyday comparison. Think of a kitchen with a front counter. The counter takes the order, tracks the bill and hands finished plates to the customer. The cooks only cook what the counter passes through. The comparison stops here: the FFN server is not a separate service. It runs part of the same model's forward pass, once per layer, for every step.

In the code

Step 1: Two workers, two runners

AFD does not register its role workers through a vLLM API. A patch rewrites parallel_config.worker_cls when it is "auto"; see {{link concepts/worker-selection}}. Each role worker then swaps in its own model runner inside init_device ({{cite afd_plugin/v1/worker/attention_worker.py:82-87}}, {{cite afd_plugin/v1/worker/ffn_worker.py:93-98}}).

Step 2: The FFN EngineCore returns early

A patch on EngineCore.__init__ checks the role. For an FFN config, it builds the model executor and then returns, before the KV cache and the scheduler are set up ({{cite afd_plugin/compat/patches/engine_core.py:59-68}}).

The FFN EngineCore sets the KV block counts to zero and installs a no-op scheduler. The no-op scheduler is not None, because a native readiness handshake calls a method on it ({{cite afd_plugin/compat/patches/engine_core.py:605-606}}, {{cite afd_plugin/compat/patches/engine_core.py:608-614}}).

Step 3: The FFN worker has no KV cache and does not sample

The FFN worker reports an empty KV cache spec, so vLLM allocates no KV blocks for it ({{cite afd_plugin/v1/worker/ffn_worker.py:102-105}}). The FFN runner repeats this ({{cite afd_plugin/v1/worker/ffn_model_runner.py:147-148}}).

Two methods guard against the native scheduler path. The scheduler-driven execute_model raises, and the FFN runner's sample_tokens raises ({{cite afd_plugin/v1/worker/ffn_worker.py:122-131}}, {{cite afd_plugin/v1/worker/ffn_model_runner.py:405-406}}).

Step 4: Each role builds half of a decoder layer

The model wrapper is role-aware. AFDDeepseekV2DecoderLayer reads the role, then builds only the modules that role owns ({{cite afd_plugin/model_executor/models/deepseek_v2.py:383-396}}). On the attention role it builds the native attention module ({{cite afd_plugin/model_executor/models/deepseek_v2.py:474-491}}) and replaces the feed-forward:

  • a dense layer becomes a {{term remote-ffn-proxy | RemoteFFNProxy}} ({{cite afd_plugin/model_executor/models/deepseek_v2.py:516-517}});
  • an MoE layer becomes an AFDDeepseekV2RemoteExpertsMoE shell ({{cite afd_plugin/model_executor/models/deepseek_v2.py:493-500}}).

On the FFN role it drops attention (a PPMissingLayer) and keeps the native experts ({{cite afd_plugin/model_executor/models/deepseek_v2.py:520}}, {{cite afd_plugin/model_executor/models/deepseek_v2.py:538-559}}). The {{link concepts/model-wrappers}} page reads this split in full.

Step 5: Where requests go, and the start order

Requests go only to the attention API server. The two servers may start in either order ({{cite README.md:258-260}}).

The attention side keeps logits and sampling because only it holds the whole token state and the KV cache. The sampling runs once per step, after the last layer, on every step ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:582-594}}).

The FFN worker does not wait for the scheduler. After the connector is initialized, it starts a daemon thread that runs the {{term ffn-server-loop | FFN server loop}} ({{cite afd_plugin/v1/worker/ffn_worker.py:107-113}}, {{cite afd_plugin/v1/worker/ffn_worker.py:133-158}}). The loop body runs one step at a time:

  1. If the connector has no control plane, raise. GPU FFN needs a control-plane-driven connector ({{cite afd_plugin/v1/worker/ffn_worker.py:169-174}}).
  2. Receive one DP metadata payload for the step ({{cite afd_plugin/v1/worker/ffn_worker.py:176}}).
  3. Run capture_model for a warm-up or capture step, else execute_model ({{cite afd_plugin/v1/worker/ffn_worker.py:182-196}}).

The {{link concepts/ffn-runtime}} page reads the loop and the per-layer forward in full. The {{link concepts/control-plane}} page reads the DP metadata payload.

The README says the two servers may start in either order ({{cite README.md:258-260}}). The order does not matter because the connector setup is a collective rendezvous. Every attention and FFN rank must call init_afd_connector ({{cite afd_plugin/connectors/base.py:124}}); the first ranks wait at the rendezvous until the rest arrive ({{cite afd_plugin/connectors/gpu/p2p.py:245-262}}). The FFN worker builds and initializes its connector inside initialize_from_config, then starts the loop ({{cite afd_plugin/v1/worker/ffn_worker.py:107-113}}).

What can go wrong

This page shows the GPU (CUDA) role split. The NPU variant uses the same role idea with a different transport; see {{link concepts/npu-overview}}. The page also folds the metadata provider and the DBO stages; the {{link concepts/attention-runtime}} and {{link concepts/ffn-runtime}} pages give those.
  • A request sent to the FFN server. The FFN server has no API server, so there is nothing to answer it. Send requests only to the attention API server ({{cite README.md:258-260}}).
  • The scheduler reaches the FFN worker. A scheduler-driven execute_model on the FFN worker raises at once ({{cite afd_plugin/v1/worker/ffn_worker.py:122-131}}).
  • A connector with no control plane on GPU. The GPU FFN loop needs a control-plane-driven connector and raises for one that sets control_plane = None ({{cite afd_plugin/v1/worker/ffn_worker.py:169-174}}).

Why it matters. The two servers do very different work. If you treat the FFN server like a normal vLLM server, nothing schedules its work and no token comes back.

Which three parts does the FFN server not have?

No API server, no KV cache and no real scheduler (only a no-op stand-in). Its EngineCore returns after the executor is built ({{cite afd_plugin/compat/patches/engine_core.py:59-68}}), and the worker reports an empty KV cache spec ({{cite afd_plugin/v1/worker/ffn_worker.py:102-105}}).

 Which server samples the next token?

The attention server. Its runner wraps native sampling, which runs every step ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:582-594}}). The FFN runner's sample_tokens raises ({{cite afd_plugin/v1/worker/ffn_model_runner.py:405-406}}).

 On the FFN role, what replaces the attention module of a decoder layer?

A PPMissingLayer: the FFN role builds no attention ({{cite afd_plugin/model_executor/models/deepseek_v2.py:520}}). It keeps the native experts instead ({{cite afd_plugin/model_executor/models/deepseek_v2.py:538-559}}).

 The two servers can start in either order. Why is that safe?

Connector setup is a collective rendezvous. Every rank calls init_afd_connector ({{cite afd_plugin/connectors/base.py:124}}) and the early ranks wait at tcp://host:port for the rest ({{cite afd_plugin/connectors/gpu/p2p.py:245-262}}).

 What drives one FFN step, if not the scheduler?

The connector loop. It receives one DP metadata payload per step ({{cite afd_plugin/v1/worker/ffn_worker.py:176}}), then calls execute_model or capture_model ({{cite afd_plugin/v1/worker/ffn_worker.py:182-196}}). The loop is a daemon thread started after connector init ({{cite afd_plugin/v1/worker/ffn_worker.py:133-158}}).

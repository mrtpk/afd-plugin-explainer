This page maps the class layout, the collective init, the four data calls, the control plane and the custom ops. --- The GPU {{term connector}} is P2pNcclAFDConnector. It moves hidden states with vLLM's {{term pynccl | PyNcclCommunicator}} over point-to-point NCCL.

Purpose

This file implements the connector contract for CUDA. It builds the {{term afd-world | AFD world}}, the per-subgroup communicators and the control-plane group, and moves tensors through four custom ops. The contract itself is on {{link concepts/connector-contract}}; this page reads the implementation.

Where it sits

Who calls it

The factory loads this module by name and builds the connector for a runner ({{cite afd_plugin/connectors/factory.py:88-92}}). The runner then calls init_afd_connector once ({{cite afd_plugin/v1/worker/ffn_model_runner.py:108-109}}), then the four data calls per layer and stage, and close at shutdown ({{cite afd_plugin/v1/worker/ffn_model_runner.py:455}}).

What it calls

The data transfers go through vLLM's PyNcclCommunicator.send and recv ({{cite vllm:vllm/distributed/device_communicators/pynccl.py:91}}). The process groups come from the plugin's own helper ({{cite afd_plugin/distributed/afd_process_group.py:62-120}}) and the rank mapping from the topology module ({{cite afd_plugin/distributed/topology.py:118}}).

Walk through the main methods

init_afd_connector: the collective setup

This is a collective call: every attention and FFN rank must run it with matching host, port and rank counts ({{cite afd_plugin/connectors/gpu/p2p.py:245-262}}). It does three things. First, it registers the custom ops and joins the AFD world group, rendezvoused at tcp://host:port ({{cite afd_plugin/connectors/gpu/p2p.py:267-276}}).

Second, it builds this rank's subgroup communicators over a prefix of the world's rendezvous store ({{cite afd_plugin/connectors/gpu/p2p.py:278-304}}). It creates two PyNcclCommunicator instances, attention-to-FFN and FFN-to-attention, and registers each for the custom ops.

Third, on ranks that join the control plane, it creates the "p2p" group ({{cite afd_plugin/connectors/gpu/p2p.py:306-314}}). The {{link concepts/topology}} page reads the world order and the group sizes.

The four data calls

The data path is four methods. The attention side calls two, the FFN side calls two.

  • send_attn_output sends hidden states, then optional router logits and token IDs, to subgroup rank 0 ({{cite afd_plugin/connectors/gpu/p2p.py:371-390}}).
  • recv_ffn_output receives this rank's output slice into a preallocated ref_tensor ({{cite afd_plugin/connectors/gpu/p2p.py:415-421}}).
  • recv_attn_output receives every peer's tensor in one NCCL group, concatenates them, and records each peer's length ({{cite afd_plugin/connectors/gpu/p2p.py:514-544}}).
  • send_ffn_output splits the output by those lengths and sends each slice back ({{cite afd_plugin/connectors/gpu/p2p.py:590-613}}).

The {{link concepts/wire-data}} page reads the shapes, the fan-in and the split in full.

P2pNcclAFDControlPlane: the DP-metadata path

The connector owns one control-plane instance and exposes it as control_plane ({{cite afd_plugin/connectors/gpu/p2p.py:222}}, {{cite afd_plugin/connectors/gpu/p2p.py:724-733}}). It has three methods: apply a payload locally, send one, receive one.

update_state_from_dp_metadata derives the wire-tensor shapes and preallocates the graph-mode buffers ({{cite afd_plugin/connectors/gpu/p2p.py:744-851}}); send_dp_metadata_list transmits only on the designated sender ranks ({{cite afd_plugin/connectors/gpu/p2p.py:870-883}}). The {{link concepts/control-plane}} page reads these.

_register_p2p_custom_ops: four ops, once per process

The module registers four custom ops: afd_p2p_send, afd_p2p_recv, and the _group variants ({{cite afd_plugin/connectors/gpu/p2p.py:979-1122}}). Each op wraps the NCCL send or receive on the current stream and has a fake implementation for tracing.

  1. Line 1089-1090. If the op is already on torch.ops.vllm, return; torch rejects a re-definition.
  2. Line 1091-1096. Otherwise register the op, its mutated args and its fake implementation.
  3. Line 1122. Set the module flag so the registration runs once per process.

Deep dive

The connector owns three communication objects with different scopes.

ObjectScopeBuilt at
AFD world group ("afd")all ranks; the rendezvous store{{cite afd_plugin/connectors/gpu/p2p.py:269-276}}
subgroup communicators (a2e, e2a)one FFN rank + its attention peers{{cite afd_plugin/connectors/gpu/p2p.py:289-304}}
control-plane group ("p2p")FFN ranks + first min_size attention ranks{{cite afd_plugin/connectors/gpu/p2p.py:306-314}}

The subgroup communicators are built while the AFD world is the default process group, so the stateless group reuses the world's store instead of opening a second one ({{cite afd_plugin/connectors/gpu/p2p.py:278-288}}). The custom ops look the communicators up by integer id, because an op cannot capture a Python object ({{cite afd_plugin/connectors/gpu/p2p.py:965-976}}).

Which vLLM class moves the tensors?

PyNcclCommunicator, vLLM's NCCL wrapper ({{cite vllm:vllm/distributed/device_communicators/pynccl.py:91}}). The connector wraps its send and recv in custom ops.

 What three groups does init_afd_connector set up?

The AFD world group ({{cite afd_plugin/connectors/gpu/p2p.py:269-276}}), the per-subgroup communicators ({{cite afd_plugin/connectors/gpu/p2p.py:289-304}}), and the control-plane "p2p" group on ranks that join it ({{cite afd_plugin/connectors/gpu/p2p.py:306-314}}).

 Why does the op registration check hasattr(torch.ops.vllm, op_name) first?

Because torch keeps the op in a process-global registry. After a module reload, the module flag can be False while the op is still defined, so re-defining it would fail; the code reuses the existing op instead ({{cite afd_plugin/connectors/gpu/p2p.py:1089-1096}}).

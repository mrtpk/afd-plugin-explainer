This page reads it step by step. --- This module is the plugin entry point. register_afd applies the compat patches and registers the routing strategy, the DBO op and the AFD models.

Purpose

vLLM calls register_afd once per process through the vllm.general_plugins entry point. The function installs AFD and then stops; it runs no model and keeps no connection.

Where it sits

Who calls it

Only vLLM calls it, through the entry point ({{cite pyproject.toml:45-46}}). The call sites and processes are on the {{link learn/vllm-plugins}} page.

What it calls

It imports the four patch modules ({{cite afd_plugin/__init__.py:172-176}}), the routing simulator ({{cite afd_plugin/__init__.py:183-185}}), the DBO op ({{cite afd_plugin/__init__.py:190}}), and, on NPU, the Ascend config patch ({{cite afd_plugin/__init__.py:205-207}}). It ends by calling vLLM's ModelRegistry.register_model ({{cite afd_plugin/__init__.py:211-214}}).

Walk through register_afd

The function runs in two parts: safety checks that can return early, then the registration steps.

Part 1: Guard, import safety and version check

  1. Line 151. The guard returns if _registered is already set, so the registration body runs once per process ({{cite afd_plugin/__init__.py:150-153}}).
  2. Line 155. It applies the opt-in spawn override again (it also ran at import time).
  3. Line 157. If vLLM is not importable, it sets _registered and returns. So importing the package stays safe on a machine with no vLLM ({{cite afd_plugin/__init__.py:157-160}}).
  4. Line 165. It checks the vLLM version with strict=False, so a mismatch gives a warning, not an error ({{cite afd_plugin/compat/vllm.py:38-50}}). The whole check sits in a try/except ({{cite afd_plugin/__init__.py:162-170}}).

Part 2: Patches, routing, DBO, the NPU patch and the models

  1. Lines 172-176. It imports the four patch modules. Importing a patch module applies it. The import sits in a try/except ({{cite afd_plugin/__init__.py:172-181}}).
  2. Line 187. It registers the AFD routing strategy. This call is not wrapped ({{cite afd_plugin/__init__.py:183-187}}).
  3. Line 192. It registers the DBO yield custom op, inside a try/except ({{cite afd_plugin/__init__.py:189-197}}).
  1. Line 204. It applies the Ascend config patch only when the platform device type is "npu" ({{cite afd_plugin/__init__.py:202-209}}). This step is not wrapped.
  2. Lines 211-214. It registers each model under its AFD-prefixed name ({{cite afd_plugin/__init__.py:211-214}}).
  3. Line 216. It sets _registered = True, so a later call in the same process returns early.

The spawn override

The override is opt-in through one environment variable. It changes Python's default multiprocessing context, for an Ascend async recipe that cannot use forkserver.

  1. Line 60. It returns at once unless AFD_FORCE_SPAWN_MULTIPROCESSING is "1" ({{cite afd_plugin/__init__.py:60}}).
  2. Line 62. It forces the default start method to spawn.
  3. It then redirects the forkserver context and get_context("forkserver") to the spawn context ({{cite afd_plugin/__init__.py:70-87}}).

It runs once at import time ({{cite afd_plugin/__init__.py:94}}) and again inside register_afd ({{cite afd_plugin/__init__.py:155}}). The import-time call reaches the Ascend workers, which import the worker class directly and do not call the entry point ({{cite afd_plugin/__init__.py:90-94}}).

Deep dive

Four steps swallow their own exceptions, and three do not. The difference decides which failures are quiet and which stop the process.

StepLinesOn failure
Version check{{cite afd_plugin/__init__.py:162-170}}Caught: logged at debug.

DBO custom op{{cite afd_plugin/__init__.py:189-197}}Caught: logged at debug.

NPU Ascend patch{{cite afd_plugin/__init__.py:199-209}}Not caught: the error propagates.

The version-check exception is caught twice: the helper warns instead of raising with strict=False, and the call also sits in a try/except ({{cite afd_plugin/compat/vllm.py:48-50}}).

Import safety. Importing afd_plugin must not need vLLM, so local CPU tests work. Two things make it safe: register_afd returns early when find_spec("vllm") is None ({{cite afd_plugin/__init__.py:157-160}}), and __version__ falls back to a setuptools_scm value or "0.0.0+unknown" ({{cite afd_plugin/__init__.py:36-44}}).

VariableRead atEffect
AFD_FORCE_SPAWN_MULTIPROCESSING{{cite afd_plugin/__init__.py:60}} "1" forces the spawn start method and redirects forkserver. Any other value does nothing.

Under what name is DeepseekV2ForCausalLM registered?

AFDDeepseekV2ForCausalLM. The loop registers each key under "AFD" + key ({{cite afd_plugin/__init__.py:211-214}}).

 Which step runs only on NPU?

The Ascend config patch. It runs only when the platform device type is "npu" ({{cite afd_plugin/__init__.py:202-209}}).

 What happens when register_afd runs on a machine with no vLLM installed?

It sets _registered = True and returns before any registration, so the import stays safe ({{cite afd_plugin/__init__.py:157-160}}).

 If registering a model raises, does the process keep running? And if the version check raises?

Model registration is not wrapped, so its error propagates ({{cite afd_plugin/__init__.py:211-214}}). The version check is wrapped in a try/except, and with strict=False it only warns, so it does not stop the process ({{cite afd_plugin/__init__.py:162-170}}).

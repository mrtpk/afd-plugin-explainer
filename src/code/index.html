This page maps the repository. It shows the folder tree with counts, which folder depends on which, and how much of the Python code is GPU, NPU or shared. The module pages then read the most important files.

Purpose

afd-plugin is one Python package, afd_plugin, plus kernels, recipes, docs and tests. The package is what vLLM loads. This map helps you find a file and see where it sits before you open a module page.

How the folders depend on each other

The Python imports run in one direction, from the entry point down to the distributed helpers. The main edges are:

  1. Entry point. afd_plugin/__init__.py imports the config ({{cite afd_plugin/__init__.py:16}}), then the compat patches, the routing simulator and the DBO op ({{cite afd_plugin/__init__.py:172-192}}).
  2. Config and compat. The config_validation patch reads the AFD config and the validation helpers ({{cite afd_plugin/compat/patches/config_validation.py:20-24}}).
  3. Workers and model wrappers. The runners in v1/worker and the model wrappers in model_executor import the connectors ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:37}}, {{cite afd_plugin/model_executor/models/deepseek_v2.py:25}}).
  4. Connectors. The connectors read the config and resolve the role rank from the distributed helpers ({{cite afd_plugin/connectors/factory.py:11-17}}).
  5. Distributed. afd_plugin/distributed holds the process group, the topology and the role-rank helpers; it is at the bottom of the chain.

So the order is: entry point → config and compat → workers and model wrappers → connectors → distributed.

The GPU / NPU / shared split

About half of the Python is NPU-specific, and only a small part is GPU-specific. The rest is shared.

The split is by folder name. A file counts as GPU or NPU only when a path part is gpu or npu. Several "shared" files are CUDA paths in practice: the repository groups only the connectors by backend ({{cite afd_plugin/connectors/gpu/}}, {{cite afd_plugin/connectors/npu/}}), while the shared runners and model wrappers live outside those folders.

How the numbers were measured

The line counts above and in the tree come from the repository at the pinned commit, not from a tool report. The method:

  1. List tracked files with git ls-tree -r --name-only at the pinned commit.
  2. Keep the .py files under afd_plugin/ for the split; count the newlines in each one (a file with no trailing newline still counts its last line).
  3. Classify each file: NPU when a path part is npu, GPU when a path part is gpu, else shared.

The folder tree uses the same git ls-tree file list and newline count, over all text files, not only Python. The site tool tools/gen_folder_tree.py does this and writes the tree between the markers. Binary files count as 0 lines.

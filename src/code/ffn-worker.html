Purpose

These three files run the FFN side with no scheduler and no KV cache. The concept is on {{link concepts/ffn-runtime}}; this page maps the files.

Where it sits

Who calls it

The AFD config patch rewrites worker_cls to AFDFFNWorker when the role is FFN ({{cite afd_plugin/validation.py:280-296}}). The FFN EngineCore returns after the executor is built, so no scheduler drives this worker; the loop is driven by the control plane instead ({{cite afd_plugin/v1/worker/ffn_worker.py:133-158}}).

What it calls

The worker swaps the runner class and delegates to native Worker.init_device ({{cite afd_plugin/v1/worker/ffn_worker.py:73-100}}). The runner builds the connector ({{cite afd_plugin/connectors/factory.py:49-68}}) and calls the model wrapper's compute_ffn_output or compute_experts_output.

Walk through the main methods

_run_ffn_server_loop: one step per control payload

The loop runs until the shutdown event is set. Each pass reads one DP-metadata payload, then dispatches to capture or execute ({{cite afd_plugin/v1/worker/ffn_worker.py:160-199}}).

  1. Lines 169-174. A connector with control_plane None raises; the GPU FFN needs one.
  2. Line 176. One recv_dp_metadata_list per step.
  3. Lines 182-189. Warm-up or graph capture calls capture_model.
  4. Lines 190-196. Otherwise execute_model runs the step; then the loop synchronizes.

_ffn_forward: layers x stages

The forward sets the layer set from the gate flag, then loops layers and stages ({{cite afd_plugin/v1/worker/ffn_model_runner.py:207-269}}).

  1. Line 236. recv_attn_output returns the hidden states and the context.
  2. Lines 251-261. An attention-side-gate expert layer calls compute_experts_output.
  3. Lines 262-267. Any other layer calls compute_ffn_output through _execute_eager_mode.
  4. Line 268. send_ffn_output sends the result back.

aggregate_ffn_token_counts: attention counts to FFN ranks

Each FFN rank sums the contiguous block of attention ranks mapped to it ({{cite afd_plugin/v1/worker/ffn_metadata.py:15-60}}). Every attention peer contributes at least one row, so a zero-token peer still adds a placeholder.

Deep dive

The GPU FFN path supports only control-plane-driven connectors. The runner asserts it at construction ({{cite afd_plugin/v1/worker/ffn_model_runner.py:87-89}}), and the loop re-checks it each pass ({{cite afd_plugin/v1/worker/ffn_worker.py:169-174}}). The async NPU connector sets control_plane = None and drives the FFN side through its own receive loop; that path is on {{link concepts/npu-overview}}.

What does sample_tokens do on the FFN runner?

It raises; the FFN role never samples ({{cite afd_plugin/v1/worker/ffn_model_runner.py:405-406}}).

 What starts the FFN server loop, and on what kind of thread?

initialize_from_config calls start_ffn_server_loop, which starts a daemon thread ({{cite afd_plugin/v1/worker/ffn_worker.py:107-113}}, {{cite afd_plugin/v1/worker/ffn_worker.py:153-158}}).

 On 3A2F, why does a zero-token attention peer still add a row to its FFN rank's count?

aggregate_ffn_token_counts takes max(1, count) per peer, so every peer contributes at least one placeholder row; F0 sums the block {A0, A1} and F1 the block {A2} ({{cite afd_plugin/v1/worker/ffn_metadata.py:49-60}}).

The {{term control-plane | control plane}} publishes once; each layer runs two {{term stage | stages}}.

The idea

One decode step produces one new token per request. On AFD, the attention side runs the step and the FFN side answers each layer. With DBO, each layer runs two {{term stage | stages}} that overlap. With graphs, both sides replay instead of running eager.

This tour follows the graph recipe: 2A2F, DP1, TP2, DBO on, FULL_DECODE_ONLY ({{cite recipe/gpu/P2pNcclAFDConnector/deepseek_v2_lite/prefill_decode_colocation/2a2f_graph_dbo_dp1tp2.sh:7-29}}). Rank A0 maps to F0 and A1 to F1 ({{cite afd_plugin/distributed/topology.py:135-136}}).

Keep the two frequencies apart. The control plane publishes {{term dp-metadata | DP metadata}} once per step, before the layer loop. The {{term data-plane | data plane}} sends tensors once per layer and stage. Sampling runs once per step, after the last layer.

The attention server's {{term enginecore | EngineCore}} and scheduler build one step, then the executor runs it ({{cite vllm:vllm/v1/engine/core.py:600-601}}). This is native vLLM. The FFN server has no such loop; it is connector-driven ({{cite afd_plugin/v1/worker/ffn_worker.py:32-38}}).

The executor calls the AFD runner's execute_model. It wraps the native method in an AFD execution context, then delegates ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:569-595}}).

Native code still does the request, attention and KV work. The wrapper adds AFD state around it. See {{link concepts/attention-runtime}}.

The context scopes four things: the DP1 DBO dispatch seam, the FULL replay hook, the ubatch prepare seam, and the metadata provider ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:340-349}}).

The replay hook is used only in FULL_DECODE_ONLY mode with a graph manager ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:323-327}}). See {{link concepts/cuda-graphs}}.

Before the layer loop, the attention side publishes the {{term dp-metadata | DP metadata}}. With DBO, the ubatch prepare seam sends it after it slices the step into two stages ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:153-157}}).

That call updates the local control state and sends one payload ({{cite afd_plugin/v1/worker/attention_metadata.py:115-116}}). It is the first thing that crosses the connector each step. See {{link concepts/control-plane}}.

There are two code paths to the same publish, chosen by whether the step uses DBO. Both run once per step, before the layer loop.

  1. With DBO. The ubatch prepare seam calls send_dp_metadata after it slices the step into two stages ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:153-157}}).
  2. Without ubatching. The metadata provider calls it from install_afd_metadata_on_forward_context ({{cite afd_plugin/v1/worker/attention_metadata.py:252-257}}).

The FFN side waits for exactly one payload per step either way ({{cite afd_plugin/v1/worker/ffn_worker.py:176}}). A per-step call must not be folded into the per-layer sequence. The payload carries the per-stage token counts that set the tensor shapes. See {{link concepts/wire-data}}.

For a pure-decode step, native FULL replay runs. The replay hook publishes one padded control payload just before the replay ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:286-303}}). For a DBO step with two stages, the prepare seam already sent the full two-stage payload, so the hook asserts and delegates ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:275-280}}).

Inside each layer, the {{term remote-ffn-proxy | proxy}} sends its hidden states, yields, then receives. The yield lets the other stage run while this one waits ({{cite afd_plugin/model_executor/models/deepseek_v2.py:146-158}}).

This runs once per layer and once per {{term stage}}. With DBO there are two stages per layer. See {{link concepts/dbo}}.

The {{term ffn-server-loop | FFN server loop}} blocks on the control plane for exactly one payload per step ({{cite afd_plugin/v1/worker/ffn_worker.py:176}}), then dispatches to execute or capture ({{cite afd_plugin/v1/worker/ffn_worker.py:182-196}}).

So the control plane runs once per step on the FFN side too, matching the attention side.

The FFN runner builds the {{term ffn-graph-key | FFN graph key}} from the DP metadata and replays the stored graph for a pure-decode step ({{cite afd_plugin/v1/worker/ffn_model_runner.py:166-177}}). If no graph matches the key, it runs eager instead.

See {{link concepts/cuda-graphs}}.

The eager path, _ffn_forward, loops over layers and stages. For each pair it receives the hidden states, runs the FFN or MoE compute, and sends the result back ({{cite afd_plugin/v1/worker/ffn_model_runner.py:222-269}}).

When the FFN side replays a graph, this same work is recorded in the graph instead of run step by step. See {{link concepts/ffn-runtime}}.

After the forward pass, the worker makes a separate native call, sample_tokens ({{cite vllm:vllm/v1/worker/gpu_worker.py:1142-1147}}). Native Model Runner V2 computes the logits and samples there ({{cite vllm:vllm/v1/worker/gpu/model_runner.py:2048-2050}}). The AFD attention runner does not override this method, so it samples natively.

The FFN runner has no sampler; its sample_tokens raises ({{cite afd_plugin/v1/worker/ffn_model_runner.py:405-406}}). So sampling runs once per step, on the attention side. The step is done; the next step repeats the whole path.

What can go wrong

  • Folding the per-step publish into the layer loop. The control plane publishes once, before the layers; it does not publish again inside the loop ({{cite afd_plugin/v1/worker/attention_metadata.py:115-116}}).
  • A shape that no captured graph covers. The FFN side runs that step eager instead of replaying ({{cite afd_plugin/v1/worker/cuda_graph.py:148-150}}).
  • A step too small for DBO. A step below the threshold runs as one stage, with no overlap ({{cite vllm:vllm/v1/worker/ubatch_utils.py:144-149}}).
  • Expecting the FFN side to sample. It never does; its sample_tokens raises ({{cite afd_plugin/v1/worker/ffn_model_runner.py:405-406}}).

Why it matters. One step has one control-plane publish, then every layer and stage of send and receive, then one sampling call. The frequencies must not be mixed, or the two roles fall out of step.

How many times does the control plane publish per step?

Once, before the layer loop. The attention side sends one DP-metadata payload ({{cite afd_plugin/v1/worker/attention_metadata.py:115-116}}); the FFN loop receives one ({{cite afd_plugin/v1/worker/ffn_worker.py:176}}).

 What does the FFN runner do when a graph matches the key?

It calls graph.replay() and returns, instead of running the layers eager ({{cite afd_plugin/v1/worker/ffn_model_runner.py:175-177}}).

 In a DBO step, why does the FULL replay hook not send a new control payload?

Because the ubatch prepare seam already sent the full two-stage payload. The hook asserts the staged metadata and delegates to the native replay ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:275-280}}).

 Which side samples the token, and when?

The attention side, once per step, after the last layer. The AFD runner inherits the native sample_tokens ({{cite vllm:vllm/v1/worker/gpu/model_runner.py:2048-2050}}); the FFN runner's raises ({{cite afd_plugin/v1/worker/ffn_model_runner.py:405-406}}).

 List the per-stage data-plane calls for one layer, in order, across both roles.

Attention send_attn_output ({{cite afd_plugin/model_executor/models/deepseek_v2.py:146}}); DBO yield; FFN recv_attn_output ({{cite afd_plugin/v1/worker/ffn_model_runner.py:236}}); FFN compute; FFN send_ffn_output ({{cite afd_plugin/v1/worker/ffn_model_runner.py:268}}); attention recv_ffn_output ({{cite afd_plugin/model_executor/models/deepseek_v2.py:155}}). This runs for each of the two stages.

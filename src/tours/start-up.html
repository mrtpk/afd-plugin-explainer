The plugin loads, the config patch picks the role worker, the two roles meet at the {{term connector}}, and both sides capture graphs.

The idea

AFD runs two vllm serve processes, one per role, with the same model. Each process loads the {{term plugin}}, which rewrites the worker class for its role. The {{term attention-role | attention}} server comes up like a normal vLLM server. The {{term ffn-role | FFN}} server stops its {{term enginecore | EngineCore}} early and runs a connector loop instead. The two roles then meet at the connector and capture CUDA graphs.

This tour uses the graph recipe for one attention server and one FFN server: 2A2F, DP1, TP2, with DBO and FULL_DECODE_ONLY graphs ({{cite recipe/gpu/P2pNcclAFDConnector/deepseek_v2_lite/prefill_decode_colocation/2a2f_graph_dbo_dp1tp2.sh:7-32}}).

Keep one rule in mind. The two roles start as separate processes and can come up in either order. They synchronize at one point: the collective connector handshake. Everything before it is per-process; the handshake is where the roles meet.

The picture

The two diagrams split the start-up in half. The first follows the attention server; the second follows the FFN server. Read each top to bottom.

Each role is a separate vllm serve command with its own {{term additional-config | --additional-config}}. The only difference between the two in this recipe is role ({{cite recipe/gpu/P2pNcclAFDConnector/deepseek_v2_lite/prefill_decode_colocation/2a2f_graph_dbo_dp1tp2.sh:11-19}}).

Both commands set VLLM_USE_V2_MODEL_RUNNER=1 ({{cite recipe/gpu/P2pNcclAFDConnector/deepseek_v2_lite/prefill_decode_colocation/2a2f_graph_dbo_dp1tp2.sh:5}}). AFD needs the V2 model runner on. See {{link concepts/worker-selection}}.

vLLM loads general plugins at the start of add_cli_args, in the launch process ({{cite vllm:vllm/engine/arg_utils.py:3009}}), and again when EngineArgs is built ({{cite vllm:vllm/engine/arg_utils.py:839}}). Both run in process 0 only. The loader has a once-per-process guard, so repeat calls are cheap ({{cite vllm:vllm/plugins/__init__.py:82-85}}).

The plugin entry point is afd = "afd_plugin:register_afd" ({{cite pyproject.toml:45-46}}). The loader calls it. See {{link learn/vllm-plugins}}.

register_afd runs once per process. It checks the vLLM version (warn only), imports the four patch modules, registers the routing strategy and the DBO op, and registers the AFD model wrappers ({{cite afd_plugin/__init__.py:142-216}}).

The patch imports install the {{term patch | compat patches}} at import time, behind the {{term version-gate | version gate}}. One of them, config_validation, is what rewrites the worker class next. See {{link concepts/compat-patches}}.

When vLLM builds the engine config, the patched create_engine_config runs. It rewrites worker_cls to the AFD role worker, but only when the value was "auto" ({{cite afd_plugin/compat/patches/config_validation.py:60}}, {{cite afd_plugin/compat/patches/config_validation.py:92-93}}).

The attention role gets AFDAttentionWorker; the FFN role gets AFDFFNWorker ({{cite afd_plugin/validation.py:290-291}}). See {{link concepts/worker-selection}}.

The {{term enginecore | EngineCore}} process builds the model executor. For an FFN config, the patched __init__ returns right after that, so it sets up no scheduler and no KV cache ({{cite afd_plugin/compat/patches/engine_core.py:56-68}}).

The FFN path sets zero GPU and CPU blocks and installs a no-op scheduler, which is not None so the native readiness handshake still works ({{cite afd_plugin/compat/patches/engine_core.py:605-614}}). The attention EngineCore is unchanged.

Each worker process loads the plugin again before the worker class is resolved ({{cite vllm:vllm/v1/worker/worker_base.py:271}}), then resolves the class ({{cite vllm:vllm/v1/worker/worker_base.py:273-277}}). The guard makes the repeat load a no-op.

In init_device, the AFD worker validates the stack, then swaps the native runner class for the AFD runner while native construction runs ({{cite afd_plugin/v1/worker/attention_worker.py:82-87}}).

The FFN worker does the same swap for GPUFFNModelRunner ({{cite afd_plugin/v1/worker/ffn_worker.py:93-98}}). See {{link concepts/worker-selection}}.

The attention runner loads the model, then initializes the connector at the end of load_model, so attention and FFN weight loading overlap ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:454-462}}).

The connector itself is built earlier, in the runner constructor ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:384-390}}). Only the rendezvous is deferred.

init_afd_connector is a collective call: every attention and FFN rank runs it, and the two roles meet here ({{cite afd_plugin/connectors/base.py:124}}). The P2P connector builds its process groups at a {{term rendezvous}} on the configured host and port ({{cite afd_plugin/connectors/gpu/p2p.py:245-276}}).

Either role can reach this point first. The group setup blocks until both roles arrive, or until the timeout ({{cite afd_plugin/connectors/gpu/p2p.py:271}}). See {{link concepts/topology}}.

init_afd_connector builds three groups ({{cite afd_plugin/connectors/gpu/p2p.py:245-316}}):

  1. The AFD world group, named "afd". It holds every attention and FFN rank. Its timeout is afd_process_group_timeout_s, 120 seconds by default ({{cite afd_plugin/connectors/gpu/p2p.py:269-276}}).
  2. The control group, named "p2p". It holds the FFN ranks and the first min_size attention ranks, with a fixed 30-minute timeout ({{cite afd_plugin/connectors/gpu/p2p.py:306-314}}).
  3. The data-plane subgroups. Each FFN rank and its attention peers share one subgroup, built on a PrefixStore over the world rendezvous, with a 300-second timeout ({{cite afd_plugin/connectors/gpu/p2p.py:278-304}}).

The subgroups reuse the world's rendezvous store, so they need no port of their own ({{cite afd_plugin/connectors/gpu/p2p.py:280-288}}). See {{link concepts/topology}}.

Only the attention side owns a KV cache. The FFN worker returns an empty KV spec, so vLLM allocates no FFN blocks ({{cite afd_plugin/v1/worker/ffn_worker.py:102-105}}). The FFN worker then joins the connector and starts its loop instead of allocating a cache ({{cite afd_plugin/v1/worker/ffn_worker.py:107-113}}).

The attention runner allocates its KV cache as usual, with a scoped seam that enables DP1 DBO ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:473-486}}). See {{link concepts/roles}}.

The attention runner wraps native capture_model to publish warm-up and capture control for each FULL descriptor ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:509-553}}). The FFN worker performs no warm-up of its own ({{cite afd_plugin/v1/worker/ffn_worker.py:115-120}}); its graphs are captured from the server loop when the warm-up and capture payloads arrive ({{cite afd_plugin/v1/worker/ffn_worker.py:182-189}}).

So graph capture is driven by the attention side and mirrored on the FFN side. See {{link concepts/cuda-graphs}}.

The FFN EngineCore busy loop starts the worker loop with a collective RPC ({{cite afd_plugin/compat/patches/engine_core.py:650-659}}). The worker starts a daemon thread, the {{term ffn-server-loop | FFN server loop}} ({{cite afd_plugin/v1/worker/ffn_worker.py:133-158}}).

The loop blocks on the control plane for the first payload. The FFN server is now driven by the attention side ({{cite afd_plugin/v1/worker/ffn_worker.py:168-176}}). See {{link code/ffn-worker}}.

Both servers are up. The attention API server accepts requests; the FFN server runs its loop. The {{link tours/life-of-a-request}} tour follows one request from here, and {{link tours/one-decode-step}} follows one step in detail.

What can go wrong

  • A host or port mismatch. The two roles meet at the same rendezvous. Different values make the handshake block until the timeout ({{cite afd_plugin/connectors/gpu/p2p.py:271-276}}).
  • An explicit non-AFD worker. The config patch rewrites worker_cls only when it was "auto"; an explicit non-AFD worker is rejected later ({{cite afd_plugin/validation.py:357-367}}).
  • A mismatched vLLM. On a non-matching, non-dev vLLM the install gate skips the patches, so worker_cls is never rewritten and AFD does not take effect ({{cite afd_plugin/compat/vllm.py:53-68}}).
  • V2 runner off. AFD needs the V2 model runner on; the validator raises when V2 resolves to off ({{cite afd_plugin/validation.py:90-91}}). The recipes set the env variable ({{cite recipe/gpu/P2pNcclAFDConnector/deepseek_v2_lite/prefill_decode_colocation/2a2f_graph_dbo_dp1tp2.sh:5}}).

Why it matters. The two roles start apart and meet once, at the connector handshake. If the patches do not install, or the roles do not meet, start-up cannot complete.

What is the only difference between the two vllm serve commands in this recipe?

The role field in the AFD config: one is attention, one is ffn ({{cite recipe/gpu/P2pNcclAFDConnector/deepseek_v2_lite/prefill_decode_colocation/2a2f_graph_dbo_dp1tp2.sh:13}}, {{cite recipe/gpu/P2pNcclAFDConnector/deepseek_v2_lite/prefill_decode_colocation/2a2f_graph_dbo_dp1tp2.sh:39}}).

 Why does the FFN EngineCore not set up a scheduler or KV cache?

For an FFN config it returns right after the executor is built; it runs a connector loop instead ({{cite afd_plugin/compat/patches/engine_core.py:56-68}}).

 The two roles start as separate processes. Where do they synchronize?

At the collective connector handshake, init_afd_connector. Every rank runs it, and the group setup blocks until both roles arrive ({{cite afd_plugin/connectors/base.py:124}}, {{cite afd_plugin/connectors/gpu/p2p.py:269-276}}).

 Why is the attention connector rendezvous deferred to the end of load_model?

So attention and FFN weight loading overlap across the two roles ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:454-462}}).

 The FFN worker does no warm-up of its own. How are its CUDA graphs captured?

The attention side drives capture by sending warm-up and capture control. The FFN server loop reads those payloads and calls capture_model ({{cite afd_plugin/v1/worker/ffn_worker.py:115-120}}, {{cite afd_plugin/v1/worker/ffn_worker.py:182-189}}).

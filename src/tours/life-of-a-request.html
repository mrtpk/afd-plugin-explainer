The idea

A client sends a request to one server. The {{term attention-role | attention}} server owns the API, the scheduler and the {{term enginecore | EngineCore}}. The {{term ffn-role | FFN}} server owns no API for requests; a connector loop drives it. So the whole request path lives on the attention side, and the FFN side answers one piece of each model layer.

This tour uses the simplest GPU recipe: one attention server, one FFN server, and the GPU {{term connector | P2P connector}} ({{cite recipe/gpu/P2pNcclAFDConnector/deepseek_v2_lite/prefill_decode_colocation/2a2f_eager_dbo_dp1tp2.sh:7-29}}). Each server runs two ranks (--tensor-parallel-size 2), so the topology is 2A2F. Rank A0 maps to rank F0 ({{cite afd_plugin/distributed/topology.py:135-136}}). We follow A0 and F0.

Keep one timing rule in mind. The {{term control-plane | control plane}} publishes {{term dp-metadata}} once per step, before the layer loop. The {{term data-plane | data plane}} sends tensors once per layer and {{term stage}}. With {{term dbo | DBO}} there are two stages per layer.

Some recipes start tools/proxy_server.py, a load-balance proxy copied from vLLM-Ascend ({{cite tools/proxy_server.py:1}}). It splits prefill and decode across servers in the 2p1a1f recipes ({{cite recipe/gpu/P2pNcclAFDConnector/deepseek_v2_lite/prefill_decode_disaggregation/2p1a1f_eager_dbo.sh:110-118}}). It is not part of the attention/FFN split, and this tour does not use it.

A client sends an HTTP request to the attention server. Clients must send requests only there. The FFN server is connector-driven ({{cite README.md:258-260}}).

The API server is native vLLM ({{cite vllm:vllm/entrypoints/openai/api_server.py | api_server.py}}). AFD changes nothing here. The request now enters the engine.

The attention server's {{term enginecore | EngineCore}} and scheduler are native vLLM ({{cite vllm:vllm/v1/engine/core.py | v1/engine/core.py}}). The scheduler puts the request into a step and calls the executor.

The FFN server has no such loop for requests. Its worker runs a connector loop instead ({{cite afd_plugin/v1/worker/ffn_worker.py:32-38}}). So the scheduler lives on the attention side only. See {{link concepts/roles}}.

This is the first plugin code on the path. The {{term worker-cls | worker_cls}} was rewritten to the AFD attention worker at start-up, so the native executor now builds and calls AFDAttentionWorker. Its init_device checks the stack, then constructs the AFD runner ({{cite afd_plugin/v1/worker/attention_worker.py:60-88}}).

The worker validates the role and the runner config ({{cite afd_plugin/v1/worker/attention_worker.py:64-73}}), then substitutes AFDAttentionModelRunnerV2 for the native runner class while the native setup runs ({{cite afd_plugin/v1/worker/attention_worker.py:82-87}}). See {{link concepts/worker-selection}}.

For each step, the executor calls the runner's execute_model. The AFD runner does not copy the native method. It wraps it in an AFD execution context, then delegates ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:570-594}}).

Native execute_model still does all the request, attention, KV and sampling work. The wrapper only installs AFD state around it ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:555-568}}).

The context sets up two things that matter for AFD: a metadata provider that binds AFD metadata to the forward context, and, for DBO, a prepare seam on the ubatch runner ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:317-349}}).

The metadata provider is install_afd_metadata_on_forward_context ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:345-347}}). It runs when native code builds the forward context, and it is where the control plane publish happens. See {{link concepts/attention-runtime}}.

Before the layer loop, the attention side sends the {{term dp-metadata | DP metadata}} to the FFN side. The prepare seam calls send_dp_metadata once ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:156-157}}). That call updates the local control state, then sends one payload ({{cite afd_plugin/v1/worker/attention_metadata.py:115-116}}).

This payload is the first thing that crosses the connector each step. It carries the per-stage token counts that set the tensor shapes. See {{link concepts/control-plane}}.

Accuracy note from the fact checks: a per-step call must not be folded into the per-layer sequence. The publish runs before any layer sends data.

There are two paths to the same publish. With DBO, the ubatch prepare seam calls send_dp_metadata after it slices the step into stages ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:153-157}}). Without ubatching, the metadata provider calls it from install_afd_metadata_on_forward_context ({{cite afd_plugin/v1/worker/attention_metadata.py:252-257}}). Either way, one publish per step, before the layer loop.

The FFN side waits for exactly one payload per step. Its server loop calls recv_dp_metadata_list once ({{cite afd_plugin/v1/worker/ffn_worker.py:176}}), then applies it ({{cite afd_plugin/v1/worker/ffn_model_runner.py:194-203}}).

Native execute_model runs the model forward. The AFD {{term model-wrapper | model wrapper}} subclasses the native model, so the attention of each layer runs locally. Only the FFN stage of each layer is replaced ({{cite afd_plugin/model_executor/models/deepseek_v2.py:117-125}}).

The replacement is a {{term remote-ffn-proxy | RemoteFFNProxy}}. It holds no weights. Its forward sends and receives through the connector instead of computing the FFN. The loop over layers is native vLLM.

Inside each layer, the proxy sends its hidden states to the FFN side, then waits for the result. This runs once per layer, and once per {{term stage}} ({{cite afd_plugin/model_executor/models/deepseek_v2.py:127-158}}).

The call to send_attn_output ({{cite afd_plugin/model_executor/models/deepseek_v2.py:146}}) is the hidden-state tensor crossing the connector (the data plane). The matching recv_ffn_output comes later in the same call ({{cite afd_plugin/model_executor/models/deepseek_v2.py:155}}).

The tensor is hidden_states of shape [num_tokens, hidden_size] in the model dtype ({{cite afd_plugin/connectors/gpu/p2p.py:331-335}}). The transfer metadata records the layer index, the stage index and the sequence lengths ({{cite afd_plugin/connectors/metadata.py:188-190}}). For DeepSeek-V2-Lite the hidden size is 2048, which is inferred from the checkpoint config. With 8 decode tokens the tensor is [8, 2048]. See {{link concepts/wire-data}}.

The FFN worker runs a daemon thread, the {{term ffn-server-loop | FFN server loop}}. No scheduler drives it. The loop waits for one DP-metadata payload, then runs the model ({{cite afd_plugin/v1/worker/ffn_worker.py:160-196}}).

If the native scheduler ever calls the FFN worker's execute_model, it raises at once, so a misrouted request fails fast ({{cite afd_plugin/v1/worker/ffn_worker.py:122-131}}). The GPU FFN side also needs a control plane; a connector without one is rejected here ({{cite afd_plugin/v1/worker/ffn_worker.py:169-174}}).

_ffn_forward loops over the layers, and over the stages inside each layer. For each pair it receives the hidden states, runs the FFN or MoE compute, and sends the result back ({{cite afd_plugin/v1/worker/ffn_model_runner.py:222-269}}).

  1. Line 236. recv_attn_output returns the hidden states and the transfer context ({{cite afd_plugin/v1/worker/ffn_model_runner.py:236}}).
  2. Line 263. _execute_eager_mode runs the FFN and MoE for this layer ({{cite afd_plugin/v1/worker/ffn_model_runner.py:263}}).
  3. Line 268. send_ffn_output sends the result back to the attention side ({{cite afd_plugin/v1/worker/ffn_model_runner.py:268}}).

Back on the attention side, recv_ffn_output returns the FFN result into the proxy's output ({{cite afd_plugin/model_executor/models/deepseek_v2.py:155-158}}). The native layer then adds the residual and goes to the next layer.

Stops 8 to 11 repeat for every decoder layer. With DBO they repeat for both stages of each layer. The control plane does not publish again inside this loop.

After the last layer, native execute_model computes the logits and samples the token. The AFD runner delegated all of this to native vLLM ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:586-594}}). So sampling runs on the attention side.

The FFN runner has no sampler; its sample_tokens raises ({{cite afd_plugin/v1/worker/ffn_model_runner.py:405-406}}). The attention server returns the token to the client over the same HTTP response. The request is done for this step.

The loop

One request is many steps. Prefill runs one step for the prompt. Then decode runs one step per new token. Each step runs the whole path again: one control-plane publish, then every layer and stage of send and receive.

What can go wrong

  • Requests sent to the FFN server. The FFN worker is connector-driven. A scheduler-driven execute_model raises at once ({{cite afd_plugin/v1/worker/ffn_worker.py:122-131}}).
  • A connector with no control plane on GPU. The GPU FFN loop supports only control-plane-driven connectors, and raises otherwise ({{cite afd_plugin/v1/worker/ffn_worker.py:169-174}}).
  • A shape that does not match the metadata. The send call checks the leading dimension against the token count, and raises when it differs (skipped while torch.compile traces) ({{cite afd_plugin/connectors/gpu/p2p.py:347-353}}).
  • A host or port mismatch between the two servers. Both roles meet at the same {{term rendezvous}} ({{cite afd_plugin/connectors/gpu/p2p.py:271}}). Different values make the group setup hang until the timeout ({{cite afd_plugin/connectors/gpu/p2p.py:275}}).

Why it matters. The attention side owns the request, and the FFN side answers only pieces of each layer. If a request reaches the FFN server, or the two roles do not meet, the step cannot complete.

Which server do clients send requests to, and why not the other one?

The attention API server. The FFN server is connector-driven and has no request path; a scheduler-driven FFN execute_model fails fast ({{cite README.md:258-260}}, {{cite afd_plugin/v1/worker/ffn_worker.py:122-131}}).

 What drives the model on the FFN server?

A connector-driven daemon loop, the FFN server loop, not a scheduler. It waits for DP metadata, then runs the model ({{cite afd_plugin/v1/worker/ffn_worker.py:160-196}}).

 How many times does the control plane publish per step, and when?

Once, before the layer loop. The attention side sends one DP-metadata payload ({{cite afd_plugin/v1/worker/attention_metadata.py:115-116}}); the FFN loop receives one ({{cite afd_plugin/v1/worker/ffn_worker.py:176}}).

 Which side samples the token?

The attention side. Native execute_model computes the logits and samples ({{cite afd_plugin/v1/worker/attention_model_runner_v2.py:586-594}}). The FFN runner's sample_tokens raises ({{cite afd_plugin/v1/worker/ffn_model_runner.py:405-406}}).

 List the data-plane calls for one layer and stage, in order, across both servers.

Attention send_attn_output ({{cite afd_plugin/model_executor/models/deepseek_v2.py:146}}); FFN recv_attn_output ({{cite afd_plugin/v1/worker/ffn_model_runner.py:236}}); FFN compute; FFN send_ffn_output ({{cite afd_plugin/v1/worker/ffn_model_runner.py:268}}); attention recv_ffn_output ({{cite afd_plugin/model_executor/models/deepseek_v2.py:155}}). The data plane runs once per layer and stage; the control plane ran once before the loop.

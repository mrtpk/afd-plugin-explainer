How the plugin uses the environment

Most AFD settings go through --additional-config (see {{link reference/afd-config}}). A smaller set of settings comes from environment variables. The plugin uses them for build-time choices, the profilers, the Ascend operator loader, the benchmark routing strategy, and a few runtime switches. The AFD config values do not change these; you set them in the shell.

The table below is generated from the source, so the names, defaults and lines stay correct at the pinned commit. Run python3 tools/gen_env_vars.py to refresh it. The generator parses the Python with ast only; it never imports the plugin or vLLM.

What each group does

The generated table gives the default and the read site. This section gives the effect, with a citation. The variables fall into five groups.

  • AFD_FORCE_SPAWN_MULTIPROCESSING — when set to 1, register_afd forces the spawn multiprocessing start method at import and at registration ({{cite afd_plugin/__init__.py:55-62}}). AFD needs separate processes per role, so the start method matters. See {{link concepts/plugin-entry-point}}.

These run at install time, when you build the plugin. They decide whether to build the Ascend operators and how. They have no effect on a running server.

  • AFD_BUILD_ASCEND_OPS — forces the Ascend operator build on or off. When unset, the build auto-detects an Ascend platform ({{cite setup.py:43-54}}).
  • AFD_SKIP_ACLNN_BUILD — when not 1, the build runs csrc/npu/build_aclnn.sh ({{cite setup.py:66-71}}).
  • SOC_VERSION — the Ascend SoC version passed to the operator build; default 910c ({{cite setup.py:67}}, {{cite setup.py:88}}).
  • CMAKE_BUILD_TYPE — the CMake build type; default Release ({{cite setup.py:85}}).
  • ASCEND_HOME_PATH, TORCH_NPU_PATH — passed to CMake when set ({{cite setup.py:98-101}}); also two of the four variables that mark an Ascend platform ({{cite setup.py:18-23}}, {{cite setup.py:38}}).
  • ASCEND_OPP_PATH, ASCEND_TOOLKIT_HOME — the other two platform markers ({{cite setup.py:18-23}}, {{cite setup.py:38}}).
  • MAX_JOBS — the parallel build job count; defaults to the CPU count ({{cite setup.py:104}}).

The plugin owns a torch profiler for each GPU runner role and each NPU runner role. Each family has its own prefix: AFD_GPU_ATTENTION_PROFILER, AFD_GPU_FFN_PROFILER, AFD_NPU_ATTENTION_PROFILER, AFD_NPU_FFN_PROFILER. The suffix picks the setting (_ENABLE, _WAIT, _WARMUP, _ACTIVE, _REPEAT, _SKIP_FIRST, _DIR; the NPU profiler adds _WITH_STACK). The GPU profiler reads them in afd_gpu_profiler_config ({{cite afd_plugin/compat/profiler.py:46-61}}); the NPU profiler in afd_npu_profiler_config ({{cite afd_plugin/compat/npu/profiler.py:52-70}}).

  • ..._ENABLE — turns the profiler on for that role; default off. Only when it is on does the plugin build a torch profiler ({{cite afd_plugin/compat/profiler.py:64-96}}).
  • ..._WAIT, ..._WARMUP, ..._ACTIVE, ..._REPEAT, ..._SKIP_FIRST — the torch profiler schedule ({{cite afd_plugin/compat/profiler.py:83-89}}).
  • ..._DIR — the trace output directory. When unset, the plugin falls back to VLLM_TORCH_PROFILER_DIR, then to the per-role default ({{cite afd_plugin/compat/profiler.py:131-132}}).
  • ..._WITH_STACK (NPU only) — records Python stacks in the trace ({{cite afd_plugin/compat/npu/profiler.py:69}}).
  • AFD_BENCHMARK_FORCE_LB_TOPN_PER_RANK — limits the local expert pool per EP rank in the {{term afd-balanced}} routing strategy; 0 selects all local experts ({{cite afd_plugin/model_executor/routing_simulator.py:125-127}}). It changes model outputs, so it is for benchmark runs only. See {{link concepts/tuning}}.
  • AFD_FORCE_BALANCED_TOPK_IDS — a runtime switch for balanced top-k expert ids ({{cite afd_plugin/envs.py:14-15}}).

These matter only on an Ascend NPU. The {{link concepts/npu-overview}} page covers the NPU path.

  • BATCH_SIZE_FACTOR — multiplies the CAM receive capacity (262144 × factor, with native float rounding), and marks the async FFN graph capacity ({{cite afd_plugin/validation.py:45-54}}, {{cite afd_plugin/compat/npu/feature_validation.py:245-249}}). Default 1.
  • AFD_CUST_OPAPI_LIB_PATH — the loader sets this to the plugin's custom op-API library path when it exists ({{cite afd_plugin/compat/npu/ops.py:52-54}}).
  • ASCEND_CUSTOM_OPP_PATH, LD_LIBRARY_PATH — the loader prepends the plugin's vendor paths to these ({{cite afd_plugin/compat/npu/ops.py:43-54}}).
  • AFD_ASYNC_CAM_LAYERED_GMM — selects the layered GMM path for the async CAM connector ({{cite afd_plugin/envs.py:18-19}}).
  • AFD_CAM_OP_IO_LOG, AFD_ASYNC_MOE_LAYOUT_LOG — diagnostic logging switches ({{cite afd_plugin/connectors/npu/async_cam.py:955}}, {{cite afd_plugin/model_executor/models/npu/async_cam_layout.py:187}}).
  • VLLM_ASCEND_ENABLE_FLASHCOMM1 — a vLLM-Ascend switch the plugin reads to gate a feature path ({{cite afd_plugin/compat/npu/feature_validation.py:188-191}}, {{cite afd_plugin/connectors/npu/async_cam.py:425-428}}).

vLLM variables that AFD depends on

These variables belong to vLLM, not to the plugin, but AFD needs them set correctly. The recipes set the first one.

VariableWhy AFD needs itSource (vLLM)
VLLM_USE_V2_MODEL_RUNNER AFD runs on Model Runner V2. The validator raises when V2 resolves to off ({{cite afd_plugin/validation.py:90-91}}). When the variable is unset, vLLM still picks V2 by default; the recipes set it to 1 to be explicit. {{cite vllm:vllm/envs.py:2037-2038}}, {{cite vllm:vllm/config/vllm.py:692-694}}
VLLM_PLUGINS vLLM's plugin loader filters by this list. AFD loads only when afd is in the list, or the variable is unset ({{cite vllm:vllm/plugins/__init__.py:64}}). An empty string loads no plugin. {{cite vllm:vllm/envs.py:1146-1150}}
VLLM_MOE_ROUTING_SIMULATION_STRATEGY Selects a routing strategy. Set it to afd_balanced to use the plugin's deterministic benchmark routing ({{cite afd_plugin/model_executor/routing_simulator.py:5-8}}). {{cite vllm:vllm/envs.py:1743-1745}}
VLLM_TORCH_PROFILER_DIR The plugin profilers fall back to this directory for traces when the per-role ..._DIR is unset ({{cite afd_plugin/compat/profiler.py:131-132}}). Not declared in vLLM v0.30.0 (see note).

The plugin reads VLLM_TORCH_PROFILER_DIR as a fallback trace directory ({{cite afd_plugin/compat/profiler.py:132}}, {{cite afd_plugin/compat/npu/profiler.py:149}}). At the pinned vLLM commit this name does not appear in vllm/envs.py. The plugin reads it with a plain os.getenv, so an unset value simply means the per-role default is used.

v1/worker: the FFN worker and runner

AdvancedCode mapabout 4 min read + 1 min deep dives

Code version: afd-plugin @ 7452d52 · 2026-10-27 · vLLM @ ced6857

Before you read

This page uses ideas from these pages:

  • The FFN runtime: a connector-driven server loop Advanced

In one sentence

The FFN role is a native vLLM worker that starts a daemon loop, a stand-alone runner driven by the control plane, and small token-count helpers.

Purpose#

These three files run the FFN side with no real scheduler (a no-op stand-in) and no KV cache. The concept is on The FFN runtime: a connector-driven server loop; this page maps the files.

Where it sits#

Who calls it#

The AFD config patch rewrites worker_cls to AFDFFNWorker when the role is FFN (afd_plugin/validation.py:280-296). The FFN EngineCore returns after the executor is built, so no scheduler drives this worker; the loop is driven by the control plane instead (afd_plugin/v1/worker/ffn_worker.py:133-158).

What it calls#

The worker swaps the runner class and delegates to native Worker.init_device (afd_plugin/v1/worker/ffn_worker.py:73-100). The runner builds the connector (afd_plugin/connectors/factory.py:49-68) and calls the model wrapper's compute_ffn_output or compute_experts_output.

Walk through the main methods#

_run_ffn_server_loop: one step per control payload#

The loop runs until the shutdown event is set. Each pass reads one DP-metadata payload, then dispatches to capture or execute (afd_plugin/v1/worker/ffn_worker.py:160-199).

  1. Lines 169-174. A connector with control_plane None raises; the GPU FFN needs one.
  2. Line 176. One recv_dp_metadata_list per step.
  3. Lines 182-189. Warm-up or graph capture calls capture_model.
  4. Lines 190-196. Otherwise execute_model runs the step; then the loop synchronizes.

_ffn_forward: layers x stages#

The forward sets the layer set from the gate flag, then loops layers and stages (afd_plugin/v1/worker/ffn_model_runner.py:207-269).

  1. Line 236. recv_attn_output returns the hidden states and the context.
  2. Lines 251-261. An attention-side-gate expert layer calls compute_experts_output.
  3. Lines 262-267. Any other layer calls compute_ffn_output through _execute_eager_mode.
  4. Line 268. send_ffn_output sends the result back.

aggregate_ffn_token_counts: attention counts to FFN ranks#

Each FFN rank sums the contiguous block of attention ranks mapped to it (afd_plugin/v1/worker/ffn_metadata.py:15-60). Every attention peer contributes at least one row, so a zero-token peer still adds a placeholder.

Deep dive#

Deep dive

Why the worker and runner both reject a no-control-plane connector

The GPU FFN path supports only control-plane-driven connectors. The runner asserts it at construction (afd_plugin/v1/worker/ffn_model_runner.py:87-89), and the loop re-checks it each pass (afd_plugin/v1/worker/ffn_worker.py:169-174). The async NPU connector sets control_plane = None and drives the FFN side through its own receive loop; that path is on Ascend NPU overview: the same contract, different transports.

Check yourself#

  1. 1
    What does sample_tokens do on the FFN runner?
    easy
    Show answer

    It raises; the FFN role never samples (afd_plugin/v1/worker/ffn_model_runner.py:405-406).

  2. 2
    What starts the FFN server loop, and on what kind of thread?
    medium
    Show answer

    initialize_from_config calls start_ffn_server_loop, which starts a daemon thread (afd_plugin/v1/worker/ffn_worker.py:107-113, afd_plugin/v1/worker/ffn_worker.py:153-158).

  3. 3
    On 3A2F, why does a zero-token attention peer still add a row to its FFN rank's count?
    hard
    Show answer

    aggregate_ffn_token_counts takes max(1, count) per peer, so every peer contributes at least one placeholder row; F0 sums the block {A0, A1} and F1 the block {A2} (afd_plugin/v1/worker/ffn_metadata.py:49-60).

AFD Plugin Explained

Code version: afd-plugin @ 7452d52 · 2026-10-27 · vLLM @ ced6857

afd-plugin is a vLLM external plugin for AFD. The attention part and the feed-forward (FFN/MoE) part of a model run in two separate server processes, and a connector moves hidden states between them. The plugin adds its own worker classes, model runners, model wrappers, connectors, config validation and compatibility patches, and it changes no vLLM source file (README.md:9-13, README.md:21-24). This site explains the plugin code at commit 7452d52, and the vLLM code it builds on at commit ced6857. You need to know Python and the basics of LLM serving.

At a glance#

What it isA vLLM external plugin for Attention-FFN Disaggregation (AFD) (README.md:9-13).
Runs onNVIDIA CUDA GPU and Ascend NPU (README.md:11-13). This site explains the GPU paths in full; one page, Ascend NPU overview: the same contract, different transports, covers the NPU.
TargetsvLLM v0.30.0 at commit ced6857 (README.md:21, pyproject.toml:37). Other vLLM versions are not supported on GPU (README.md:69-70).
ModelsDeepSeek V2 / V3 / V3.2 / V4, GLM-MoE-DSA, Qwen3-MoE, and one Qwen3.5-MoE architecture, Qwen3_5MoeForConditionalGeneration (the README lists this one under "Qwen3.5 / Qwen3.6 MoE"). The code registers eight architectures, each under an AFD-prefixed name (afd_plugin/__init__.py:96-131, README.md:47-51).
ConnectorsThree: P2pNcclAFDConnector (CUDA), CAMP2pAFDConnector and CAMAsyncAFDConnector (both NPU) (afd_plugin/connectors/factory.py:88-102).
Code sizeAbout 20,195 lines of Python in afd_plugin/, across 78 files. The C/C++ kernels in csrc/ are out of scope. See The code map: folders, sizes and dependencies for the breakdown and the method.
How to runStart two vllm serve processes, one for each role, and give each one --additional-config '{"afd":{ ... }}'. Send requests only to the attention API server (README.md:218-240, README.md:258-260).

The system map#

One decode step runs left to right, then back. The attention server computes attention and hands its hidden states to the FFN server through the connector. Simplified

The map shows one decode step on a simple one-attention, one-FFN topology. It leaves out data parallelism, the per-peer split and concatenation, DBO (two stages per layer) and the CUDA graph replay. The connector runs once per model layer, not once per step. The tours and the concept pages give the full detail.

What is not in this release#

This site has limits of scope, and the plugin itself states limits.

Out of the site's scope.

  • The C/C++ kernel sources in csrc/. The site explains only how the Python code selects, builds, loads and calls them.
  • The Ascend NPU code, except the one overview page Ascend NPU overview: the same contract, different transports. Other pages name the NPU variant in one line only.
  • The tests. They are a source of facts, not a page topic.

What the repository calls experimental or limited.

  • The project is experimental and needs more large-scale testing (README.md:17-19).
  • The GPU target is exactly vLLM 0.30.0; other versions are not supported on GPU (README.md:69-70).
  • GPU CUDA graphs are limited to FULL_DECODE_ONLY (README.md:86).
  • Native DBO is limited to exactly two ubatches (README.md:87).
  • Qwen3-MoE rejects attention-side gate placement, sequence-parallel MoE, EPLB, pipeline parallelism, speculative decoding, LoRA and NPU (README.md:91-92).
  • The GPU and NPU end-to-end tests are opt-in and need real hardware and model weights (README.md:85).

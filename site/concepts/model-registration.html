Model registration: the AFD<arch> wrappers

IntermediateAFD conceptsabout 4 min read + 1 min deep dives

Code version: afd-plugin @ 7452d52 · 2026-10-27 · vLLM @ ced6857

Before you read

This page uses ideas from these pages:

  • The plugin entry point: register_afd Intermediate

In one sentence

AFD registers each supported model under an AFD<arch> name. At build time it swaps the model config to that AFD identity.

The idea#

AFD needs a role-aware version of each model, so the attention side can replace the FFN stage with a remote proxy. It supplies one AFD<arch> class per architecture. It registers these classes with vLLM's ModelRegistry, as lazy "module:Class" strings, so vLLM imports a class only when it is needed.

The model config names a plain architecture, for example DeepseekV2ForCausalLM. At build time, the AFD worker swaps that name to AFDDeepseekV2ForCausalLM, so vLLM builds the AFD class instead of the native one. The swap copies the config, so the native config is left unchanged.

An everyday comparison. Think of a catalogue with an "AFD" edition of each item. You order by the plain name; the clerk swaps in the AFD edition. The comparison stops here: the swap keeps one hidden link intact, so vLLM Ascend can still tell a text model from a multimodal one.

The picture#

Read panel 1 as load time: register the names. Read panel 2 as build time: detect and swap the identity. Read panel 3 as the exact mappings. The Model wrappers: the role-aware decoder layer page shows what the wrappers do inside.

In the code#

Step 1: Register each AFD name#

At the end of register_afd, a loop registers each architecture under the name "AFD" + arch (afd_plugin/__init__.py:211-214). The source map holds eight architectures (afd_plugin/__init__.py:96-139).

Step 2: The lazy "module:Class" form#

The registered value is a string, not a class. vLLM stores it and imports the class only when the model is built (vllm:vllm/model_executor/models/registry.py:1126-1141). So loading the plugin does not import every model file.

Step 3: Detect an AFD model#

has_afd_model_registration returns true when the model's architecture, with any AFD prefix removed, is in the map (afd_plugin/model_executor/models/model_utils.py:16-22). The runtime validator uses it to require a registered AFD model (afd_plugin/validation.py:136-141).

Step 4: Swap the model identity#

get_afd_model_config finds the architecture in the map, deep-copies the model config, and sets its architecture to AFD<arch> (afd_plugin/model_executor/models/model_utils.py:25-46). The worker then uses the returned config (afd_plugin/v1/worker/attention_worker.py:75-80).

Step 5: Which architectures map to which wrapper#

The map registers these exact strings (afd_plugin/__init__.py:96-131).

Deep dive#

Deep dive

Why deepcopy, and the hf_text_config identity

get_afd_model_config does not change the original config. It deep-copies it, then sets the architecture on the copy (afd_plugin/model_executor/models/model_utils.py:43-45).

  • deepcopy keeps the inner aliasing. A code comment states the reason: the pure-text identity hf_text_config is hf_config is kept automatically, because deepcopy preserves aliasing within the copied object graph (afd_plugin/model_executor/models/model_utils.py:39-43).
  • vLLM Ascend reads that identity. It uses the same-object check to tell a text model from a multimodal model. So the swap must not break it.
  • Only the architecture name changes. The rest of the config is the copy of the original (afd_plugin/model_executor/models/model_utils.py:44).
Deep dive

README names a family; the code registers one string

The README names model families loosely. The code registers exact architecture strings.

  • The README lists "Qwen3.5 / Qwen3.6 MoE" (README.md:51), but the code registers one architecture, Qwen3_5MoeForConditionalGeneration (afd_plugin/__init__.py:125-131).
  • get_afd_model_config raises for that architecture when the device type is not cuda (afd_plugin/model_executor/models/model_utils.py:34-38). So Qwen3.5 and Qwen3.6 run on CUDA only.
  • DeepseekV4ForCausalLM resolves to the NPU class or the GPU class, chosen at import by torch_npu (afd_plugin/__init__.py:109-113).

What can go wrong#

  • Model not registered. A model whose architecture is not in the map fails the runtime check: "AFD ModelRunnerV2 requires a registered AFD model" (afd_plugin/validation.py:136-141).
  • Qwen3.5 on NPU. get_afd_model_config raises for a non-CUDA device (afd_plugin/model_executor/models/model_utils.py:34-38).
  • Model file import error. Because the registration is a lazy string, an import error in the model file surfaces when vLLM builds the model, not when the plugin loads (vllm:vllm/model_executor/models/registry.py:1126-1141).

Why it matters. The worker runs an AFD model only after the identity swap. If the architecture is not registered, the swap does nothing and the runtime check stops start-up.

  4. 4

  5. 5
    Why does get_afd_model_config use deepcopy instead of editing the architecture in place?

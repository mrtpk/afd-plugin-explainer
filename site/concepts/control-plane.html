The control plane: DP metadata once per step

AdvancedAFD conceptsabout 6 min read + 2 min deep dives

Code version: afd-plugin @ 7452d52 · 2026-10-27 · vLLM @ ced6857

Before you read

This page uses ideas from these pages:

  • The connector contract: the Attention/FFN transport Intermediate

In one sentence

The control plane sends DP metadata from the attention side to the FFN side. It runs once per step, before the layer loop.

The idea#

The FFN side must know the token count of each stage before it receives any hidden states. The sizes set the shapes of the wire tensors and the receive buffers. The attention side sends these counts once per step, before the layer loop, over the control plane. This is separate from the data plane, which moves the hidden states once per layer and stage.

The payload is small: the per-DP-rank token counts, plus a few flags for graph capture and warm-up. It travels as JSON over a dedicated process group.

An everyday comparison. Think of a manifest sent ahead of a convoy of trucks. The manifest lists how many boxes each truck carries, so the warehouse can set up the right number of bays before the trucks arrive. The comparison stops here: one connector, the async NPU one, carries no manifest at all; its receive loop sizes each transfer as it comes.

The picture#

Read panel 1 as the per-step order: control plane first, then the data-plane layer loop, then sampling. Read panel 2 as the path of one payload from the attention side to the FFN side.

In the code#

Step 1: Once per step, before the layers#

The control plane runs once per step, before the layer loop. On the attention side the publish happens during input preparation, before the model forward (afd_plugin/v1/worker/attention_metadata.py:115-116). On the FFN side the loop receives one payload per step, before it runs any layer (afd_plugin/v1/worker/ffn_worker.py:176). The data plane then runs once per layer and stage inside the forward.

Step 2: What the payload carries#

The payload is an AFDControlPayload: a map from stage index to DP metadata, plus the graph and warm-up flags (afd_plugin/connectors/metadata.py:107-150).

Each stage's DP metadata is an AFDDPMetadata. Its one required field is the per-DP-rank token count, stored as an int32 CPU tensor (afd_plugin/connectors/metadata.py:23-44). This plugin-owned type keeps the wire format decoupled from vLLM's own DP metadata object (afd_plugin/connectors/metadata.py:320-328).

Step 3: The two attention publish paths#

The attention runner publishes the DP metadata on one of two paths, both once per step before the layer loop. For a DBO step, a prepare seam publishes one complete payload before the microbatch threads start (afd_plugin/v1/worker/attention_model_runner_v2.py:153-157).

For a non-DBO step, the metadata is attached to the forward context and sent there (afd_plugin/v1/worker/attention_metadata.py:252-257). Both paths end in the same call, which updates the local state and then sends (afd_plugin/v1/worker/attention_metadata.py:115-116).

Step 4: The wire format and the separate group#

The payload is encoded as compact JSON: only the per-stage token counts and the flags (afd_plugin/connectors/metadata.py:320-346). The send is two messages: a long size tensor, then a uint8 byte tensor (afd_plugin/connectors/metadata.py:376-401).

The GPU connector carries this over a dedicated NCCL process group, the "p2p" group, not the per-subgroup data communicators. The connector owns the group; the control plane uses it (afd_plugin/connectors/gpu/p2p.py:724-733, afd_plugin/connectors/gpu/p2p.py:853-883). Only the designated sender ranks transmit; the rest no-op (afd_plugin/connectors/gpu/p2p.py:870-875).

Step 5: The FFN side receives and derives the shapes#

The FFN loop blocks on recv_dp_metadata_list until its mapped attention sender transmits (afd_plugin/connectors/gpu/p2p.py:885-908). The FFN runner then calls update_state_from_dp_metadata once per step, before the layer loop (afd_plugin/v1/worker/ffn_model_runner.py:194-203).

update_state_from_dp_metadata derives the expected wire-tensor shape for each stage and, in graph mode, preallocates the receive buffers so capture and replay reuse stable addresses (afd_plugin/connectors/gpu/p2p.py:744-851).

Step 6: The async NPU connector has no control plane#

One connector sets control_plane = None: the async NPU connector (afd_plugin/connectors/npu/async_cam.py:283). It has no control plane; its receive loop drives the FFN side instead. See Ascend NPU overview: the same contract, different transports.

Deep dive#

Deep dive

The wire format, field by field

encode_control_payload writes compact JSON with sorted keys (afd_plugin/connectors/metadata.py:320-346). For one stage the fields are:

FieldType on the wireMeaning
num_tokens_across_dp_cpulist of inttokens per DP rank for this stage
max_tokens_across_dp_cpuintthe max over the list
is_graph_capturingboolthe attention side is capturing a graph
is_warmupboola warm-up step, not a real serving step
is_graph_replayingboolthe attention side is replaying a captured graph
is_profileboolan initial memory-profile forward

The transfer is two torch.distributed sends: a one-element long size tensor, then the uint8 object tensor, both staged on the device the caller chooses (afd_plugin/connectors/metadata.py:389-401). The receive reads the size first, then the bytes, and raises when the two messages come from different ranks (afd_plugin/connectors/metadata.py:403-420).

Deep dive

How update_state derives the shapes

On the FFN side, update_state_from_dp_metadata stores the payload, then builds one _TensorMetadata per stage (afd_plugin/connectors/gpu/p2p.py:766-818). It reads each attention peer's token count from the DP metadata, then multiplies by the hidden size:

  • For an FFN rank, one entry per attention peer in the subgroup, plus the concatenated total (afd_plugin/connectors/gpu/p2p.py:776-807).
  • When CUDA graphs are on and the model is not eager, it preallocates the receive buffers, but only while capturing (afd_plugin/connectors/gpu/p2p.py:820-840).

A per-DP count is expanded across its TP peers when the DP metadata covers fewer ranks than the role size (afd_plugin/connectors/gpu/p2p.py:939-962). The Data on the wire: tensors per layer and stage page reads the shapes in full.

Deep dive

Why one sender per FFN rank is enough

The control-plane group is the FFN ranks plus the first min_size attention ranks (afd_plugin/distributed/topology.py:42-43). Each FFN rank f receives from the attention rank at p2p_rank % min_size + ffn_size, which resolves to attention role rank f (afd_plugin/connectors/gpu/p2p.py:902). The DP metadata is the same per-DP-rank token list for every rank, so one sender per FFN rank carries all the FFN rank needs. The Topology and role ranks: the AFD world page shows which ranks are senders.

What can go wrong#

Simplified

This page shows the GPU control plane. The sync NPU connector has a control plane too; the async NPU connector has none (afd_plugin/connectors/npu/async_cam.py:283). See Ascend NPU overview: the same contract, different transports. The page leaves out the graph lifecycle details, which the CUDA graphs in AFD: FULL_DECODE_ONLY on both roles page covers.

  • A GPU connector with no control plane. The GPU FFN loop needs a control-plane-driven connector and raises for one that sets control_plane = None (afd_plugin/v1/worker/ffn_worker.py:169-174).
  • Fragments from different ranks. The receive raises if the size message and the byte message come from different ranks (afd_plugin/connectors/metadata.py:418-419).
  • A stall before the first transfer. The FFN loop blocks on the control plane each step (afd_plugin/connectors/gpu/p2p.py:885-908). If the attention side never publishes, the FFN loop waits.

Why it matters. The DP metadata sets the wire shapes. Without it, the FFN side cannot size its receive buffers, and the per-layer transfers cannot start.

    What is the main content of the payload?

    The per-DP-rank token counts for each stage, as an int32 tensor, plus graph and warm-up flags (afd_plugin/connectors/metadata.py:23-44, afd_plugin/connectors/metadata.py:135-139).

  3. 3
    The attention side has two publish paths. What are they?
    medium
    Show answer

    The DBO prepare seam, which publishes before the microbatch threads start (afd_plugin/v1/worker/attention_model_runner_v2.py:153-157), and the non-DBO forward-context path (afd_plugin/v1/worker/attention_metadata.py:252-257). Both end in the same apply-then-send call (afd_plugin/v1/worker/attention_metadata.py:115-116).

  4. 4
    Which connector has no control plane, and what drives its FFN side then?
    medium
    Show answer

    The async NPU connector, CAMAsyncAFDConnector (afd_plugin/connectors/npu/async_cam.py:283). With no control plane, its receive loop drives the FFN side (afd_plugin/connectors/base.py:56-60).

  5. 5
    On the FFN side, what does update_state_from_dp_metadata do with the payload?
    hard
    Show answer

    It derives the expected wire-tensor shape for each stage from the token counts and the hidden size, and, in graph mode, preallocates the receive buffers while capturing (afd_plugin/connectors/gpu/p2p.py:744-851). It runs once per step before the layer loop (afd_plugin/v1/worker/ffn_model_runner.py:194-203).

Ascend NPU overview: the same contract, different transports

AdvancedAFD conceptsabout 6 min read + 3 min deep dives

Code version: afd-plugin @ 7452d52 · 2026-10-27 · vLLM @ ced6857

Before you read

This page uses ideas from these pages:

  • The connector contract: the Attention/FFN transport Intermediate
  • The control plane: DP metadata once per step Advanced

In one sentence

AFD on Ascend NPU keeps the same attention/FFN split as GPU. Only the connector transport changes.

The idea#

The NPU path is the one place this site covers Ascend code. The attention/FFN contract is the same as on GPU (see The connector contract: the Attention/FFN transport): the attention side sends hidden states, the FFN side runs the experts and sends the result back. What changes is the transport. The NPU has two connectors, both backed by Ascend CAM operators.

  • CAMP2pAFDConnector — synchronous, with a control plane. HCCL carries the hidden states; a smaller Gloo group carries the DP metadata (afd_plugin/connectors/npu/camp2p.py:3-8).
  • CAMAsyncAFDConnector — asynchronous, with control_plane = None. The CAM dispatch/combine operators carry the routing metadata, so a separate control plane is not needed (afd_plugin/connectors/npu/async_cam.py:277-283).

Simplified

This page explains how the Python code selects, loads and drives the NPU operators and runners. It does not cover the CAM kernel internals or the vendored binaries, which are out of scope (afd_plugin/connectors/npu/bin/).

The picture#

Read the panels top to bottom. Panel 1 is the shared contract. Panel 2 is the synchronous connector, which keeps a control plane. Panel 3 is the asynchronous connector, where the receive loop itself drives each FFN layer.

In the code#

Step 1: CAMP2p, the synchronous connector with a control plane#

The synchronous connector builds its own HCCL groups for the hidden states (afd_plugin/connectors/npu/camp2p.py:418-431) and a smaller Gloo group for the DP metadata (afd_plugin/connectors/npu/camp2p.py:460-468). It sets a control plane, CAMP2pAFDControlPlane (afd_plugin/connectors/npu/camp2p.py:385), so the DP metadata travels once per step, the same timing as the GPU connector. See The control plane: DP metadata once per step.

Step 2: CAMAsync has no control plane; its receive loop drives the FFN side#

The asynchronous connector sets control_plane = None (afd_plugin/connectors/npu/async_cam.py:283). The CAM dispatch/combine operators own both the data motion and its routing metadata, so there is no separate DP metadata path (afd_plugin/connectors/npu/async_cam.py:277-282).

So what drives the FFN side? The NPU async FFN runner loops over the layers and, for each one, calls recv_ffn_work_item (afd_plugin/v1/worker/npu/async_ffn_model_runner.py:442-446). Each work item carries its own layer index, read from the CAM metadata of the dispatch-receive, not from a control-plane payload (afd_plugin/connectors/npu/async_cam.py:497-541).

The forward context sets dp_metadata = None for each work item (afd_plugin/v1/worker/npu/async_ffn_model_runner.py:473). The connector receive is the clock: when a dispatch arrives, the runner computes that layer and sends the result back. This is the mechanism the The control plane: DP metadata once per step page names in one line.

Step 3: The operator loader#

Both connectors need the plugin's Ascend operators. The loader ensure_cam_p2p_ops_available sets the custom op-API environment, imports afd_plugin._C_ascend, and asserts the torch.ops.afd_ascend namespace (afd_plugin/compat/npu/ops.py:73-91). ensure_afd_ascend_ops_loaded is a backward-compatible alias for it (afd_plugin/compat/npu/ops.py:94-97).

The async connector needs four more operators, so it calls ensure_cam_async_ops_available, which checks the four afd_async_* ops (afd_plugin/compat/npu/ops.py:107-119). The extension afd_plugin._C_ascend is built from csrc/npu/pybind (setup.py:116-120), gated on AFD_BUILD_ASCEND_OPS or an Ascend platform (setup.py:43-54) and the SOC_VERSION (setup.py:67, setup.py:88). See Environment variables reference.

The vendored binaries

The folder connectors/npu/bin/ holds a prebuilt CAM installer (.run) and a wheel (.whl), stored with Git LFS (afd_plugin/connectors/npu/bin/). The plugin's Python loads the CMake-built afd_plugin._C_ascend; it does not import the bin/ artifacts directly. The async docs note that the source build needs no external CAM wheel (docs/npu/CAM_ASYNC_CONNECTOR_USER_GUIDE.md:277).

Step 4: Async data-parallel patches, gated to NPU#

The async path needs two extra patches. They install only when the role is attention and async_dp is on (afd_plugin/compat/npu/runtime.py:44-53), and the whole NPU patch set installs only when the device is npu (afd_plugin/__init__.py:199-209). On GPU, async_dp must be false. See Compat patches: how AFD changes vLLM without editing it.

  • async_dp_engine — swaps the attention engine entry point to a plain EngineCoreProc for async DP (afd_plugin/compat/patches/async_dp_engine.py:117-120; installed and gated at afd_plugin/compat/patches/async_dp_engine.py:414-432).
  • async_dp_forward_context — skips the DP metadata only for the async path, and rebinds the symbol in the importing modules (afd_plugin/compat/patches/async_dp_forward_context.py:88-127, afd_plugin/compat/patches/async_dp_forward_context.py:207-212).

Deep dive

NPU model wrappers and Ascend patches

Two NPU model wrappers matter for the overview.

  • GateOnlyRemoteMoE — an attention-side MoE module that computes the gate locally and sends only the experts to the FFN role (afd_plugin/model_executor/models/deepseek_v2.py:197-199). It is the NPU branch when the gate is on the attention side.
  • npu/deepseek_v4.py — the DeepSeek-V4 AFD wrapper for the Ascend native implementation, with its own decoder layer and remote-MoE classes (afd_plugin/model_executor/models/npu/deepseek_v4.py:649). The model table maps DeepseekV4ForCausalLM to this NPU wrapper only when torch_npu is importable (afd_plugin/__init__.py:109-113).

The Ascend compat patches live under afd_plugin/compat/patches/npu/. They install only on an NPU device (afd_plugin/__init__.py:199-209).

The NPU recipes and what they report

The recipe index lists both NPU connectors as "integrated v0.30 hardware validation pending"; the measured numbers come from older runtimes (recipe/README.md:36-38).

  • CAMP2p (sync). The DeepSeek-V3.2 recipe targets vLLM-Ascend v0.19.1rc1 and compares EP64 with 48A16F and 64A16F AFD deployments (recipe/npu/CAMP2pAFDConnector/deepseek_v3_2/README.md:1-11, recipe/npu/CAMP2pAFDConnector/deepseek_v3_2/README.md:28-33).
  • CAMAsync (async). The v0.26 accuracy recipe runs the full DeepSeek-V3.2 (61 layers) with DP2/TP8 attention and EP16 FFN; the index reports a 0.9522 strict match for that token split (recipe/README.md:38, recipe/npu/CAMAsyncAFDConnector/deepseek_v3_2/v0_26_accuracy/README.md:1-10).

The NPU recipes also include result images, described with their own captions on the Tuning: the knobs the repo exposes page. This page does not restate those numbers as current results.

What can go wrong#

  • Operators not built. The loader raises when afd_plugin._C_ascend is missing; build with Ascend ops enabled (afd_plugin/compat/npu/ops.py:86-90).
  • Async ops missing. The async connector raises when any of the four afd_async_* operators is absent (afd_plugin/compat/npu/ops.py:115-119).
  • async_dp on GPU. The async-DP patches are NPU-only and gated at run time; on GPU async_dp must be false (afd_plugin/compat/npu/runtime.py:44-53).
  • Expecting a control plane with the async connector. The async connector has none; the receive loop drives the FFN side (afd_plugin/connectors/npu/async_cam.py:283).

Why it matters. The NPU keeps the AFD contract but changes the transport and the driving mechanism. The async connector folds the control plane into the data operators, so the FFN side follows the receive loop, not a metadata step.

Check yourself#

  1. 1
    Which NPU connector has a control plane, and which does not?
    easy
    Show answer

    CAMP2pAFDConnector has one, CAMP2pAFDControlPlane (afd_plugin/connectors/npu/camp2p.py:385). CAMAsyncAFDConnector sets control_plane = None (afd_plugin/connectors/npu/async_cam.py:283).

  2. 2
    What two collective libraries does CAMP2p use, and for what?
    easy
    Show answer

    HCCL for the hidden states, and a smaller Gloo group for the DP metadata (afd_plugin/connectors/npu/camp2p.py:418-431, afd_plugin/connectors/npu/camp2p.py:460-468).

  3. 3
    How does the async FFN side know which layer to compute without a control plane?
    medium
    Show answer

    The runner calls recv_ffn_work_item in a loop; each item carries its layer index, read from the CAM dispatch metadata (afd_plugin/v1/worker/npu/async_ffn_model_runner.py:442-446, afd_plugin/connectors/npu/async_cam.py:497-541).

  4. 4
    How does the plugin load the Ascend operators, and what does it not load?
    medium
    Show answer

    It imports the CMake-built afd_plugin._C_ascend and asserts the torch.ops.afd_ascend namespace (afd_plugin/compat/npu/ops.py:73-91). It does not import the vendored bin/ artifacts, and the kernel internals are out of scope.

  5. 5
    When do the async-DP patches install, and why can they not run on GPU?
    hard
    Show answer

    Only when the role is attention and async_dp is on (afd_plugin/compat/npu/runtime.py:44-53), and only when the device is npu (afd_plugin/__init__.py:199-209). On GPU async_dp must be false, so the gate never opens.
